系统调用

以下对比 x86-64 Linux、AArch64 Linux、macOS arm64 三种环境里的系统调用。

系统调用可以理解成：用户程序想读写文件、打印内容、退出进程、申请内存时，不能直接操作内核资源，于是按操作系统规定把参数放进寄存器，再执行一条特殊指令进入内核。

先记住一句话：

系统调用 = 调用号 + 参数寄存器 + 进入内核的指令

说明：AArch64 和 ARM64 在这里都指 64 位 Arm 架构。Linux AArch64 和 macOS arm64 的 CPU 指令很像，但系统调用 ABI 不一样。Linux 示例不能原样搬到 macOS；macOS 入门代码也更推荐调用 libSystem 包装函数，而不是日常硬编码裸 svc 。

初学时最容易混的是这三点：

  • Linux x86-64 的 C 函数第 4 参数用 %rcx ，但 Linux syscall 第 4 参数用 %r10 。
  • Linux AArch64 的 syscall 号放在 x8 ，不是 x0 。
  • macOS arm64 不使用 Linux AArch64 的 x8 = 64; svc #0 这套约定。

2. 系统调用和 C 函数调用有什么区别

先看一个 C 函数调用：

write(1, "hello\n", 6);

如果在 macOS arm64 或 Linux 上调用 C 库里的 write ，调用的是用户态函数。这个函数内部再按操作系统规则进入内核，并且还会处理 errno 、线程取消点、动态链接等细节。

裸系统调用则更直接：

把调用号和参数放进寄存器
执行 syscall 或 svc
内核返回结果

以 write(fd, buf, count) 为例，三个参数含义是：

参数含义打印到终端时的常用值
fd文件描述符1 表示标准输出 stdout
buf缓冲区地址字符串的地址
count写多少字节字符串长度

标准文件描述符通常是：

fd名字含义
0stdin标准输入
1stdout标准输出
2stderr标准错误

注意：系统调用不认识 “字符串” 这个高级概念。 write 只知道一个地址和一个字节数，所以汇编里必须显式给出 buf 和 count 。

3. Linux x86-64： syscall

文件名： hello-syscall-x86-64.s

.section .rodata
msg:
    .ascii "Hello from Linux x86-64 syscall\n"  # 写入原始字节，不自动追加 \0
msg_len = . - msg                              # 当前地址 . 减去 msg 地址，得到字符串长度

.section .text
.global _start
_start:
    # Linux x86-64 syscall 约定：
    # rax = 系统调用号
    # rdi = 第 1 个参数
    # rsi = 第 2 个参数
    # rdx = 第 3 个参数
    # r10 = 第 4 个参数
    # r8  = 第 5 个参数
    # r9  = 第 6 个参数
    #
    # 目标：write(1, msg, msg_len)
    # write 的系统调用号是 1。
    # fd = 1 表示标准输出 stdout。
    mov $1, %rax                                # rax = 1，选择 write
    mov $1, %rdi                                # rdi = fd = 1
    lea msg(%rip), %rsi                         # rsi = msg 的地址，注意不是 msg 里的内容
    mov $msg_len, %rdx                          # rdx = 要写出的字节数
    syscall                                     # 进入内核，执行 write

    # syscall 返回后，rax 保存返回值。
    # 对 write 来说，成功时 rax = 实际写出的字节数。
    # 这个入门例子暂时不检查错误，直接退出。

    # 目标：exit(0)
    # exit 的系统调用号是 60。
    # 第 1 参数 status 放在 rdi。
    mov $60, %rax                               # rax = 60，选择 exit
    xor %rdi, %rdi                              # rdi = 0，退出码为 0
    syscall                                     # 进入内核，结束进程

编译运行：

as --64 hello-syscall-x86-64.s -o hello-syscall-x86-64.o
ld hello-syscall-x86-64.o -o hello-syscall-x86-64
./hello-syscall-x86-64
echo $?

预期输出：

Hello from Linux x86-64 syscall
0

重点看这一行：

lea msg(%rip), %rsi

msg 是标签，也就是地址名字。 write 需要的是缓冲区地址，所以这里用 lea 把地址算出来。如果写成读取内存值，就会把字符串开头几个字节当成一个整数，而不是把字符串地址传给内核。

4. Linux AArch64： svc #0

文件名： hello-syscall-aarch64.s

.section .rodata
msg:
    .ascii "Hello from Linux AArch64 syscall\n" // 写入原始字节，不自动追加 \0
msg_len = . - msg                              // 当前地址 . 减去 msg 地址，得到字符串长度

.section .text
.global _start
_start:
    // Linux AArch64 syscall 约定：
    // x8 = 系统调用号
    // x0 = 第 1 个参数
    // x1 = 第 2 个参数
    // x2 = 第 3 个参数
    // x3 = 第 4 个参数
    // x4 = 第 5 个参数
    // x5 = 第 6 个参数
    //
    // 目标：write(1, msg, msg_len)
    // write 的系统调用号是 64。
    // fd = 1 表示标准输出 stdout。
    mov x8, #64                                 // x8 = 64，选择 write
    mov x0, #1                                  // x0 = fd = 1
    adrp x1, msg                                // x1 = msg 所在 4KB 页的页地址
    add x1, x1, :lo12:msg                       // x1 = x1 + msg 页内偏移，得到完整地址
    mov x2, #msg_len                            // x2 = 要写出的字节数
    svc #0                                      // 进入 Linux 内核，执行 write

    // svc 返回后，x0 保存返回值。
    // 对 write 来说，成功时 x0 = 实际写出的字节数。
    // 这个入门例子暂时不检查错误，直接退出。

    // 目标：exit(0)
    // exit 的系统调用号是 93。
    // 第 1 参数 status 放在 x0。
    mov x8, #93                                 // x8 = 93，选择 exit
    mov x0, #0                                  // x0 = 0，退出码为 0
    svc #0                                      // 进入内核，结束进程

编译运行：

as hello-syscall-aarch64.s -o hello-syscall-aarch64.o
ld hello-syscall-aarch64.o -o hello-syscall-aarch64
./hello-syscall-aarch64
echo $?

预期输出：

Hello from Linux AArch64 syscall
0

这里的取地址分成两条指令：

adrp x1, msg
add x1, x1, :lo12:msg

可以先这样理解：

  • adrp 取 msg 所在页的地址。
  • add ... :lo12:msg 加上页内偏移。
  • 两条合起来得到 msg 的完整地址。

对于很近的标签，有时也能看到更短的 adr x1, msg 。以下示例更常用 adrp + add ，因为这种写法更接近真实项目里访问全局符号的形式。

5. macOS arm64：推荐先调用 libSystem

macOS arm64 可以写裸 svc #0x80 ，但入门阶段更推荐先从 C 运行时和 libSystem 开始。这样写的是正常 Mach-O 程序，由 clang 负责链接，系统库负责处理平台细节。

文件名： hello-libsystem-macos-arm64.s

.section __TEXT,__const
msg:
    .ascii "Hello from macOS arm64 libSystem write\n"
msg_len = . - msg

.text
.globl _main
.p2align 2
_main:
    // macOS arm64 通常从 C 运行时调用 _main。
    // 下面要 bl _write。bl 会覆盖 x30/lr，所以 _main 是非叶子函数。
    // 非叶子函数返回前需要恢复 x30，否则不知道怎么回到 C 运行时。
    stp x29, x30, [sp, #-16]!                  // sp -= 16；保存帧指针 x29 和返回地址 x30
    mov x29, sp                                // 建立当前函数的帧指针

    // ssize_t write(int fd, const void *buf, size_t count)
    //
    // macOS arm64 调 C 函数时使用 AArch64 调用约定：
    // x0 = 第 1 个参数
    // x1 = 第 2 个参数
    // x2 = 第 3 个参数
    // x0 = 返回值
    //
    // 目标：write(1, msg, msg_len)
    mov x0, #1                                 // x0 = fd = 1，标准输出 stdout
    adrp x1, msg@PAGE                          // x1 = msg 所在 4KB 页的页地址
    add x1, x1, msg@PAGEOFF                    // x1 = x1 + msg 页内偏移，得到完整地址
    mov x2, #msg_len                           // x2 = 要写出的字节数
    bl _write                                  // 调用 libSystem 里的 write()

    // _write 返回后，x0 是返回值。
    // 这里明确让 main 返回 0，不把 write 的返回值当进程退出码。
    mov w0, #0                                 // main 返回 0，表示成功

    ldp x29, x30, [sp], #16                    // 恢复 x29/x30；sp += 16
    ret                                        // 返回给 C 运行时

编译运行：

clang hello-libsystem-macos-arm64.s -o hello-libsystem-macos-arm64
./hello-libsystem-macos-arm64
echo $?

预期输出：

Hello from macOS arm64 libSystem write
0

macOS 代码里有两个平台特点：

  • C 符号名前通常有下划线：C 里的 main 在汇编里写 _main ， write 写 _write 。
  • Mach-O 取全局地址常用 @PAGE 和 @PAGEOFF 重定位。

6. macOS arm64：裸 svc #0x80 长什么样

这一节用于理解机制，不作为日常推荐写法。macOS 的系统库会在裸内核接口外面做包装，实际项目里应该优先调用 libSystem。

Darwin arm64 的裸 UNIX syscall 常见形式是：

x16 = syscall number
x0, x1, x2, ... = 参数
svc #0x80

文件名： hello-raw-syscall-macos-arm64.s

.section __TEXT,__const
msg:
    .ascii "Hello from macOS arm64 raw syscall\n"
msg_len = . - msg

.text
.globl _main
.p2align 2
_main:
    // 这个示例不调用其他函数，只执行 svc 进入内核。
    // 因此不需要像调用 _write 那样保存 x30。
    //
    // Darwin/macOS arm64 裸 UNIX syscall 约定：
    // x16 = 系统调用号
    // x0  = 第 1 个参数
    // x1  = 第 2 个参数
    // x2  = 第 3 个参数
    //
    // 目标：write(1, msg, msg_len)
    // sys/syscall.h 中 SYS_write = 4。
    mov x16, #4                                // x16 = 4，选择 write
    mov x0, #1                                 // x0 = fd = 1，标准输出 stdout
    adrp x1, msg@PAGE                          // x1 = msg 所在页
    add x1, x1, msg@PAGEOFF                    // x1 = msg 的完整地址
    mov x2, #msg_len                           // x2 = 要写出的字节数
    svc #0x80                                  // 进入 Darwin 内核，执行 write

    // 目标：exit(0)
    // sys/syscall.h 中 SYS_exit = 1。
    mov x16, #1                                // x16 = 1，选择 exit
    mov x0, #0                                 // x0 = 0，退出码为 0
    svc #0x80                                  // 进入内核，结束进程

    // 理论上 exit 不会返回。保留 ret 只是为了让控制流完整。
    ret

编译运行：

clang hello-raw-syscall-macos-arm64.s -o hello-raw-syscall-macos-arm64
./hello-raw-syscall-macos-arm64
echo $?

预期输出：

Hello from macOS arm64 raw syscall
0

对比 Linux AArch64，输出中可能看到这些值长得很像，但关键数字完全不同：

内容Linux AArch64macOS arm64 裸 syscall
调用号寄存器x8x16
进入内核svc #0svc #0x80
write 调用号644
exit 调用号931

这就是为什么不能把 Linux AArch64 的系统调用代码直接复制到 macOS。

7. 返回值和错误处理

7.1 Linux：错误通常是负数

Linux 裸 syscall 成功时返回非负值；失败时通常返回 -errno 。例如 EBADF 的值是 9 ，裸 syscall 失败时返回 -9 。

下面故意把 fd 设成 -1 ，让 write 失败，然后把 errno 当作退出码。因为退出码一般只观察低 8 位，所以这里用 9 这种小值很适合演示。

文件名： bad-write-x86-64.s

.section .rodata
msg:
    .ascii "this write will fail\n"
msg_len = . - msg

.section .text
.global _start
_start:
    # write(-1, msg, msg_len)
    # fd = -1 不是有效文件描述符，预期返回 -EBADF，也就是 -9。
    mov $1, %rax                                # rax = write 调用号
    mov $-1, %rdi                               # rdi = fd = -1，故意制造错误
    lea msg(%rip), %rsi                         # rsi = msg 地址
    mov $msg_len, %rdx                          # rdx = 字符串长度
    syscall                                     # 返回值在 rax

    # if (rax < 0) rax = -rax;
    # AT&T 语法里 cmp $0, %rax 表示比较 rax 和 0。
    cmp $0, %rax                                # 看返回值是否小于 0
    jge ok                                      # 如果 rax >= 0，说明没有错误
    neg %rax                                    # rax = -rax，把 -errno 变成 errno

    # exit(errno)
    mov %rax, %rdi                              # rdi = errno
    mov $60, %rax                               # rax = exit 调用号
    syscall

ok:
    # 如果没有失败，就返回 0。
    xor %rdi, %rdi                              # rdi = 0
    mov $60, %rax                               # rax = exit 调用号
    syscall

运行：

as --64 bad-write-x86-64.s -o bad-write-x86-64.o
ld bad-write-x86-64.o -o bad-write-x86-64
./bad-write-x86-64
echo $?

预期输出：

9

AArch64 Linux 版本逻辑相同，只是寄存器和进入内核指令不同。

文件名： bad-write-aarch64.s

.section .rodata
msg:
    .ascii "this write will fail\n"
msg_len = . - msg

.section .text
.global _start
_start:
    // write(-1, msg, msg_len)
    // fd = -1 不是有效文件描述符，预期返回 -EBADF，也就是 -9。
    mov x8, #64                                 // x8 = write 调用号
    mov x0, #-1                                 // x0 = fd = -1，故意制造错误
    adrp x1, msg                                // x1 = msg 所在页
    add x1, x1, :lo12:msg                       // x1 = msg 的完整地址
    mov x2, #msg_len                            // x2 = 字符串长度
    svc #0                                      // 返回值在 x0

    // if (x0 < 0) x0 = -x0;
    cmp x0, #0                                  // 看返回值是否小于 0
    b.ge ok                                     // 如果 x0 >= 0，说明没有错误
    neg x0, x0                                  // x0 = -x0，把 -errno 变成 errno

    // exit(errno)
    mov x8, #93                                 // x8 = exit 调用号
    svc #0

ok:
    mov x0, #0                                  // x0 = 0
    mov x8, #93                                 // x8 = exit 调用号
    svc #0

运行：

as bad-write-aarch64.s -o bad-write-aarch64.o
ld bad-write-aarch64.o -o bad-write-aarch64
./bad-write-aarch64
echo $?

预期输出：

9

7.2 macOS 裸 syscall：错误看 carry flag

macOS arm64 裸 syscall 失败时，常见模式是设置 carry flag，并在 x0 放 errno。下面同样用无效 fd 触发 EBADF = 9 。

文件名： bad-write-raw-macos-arm64.s

.section __TEXT,__const
msg:
    .ascii "this write will fail\n"
msg_len = . - msg

.text
.globl _main
.p2align 2
_main:
    // write(-1, msg, msg_len)
    // Darwin/macOS 裸 syscall：
    // x16 = syscall number
    // x0  = arg1
    // x1  = arg2
    // x2  = arg3
    mov x16, #4                                // x16 = SYS_write
    mov x0, #-1                                // x0 = fd = -1，故意制造错误
    adrp x1, msg@PAGE                          // x1 = msg 所在页
    add x1, x1, msg@PAGEOFF                    // x1 = msg 的完整地址
    mov x2, #msg_len                           // x2 = 字符串长度
    svc #0x80                                  // 返回后如果失败，carry flag 会被置位

    b.cs failed                                // carry set，说明 syscall 失败

    // 如果没有失败，就 exit(0)。
    mov x16, #1                                // x16 = SYS_exit
    mov x0, #0                                 // x0 = 0
    svc #0x80

failed:
    // 失败时 x0 已经是 errno，例如 EBADF = 9。
    // 直接 exit(errno)。
    mov x16, #1                                // x16 = SYS_exit
    svc #0x80

运行：

clang bad-write-raw-macos-arm64.s -o bad-write-raw-macos-arm64
./bad-write-raw-macos-arm64
echo $?

预期输出：

9

如果调用 libSystem 的 _write ，错误处理又回到 C 函数规则：失败时返回 -1 ，并设置全局 errno 。所以本节讲的是 “裸 syscall 返回规则”，不是 _write 包装函数的返回规则。

8. 第 4 个参数为什么 x86-64 要用 %r10

x86-64 Linux 的 C 函数调用约定和 syscall 约定很像，但第 4 个参数不同：

参数C 函数调用Linux syscall
第 1 参数%rdi%rdi
第 2 参数%rsi%rsi
第 3 参数%rdx%rdx
第 4 参数%rcx%r10
第 5 参数%r8%r8
第 6 参数%r9%r9

原因是 syscall 指令本身会使用 %rcx 和 %r11 保存返回地址和标志位相关信息，所以内核 ABI 不把第 4 个参数放在 %rcx 。

这意味着：如果以后写 mmap 、 openat 这类参数更多的 syscall，x86-64 Linux 第 4 参数一定要放 %r10 ，不要照着 C 函数 ABI 放 %rcx 。

AArch64 Linux 没有这个坑：

参数AArch64 C 函数调用Linux AArch64 syscall
第 1 参数x0x0
第 2 参数x1x1
第 3 参数x2x2
第 4 参数x3x3
第 5 参数x4x4
第 6 参数x5x5
调用号不适用x8

9. 如何查询系统调用号

不要死记所有系统调用号。实践中经常直接查系统头文件或内核表。

Linux x86-64 常见位置：

grep -E '#define[[:space:]]+__NR_(read|write|exit)[[:space:]]' \
  /usr/include/x86_64-linux-gnu/asm/unistd_64.h

输出可能类似：

#define __NR_read 0
#define __NR_write 1
#define __NR_exit 60

Linux AArch64 常见位置是 asm-generic syscall 表。不同发行版路径可能不同，可以这样找：

grep -R -E '#define[[:space:]]+__NR_(read|write|exit)[[:space:]]' /usr/include 2>/dev/null

AArch64 常见结果：

#define __NR_read 63
#define __NR_write 64
#define __NR_exit 93

macOS 可以从当前 SDK 查：

sdk=$(xcrun --show-sdk-path)
grep -E '#define[[:space:]]+SYS_(read|write|exit)[[:space:]]' "$sdk/usr/include/sys/syscall.h"

常见结果：

#define SYS_exit  1
#define SYS_read  3
#define SYS_write 4

还可以看 macOS arm64 的 trap 宏：

sdk=$(xcrun --show-sdk-path)
grep -n 'mov x16.*trap_number\|svc #SWI_SYSCALL' \
  "$sdk/usr/include/mach/arm/syscall_sw.h"
grep -n 'SWI_SYSCALL' "$sdk/usr/include/mach/arm/vm_param.h"

这些头文件有助于确认：macOS arm64 裸 trap 是 x16 加 svc #0x80 这条线。

10. 用工具观察系统调用

Linux 上可以用 strace 看程序真的发出了哪些 syscall：

strace -e write,exit ./hello-syscall-x86-64

输出可能类似：

write(1, "Hello from Linux x86-64 syscall\n", 32) = 32
exit(0) = ?

如果是在真实 AArch64 Linux 上：

strace -e write,exit ./hello-syscall-aarch64

macOS 上可以尝试 dtruss ：

sudo dtruss -t write ./hello-libsystem-macos-arm64

macOS 的 dtruss 可能受 SIP、权限和系统版本影响。如果运行不了，不代表汇编程序错了；先以程序输出和退出码为准。

11. 三个平台最小模板

11.1 x86-64 Linux 裸 syscall 模板

.section .text
.global _start
_start:
    mov $SYSNO, %rax      # syscall number
    mov $ARG1, %rdi       # arg1
    mov $ARG2, %rsi       # arg2
    mov $ARG3, %rdx       # arg3
    syscall               # return value in rax

11.2 AArch64 Linux 裸 syscall 模板

.section .text
.global _start
_start:
    mov x8, #SYSNO        // syscall number
    mov x0, #ARG1         // arg1
    mov x1, #ARG2         // arg2
    mov x2, #ARG3         // arg3
    svc #0                // return value in x0

11.3 macOS arm64 调 libSystem 模板

.text
.globl _main
.p2align 2
_main:
    stp x29, x30, [sp, #-16]!
    mov x29, sp

    mov x0, #ARG1         // arg1
    mov x1, #ARG2         // arg2
    mov x2, #ARG3         // arg3
    bl _function          // call libSystem function, return value in x0

    mov w0, #0            // main returns 0
    ldp x29, x30, [sp], #16
    ret

11.4 macOS arm64 裸 syscall 模板

.text
.globl _main
.p2align 2
_main:
    mov x16, #SYSNO       // syscall number
    mov x0, #ARG1         // arg1
    mov x1, #ARG2         // arg2
    mov x2, #ARG3         // arg3
    svc #0x80             // return value in x0; error usually sets carry

12. 常见坑

12.1 把 Linux AArch64 syscall 照搬到 macOS

Linux AArch64:

mov x8, #64
svc #0

macOS arm64 裸 syscall:

mov x16, #4
svc #0x80

这两个不是同一个 ABI。寄存器、立即数、调用号都不一样。

12.2 忘记 syscall 会覆盖返回值寄存器

执行 syscall 或 svc 后，返回值会放进 %rax 或 x0 。如果原来在这些寄存器里存了重要数据，返回后就被覆盖了。

12.3 x86-64 第 4 参数放错寄存器

Linux x86-64 syscall 第 4 参数是 %r10 ，不是 %rcx 。写三个参数的 write 、 read 时看不出来，写四个及以上参数时就会出错。

12.4 把 .ascii 当成 C 字符串

.ascii "hello\n" 不会自动追加 \0 。但 write 不需要 \0 ， write 只看 count 。所以以下用：

msg_len = . - msg

来计算准确字节数。

12.5 把 exit 和 C 库 exit() 完全等同

裸 exit syscall 直接进入内核结束执行。C 库的 exit() 还会做用户态清理，例如运行退出处理函数、刷新标准 I/O 缓冲等。为了最小化示例，Linux 裸程序直接使用 exit syscall；真实 C 程序通常让 C 运行时和 libc 处理这些细节。

13. 小练习

  1. 把三个 hello 示例里的 fd 从 1 改成 2 ，观察输出仍然出现，但输出走的是 stderr。
  2. 把 msg_len 改小，例如改成 5 ，观察 write 只输出前几个字节。
  3. 在 Linux x86-64 示例中，故意把 lea msg(%rip), %rsi 改成 mov msg(%rip), %rsi ，运行后观察错误或崩溃，理解 “地址” 和 “地址里的值” 的差别。
  4. 在 macOS 上分别运行 libSystem 版本和裸 syscall 版本，比较两段代码的入口、调用方式和退出方式。
  5. 用 strace 或 dtruss 观察 write 的参数和返回值。
