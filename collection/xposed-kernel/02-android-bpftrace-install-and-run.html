Android 下配置 bpftrace 并使用 bt 脚本抓取数据

这篇文章记录一条完整的 Android bpftrace 实战链路：把 bpftrace 工具集放到 root 设备上，配置内核头文件环境，运行 .bt 脚本，再用 uprobe 抓取应用里的 TLS 明文数据。

最终会跑通三件事：

  1. 在 Android 上部署 bpftools ，用 wrapper 正确启动 bpftrace 。
  2. 配置 BPFTRACE_KERNEL_SOURCE ，解决 linux/types.h 找不到的问题。
  3. 编写并运行 sslsnoop.bt ，挂到应用真实加载的 libssl.so ，抓到 SSL_read / SSL_write 的明文 buffer。

先看最终运行命令

设备上准备好工具和脚本后，核心命令是：

cd /data/local/tmp/bpftools

export KH=/data/local/tmp/kheaders-$(uname -r)
export BPFTRACE_KERNEL_SOURCE="$KH"
export BPFTRACE_KERNEL_BUILD="$KH"

./bpftrace /data/local/tmp/sslsnoop.bt

如果脚本挂到了目标应用真正加载的 SSL 库，触发应用网络请求后会看到类似输出：

Attaching 13 probes...
Tracing SSL/TLS... Hit Ctrl-C to end.
TIME(us)   TID      COMM             LAT(us)   RET FUNC
13786991   29988    RxCachedThreadS       76    24 SSL_write
buffer: 24: PRI * HTTP/2.0\x0d\x0a\x0d\x0aSM\x0d\x0a\x0d\x0a

21579036   30005    thon-spider.com       17   171 SSL_read
buffer: 16384: \x00\x00\xa2\x00\x01\x00\x00\x00\x03<html>\x0d\x0a<head><title>301 Moved Permanently</title></hea

这里已经证明 bpftrace 成功挂上了用户态 SSL 函数，并从应用进程里读到了解密后的数据。

一、环境和前置条件

本文使用下面的设备条件。你不需要完全一致，但差异会影响路径、脚本和报错：

项目本文验证环境影响
AndroidAndroid 16 / API 36新系统一般 BPF、tracefs、APEX 结构更完整
CPU 架构arm64 / aarch64工具包要使用 arm64 版本
Linux 内核5.10.xkheaders、BTF、uprobe 能力和内核配置相关
bpftracev0.21.2脚本语法要兼容这个版本
权限root shellbpftrace 加载 BPF 程序需要 root
目标类型Java/Native Android appTLS 库通常来自 Conscrypt、Cronet 或系统 libssl

需要提前准备：

  • 电脑端可以使用 adb 。
  • 设备已经 root， adb shell su -c id 能返回 uid=0(root) 。
  • 设备内核支持 BPF、tracefs、uprobe。
  • 已经准备好适合设备架构的 bpftools-<arch>.tar.gz 。

可以先确认设备架构：

adb shell getprop ro.product.cpu.abilist64

arm64 设备通常输出：

arm64-v8a

二、安装 bpftools 到 Android

这里假设工具包叫 bpftools-arm64.tar.gz 。如果是 x86_64 模拟器，换成对应架构包。

在电脑端执行：

adb push bpftools-arm64.tar.gz /data/local/tmp/
adb shell 'cd /data/local/tmp && tar xf bpftools-arm64.tar.gz'

解压后目录类似：

/data/local/tmp/bpftools/
├── bpftrace              # wrapper，推荐使用这个入口
├── run.sh                # 启动前设置工具环境
├── setup.sh              # 设置 PATH、LD_LIBRARY_PATH、ARCH、TMPDIR
├── bin/
│   └── bpftrace          # 真正的 bpftrace ELF
├── lib/
│   ├── libbcc.so
│   ├── libbpf.so
│   ├── libclang.so
│   └── ...
└── share/
    └── bpftrace/

推荐始终使用 wrapper：

adb shell
su
cd /data/local/tmp/bpftools
./bpftrace --version

不要直接运行：

./bin/bpftrace --version

bpftools/bpftrace 通常会通过 run.sh 自动设置 PATH 、 LD_LIBRARY_PATH 、 ARCH 、 TMPDIR 等变量。直接运行 bin/bpftrace 时，动态库和临时目录环境可能不完整，报错会绕得多。

最小检查：

cd /data/local/tmp/bpftools
./bpftrace -e 'BEGIN { printf("ok\n"); exit(); }'

预期输出：

Attaching 1 probe...
ok

如果这里报：

ERROR: bpftrace currently only supports running as the root user.

说明当前 shell 不是 root。需要先 su ，或者用：

adb shell 'su -c "cd /data/local/tmp/bpftools && ./bpftrace --version"'

三、配置内核头文件环境

Android 上常见的 bpftrace 编译错误是：

WARNING: Could not find kernel headers in /lib/modules/5.10.x/source or /lib/modules/5.10.x/build.
/bpftrace/include/clang_workarounds.h:14:10: fatal error: 'linux/types.h' file not found

原因很直接：bpftrace 会调用 clang 编译 BPF 程序，clang 需要当前运行内核对应的头文件。Linux 发行版常见的 /lib/modules/$(uname -r)/build 在 Android 上通常不存在。

3.1 检查 kheaders

在设备 root shell 中执行：

uname -r
ls -l /sys/kernel/kheaders.tar.xz

如果内核开启了 CONFIG_IKHEADERS ，通常能看到：

-r--r--r-- 1 root root ... /sys/kernel/kheaders.tar.xz

如果文件不存在，可以尝试：

modprobe kheaders
ls -l /sys/kernel/kheaders.tar.xz

不少 Android 设备没有 modprobe 或没有把 kheaders 做成模块。如果仍然没有，只能准备和设备 uname -r 完全匹配的内核源码或构建输出目录，再推到设备上。

3.2 解压 kheaders

使用 uname -r 作为目录名，避免不同内核版本混在一起：

cd /data/local/tmp/bpftools

export KH=/data/local/tmp/kheaders-$(uname -r)
mkdir -p "$KH"

cd "$KH"
/data/local/tmp/bpftools/xzcat /sys/kernel/kheaders.tar.xz | tar -x

检查关键头文件：

ls -l "$KH/include/linux/types.h"
ls -ld "$KH/include/uapi" "$KH/arch/arm64/include"

预期能看到：

/data/local/tmp/kheaders-5.10.x/include/linux/types.h
/data/local/tmp/kheaders-5.10.x/include/uapi
/data/local/tmp/kheaders-5.10.x/arch/arm64/include

3.3 设置 bpftrace 环境变量

回到工具目录：

cd /data/local/tmp/bpftools

export KH=/data/local/tmp/kheaders-$(uname -r)
export BPFTRACE_KERNEL_SOURCE="$KH"
export BPFTRACE_KERNEL_BUILD="$KH"

再跑一个 tracepoint 测试：

./bpftrace -e 'tracepoint:raw_syscalls:sys_enter { @[comm] = count(); }'

运行几秒后按 Ctrl-C ，正常会打印按进程名聚合的系统调用次数：

Attaching 1 probe...

@[adbd]: 122
@[system_server]: 508
@[bpftrace]: 31

如果还遇到 asm/types.h 或架构相关头文件找不到，可以额外加 include 路径：

export BPFTRACE_EXTRA_CFLAGS="-I$KH/include/uapi -I$KH/arch/arm64/include/uapi -I$KH/arch/arm64/include/generated/uapi"

然后重新运行脚本。

BTF warning 不一定是致命错误

如果看到：

libbpf: kernel BTF is missing at '/sys/kernel/btf/vmlinux'

说明内核没有暴露 vmlinux BTF。对本文这种 uprobe:/path/to/libssl.so:SSL_read 脚本来说，通常不是致命问题。

依赖内核结构体类型、 args 字段、kfunc 等能力的脚本才更容易受 BTF 缺失影响。

四、准备 bt 脚本

bpftrace 脚本通常以 .bt 结尾。本文用 sslsnoop.bt 演示抓取 Android 应用的 TLS 明文。

重点不是 “解密 TLS 包”，而是在加密前后挂用户态 SSL 函数：

应用代码
  -> SSL_write 明文进入 SSL 库
  -> TLS 加密后写到 socket

socket 收到 TLS 密文
  -> SSL_read 解密
  -> 明文返回应用代码

所以只要能挂到目标进程实际使用的 SSL_read / SSL_write ，就能看到明文 buffer。

4.1 先找目标应用加载了哪个 libssl

不要先入为主地写：

uprobe:libssl:SSL_read

Android 应用不一定加载 /system/lib64/libssl.so 。实际路径可能是：

/apex/com.android.conscrypt/lib64/libssl.so
/apex/com.android.tethering/lib64/stable_cronet_libssl.so
/system/lib64/libssl.so
/product/lib64/libssl.so
/data/app/.../lib/arm64/libssl.so

先找到目标应用 PID。比如查看当前前台应用：

adb shell 'dumpsys window | grep -E "mCurrentFocus|mFocusedApp"'

输出类似：

mCurrentFocus=Window{... u0 com.yuanrenxue.challenge/com.yuanrenxue.challenge.activity.MainActivity}

再查进程：

adb shell 'ps -A | grep com.yuanrenxue.challenge'

假设 PID 是 28833 ，用 root 读取 maps：

adb shell 'su -c "grep -Ei '\''ssl|crypto|cronet|conscrypt|webview'\'' /proc/28833/maps | head -100"'

可能看到：

/apex/com.android.tethering/lib64/stable_cronet_libssl.so
/apex/com.android.tethering/lib64/stable_cronet_libcrypto.so
/apex/com.android.conscrypt/lib64/libssl.so
/apex/com.android.conscrypt/lib64/libcrypto.so

这里说明目标应用走的是 Conscrypt 和 Cronet，而不是 /system/lib64/libssl.so 。脚本必须挂这些真实路径，否则 bpftrace 会显示 Attaching ... probes... ，但应用怎么操作都没有输出。

4.2 检查 SSL 符号是否存在

用 readelf 确认库里导出了目标函数：

adb shell 'readelf -Ws /apex/com.android.conscrypt/lib64/libssl.so | grep -E " SSL_read$| SSL_write$| SSL_do_handshake$"'
adb shell 'readelf -Ws /apex/com.android.tethering/lib64/stable_cronet_libssl.so | grep -E " SSL_read$| SSL_write$| SSL_do_handshake$"'

正常能看到：

SSL_read
SSL_write
SSL_do_handshake

如果没有这些符号，说明这个库不是你要挂的库，或者符号被隐藏 / 裁剪了。

4.3 编写 sslsnoop.bt

把下面内容保存到设备。这里放到 /data/local/tmp/sslsnoop.bt ，而不是直接写进 bpftools 目录，是为了避开工具目录 owner 和旧文件尾部残留的问题：

adb shell 'cat > /data/local/tmp/sslsnoop.bt' <<'EOF'
config = {
  missing_probes = "ignore";
}

BEGIN
{
  printf("Tracing SSL/TLS... Hit Ctrl-C to end.\n");
  printf("%-10s %-8s %-16s %7s %5s %s\n",
         "TIME(us)", "TID", "COMM", "LAT(us)", "RET", "FUNC");
}

uprobe:/apex/com.android.conscrypt/lib64/libssl.so:SSL_read,
uprobe:/apex/com.android.conscrypt/lib64/libssl.so:SSL_write,
uprobe:/apex/com.android.tethering/lib64/stable_cronet_libssl.so:SSL_read,
uprobe:/apex/com.android.tethering/lib64/stable_cronet_libssl.so:SSL_write
{
  @start_ssl[tid] = nsecs;
  @func_ssl[tid] = func;
  @buffer[tid] = arg1;
  @buffer_len[tid] = arg2;
}

uprobe:/apex/com.android.conscrypt/lib64/libssl.so:SSL_do_handshake,
uprobe:/apex/com.android.tethering/lib64/stable_cronet_libssl.so:SSL_do_handshake
{
  @start_ssl[tid] = nsecs;
  @func_ssl[tid] = func;
}

uretprobe:/apex/com.android.conscrypt/lib64/libssl.so:SSL_read,
uretprobe:/apex/com.android.conscrypt/lib64/libssl.so:SSL_write,
uretprobe:/apex/com.android.tethering/lib64/stable_cronet_libssl.so:SSL_read,
uretprobe:/apex/com.android.tethering/lib64/stable_cronet_libssl.so:SSL_write
/@start_ssl[tid]/
{
  printf("%-10u %-8d %-16s %7u %5d %s\n", elapsed / 1000,
         tid, comm, (nsecs - @start_ssl[tid]) / 1000, retval, @func_ssl[tid]);
  printf("buffer: %d: %r\n", @buffer_len[tid], buf(@buffer[tid], @buffer_len[tid]));
  delete(@start_ssl[tid]);
  delete(@func_ssl[tid]);
  delete(@buffer[tid]);
  delete(@buffer_len[tid]);
}

uretprobe:/apex/com.android.conscrypt/lib64/libssl.so:SSL_do_handshake,
uretprobe:/apex/com.android.tethering/lib64/stable_cronet_libssl.so:SSL_do_handshake
/@start_ssl[tid]/
{
  printf("%-10u %-8d %-16s %7u %5d %s\n", elapsed / 1000,
         tid, comm, (nsecs - @start_ssl[tid]) / 1000, retval, @func_ssl[tid]);
  delete(@start_ssl[tid]);
  delete(@func_ssl[tid]);
}
EOF

根据你的目标应用，把上面的库路径替换成 /proc/<pid>/maps 里看到的真实 libssl.so 路径。

不建议挂 libcrypto.so

Android 上的 BoringSSL/Conscrypt 可能开启 FIPS 完整性校验。对 libcrypto.so 下 uprobe 可能会修改代码页断点，导致加载 libcrypto 的进程报：

FIPS integrity test failed.
Aborted

所以抓 TLS 明文时优先挂 libssl.so 的 SSL_read / SSL_write 。除非明确知道风险，不要把 RSA_sign 、 RSA_verify 、 rsa_ossl_* 这类 libcrypto.so probe 加进去。

五、运行 bt 脚本并抓数据

进入 root shell：

adb shell
su
cd /data/local/tmp/bpftools

设置 headers 环境：

export KH=/data/local/tmp/kheaders-$(uname -r)
export BPFTRACE_KERNEL_SOURCE="$KH"
export BPFTRACE_KERNEL_BUILD="$KH"

先用 -d 做编译检查：

./bpftrace -d /data/local/tmp/sslsnoop.bt >/dev/null

如果退出码是 0 ，说明脚本语法、符号路径和编译阶段基本没问题。 -d 输出很多 libbpf debug 信息是正常的。

正式运行：

./bpftrace /data/local/tmp/sslsnoop.bt

另一个终端触发目标 app 网络请求：

# 如果目标 Activity 没有 exported，直接 am start 可能失败。
# 用 monkey 走 launcher 入口更通用。
adb shell 'monkey -p com.yuanrenxue.challenge -c android.intent.category.LAUNCHER 1'

或者手动打开应用，点击触发请求的按钮。

正常输出类似：

Attaching 13 probes...
Tracing SSL/TLS... Hit Ctrl-C to end.
TIME(us)   TID      COMM             LAT(us)   RET FUNC
12784324   29971    SentryAsyncConn       18   734 SSL_write
buffer: 734: POST /api/3/envelope/ HTTP/1.1\x0d\x0aUser-Agent: sentry.java.android/

13786991   29988    RxCachedThreadS       76    24 SSL_write
buffer: 24: PRI * HTTP/2.0\x0d\x0a\x0d\x0aSM\x0d\x0a\x0d\x0a

21579036   30005    thon-spider.com       17   171 SSL_read
buffer: 16384: \x00\x00\xa2\x00\x01\x00\x00\x00\x03<html>\x0d\x0a<head><title>301 Moved Permanently</title></hea

这些字段含义：

字段含义
TIME(us)bpftrace 启动后的相对时间
TID触发 SSL 函数的线程 ID
COMM当前线程名，Android 网络线程名经常会被设置成域名片段
LAT(us)从函数入口到返回的耗时
RETSSL 函数返回值，通常是实际读写字节数， -1 表示本次没有成功读写
FUNC触发的 SSL 函数
buffer从 arg1 指向的用户态 buffer 读取出的内容

HTTP/1.1 请求通常能直接看到 header 和 body。HTTP/2 则是二进制帧，所以会看到：

PRI * HTTP/2.0

以及大量 \x00 、 \x01 这样的字节。它不是没抓到，而是协议本身已经不是纯文本行协议。

六、常见报错和修复

6.1 Unknown function: has_key

报错：

ERROR: Unknown function: has_key
/has_key(@start_ssl, tid)/

原因是当前 bpftrace 版本不支持 has_key() 。在 v0.21.2 上可以改成 map 取值判断：

/@start_ssl[tid]/

也就是把：

/has_key(@start_ssl, tid)/

改成：

/@start_ssl[tid]/

这里保存的是 nsecs 时间戳，实际运行中不会是 0 ，所以适合作为存在性判断。

6.2 missing_probes must be literal

报错：

ERROR: Assignemnt for missing_probes must be literal.
  missing_probes = ignore;

改成字符串：

config = {
  missing_probes = "ignore";
}

也可以不用 config 块，运行时设置：

export BPFTRACE_MISSING_PROBES=ignore

6.3 delete() only expects maps to be provided

报错：

ERROR: delete() only expects maps to be provided
  delete(@start_ssl, tid);

当前版本需要写成：

delete(@start_ssl[tid]);

不要写：

delete(@start_ssl, tid);

6.4 uprobe target file 'libssl' does not exist

报错：

ERROR: uprobe target file 'libssl' does not exist or is not executable

Android 上不要依赖短名解析：

uprobe:libssl:SSL_read

改成绝对路径：

uprobe:/apex/com.android.conscrypt/lib64/libssl.so:SSL_read

真实路径从目标进程 maps 里确认：

adb shell 'su -c "grep -Ei '\''ssl|cronet|conscrypt'\'' /proc/<pid>/maps"'

6.5 Attaching ... probes 但没有任何输出

这通常不是 bpftrace 卡住，而是 probe 没有被目标应用触发。按下面顺序查：

  1. 目标应用是否真的发起了网络请求。
  2. 脚本挂的 libssl.so 是否存在于 /proc/<pid>/maps 。
  3. 目标应用是不是 32 位进程，32 位要换 /system/lib/... 或 lib/arm 路径。
  4. 目标应用是不是用了自带网络库，例如 app 私有目录下的 libcronet.so 、 libboringssl.so 。
  5. 是否只看到了 HTTP/2 二进制帧，以为没有明文。

一个简单判断方法是：先运行 bpftrace，再重启或打开目标应用。如果启动阶段能看到 Sentry、Crash、统计上报等请求，说明脚本已经工作；后续只需要触发你关心的业务请求。

6.6 FIPS integrity test failed

报错：

FIPS integrity test failed.
Expected:   ...
Calculated: ...
Aborted

常见原因是脚本挂了 libcrypto.so 。BoringSSL/Conscrypt 的完整性校验发现代码页被 uprobe patch 过，于是 abort。

处理方式：

  1. 停掉正在运行的 bpftrace，按 Ctrl-C 。
  2. 从脚本里移除所有 libcrypto.so probe。
  3. 只挂 libssl.so 的 SSL_read / SSL_write / SSL_do_handshake 。

如果普通 killall 、 ps 也因为 FIPS abort 运行不了，可以在当前 bpftrace 终端里直接按 Ctrl-C 。必要时重启设备清理状态。

七、排查命令清单

下面这组命令可以快速定位大多数问题。

检查 root 和版本：

adb shell 'su -c "id; uname -r; getprop ro.product.cpu.abilist64"'

检查 bpftrace：

adb shell 'su -c "cd /data/local/tmp/bpftools && ./bpftrace --version"'
adb shell 'su -c "cd /data/local/tmp/bpftools && ./bpftrace --info | head -80"'

检查 headers：

adb shell 'su -c "ls -l /data/local/tmp/kheaders-$(uname -r)/include/linux/types.h /data/local/tmp/kheaders-$(uname -r)/include/uapi/linux/types.h"'

查看前台应用：

adb shell 'dumpsys window | grep -E "mCurrentFocus|mFocusedApp"'

查看应用 PID：

adb shell 'ps -A | grep com.yuanrenxue.challenge'

查看应用加载的 SSL/Crypto 库：

adb shell 'su -c "grep -Ei '\''ssl|crypto|cronet|conscrypt|webview'\'' /proc/<pid>/maps | head -100"'

检查符号：

adb shell 'readelf -Ws /apex/com.android.conscrypt/lib64/libssl.so | grep -E " SSL_read$| SSL_write$| SSL_do_handshake$"'
adb shell 'readelf -Ws /apex/com.android.tethering/lib64/stable_cronet_libssl.so | grep -E " SSL_read$| SSL_write$| SSL_do_handshake$"'

编译检查 .bt 脚本：

adb shell 'su -c "cd /data/local/tmp/bpftools && BPFTRACE_KERNEL_SOURCE=/data/local/tmp/kheaders-$(uname -r) BPFTRACE_KERNEL_BUILD=/data/local/tmp/kheaders-$(uname -r) ./bpftrace -d /data/local/tmp/sslsnoop.bt >/dev/null"'

运行脚本：

adb shell 'su -c "cd /data/local/tmp/bpftools && BPFTRACE_KERNEL_SOURCE=/data/local/tmp/kheaders-$(uname -r) BPFTRACE_KERNEL_BUILD=/data/local/tmp/kheaders-$(uname -r) ./bpftrace /data/local/tmp/sslsnoop.bt"'

八、完整流程回顾

整个链路可以压缩成下面几步：

准备 bpftools
  -> adb push 到 /data/local/tmp
  -> 用 wrapper ./bpftrace 启动
  -> 解压 /sys/kernel/kheaders.tar.xz
  -> 设置 BPFTRACE_KERNEL_SOURCE / BUILD
  -> 用 -d 检查 .bt 脚本
  -> 从 /proc/<pid>/maps 找目标 libssl.so
  -> 挂 SSL_read / SSL_write
  -> 触发 app 请求
  -> 在 bpftrace 输出里看明文 buffer

最容易踩坑的点有三个：

  1. Android 上没有 /lib/modules/$(uname -r)/build ，要自己配置 kheaders。
  2. 目标应用未必加载 /system/lib64/libssl.so ，必须看 /proc/<pid>/maps 。
  3. 不要随手挂 libcrypto.so ，FIPS 完整性校验可能会让进程 abort。

把这三点处理好以后，bpftrace 在 Android 上抓用户态数据会非常直接：脚本短、部署轻、反馈快，很适合做动态分析和网络链路定位。
