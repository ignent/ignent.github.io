开发者模式检测、剪贴板限制、调用栈处理

1. 总入口： HookEntry

入口文件：

  • HookEntry.java

handleLoadPackage(...) 调用了 4 个 Hook：

HideStack.hook(lpparam);
HideDev.hook(lpparam);
HookDemo.hook(lpparam);
ClipboardHook.hook(lpparam);

作用：

  • 每次有目标进程进入 handleLoadPackage(...) ，就安装这 4 组 Hook

2. 开发者模式检测： HideDev

文件：

  • HideDev.java

2.1 Hook

它一共 Hook 了 4 个方法：

  1. Settings.Global.getInt(ContentResolver, String)
  2. Settings.Global.getInt(ContentResolver, String, int)
  3. Settings.Secure.getInt(ContentResolver, String)
  4. Settings.Secure.getInt(ContentResolver, String, int)

2.2 拦截 key

代码里定义了一个 KEYS 数组：

private static final String[] KEYS = {
        "development_settings_enabled",
        "adb_enabled",
        "clipboard"
};

这表示当前代码会特别处理这 3 个设置项查询。

2.3 关键逻辑

核心逻辑在 beforeHookedMethod(...) ：

String key = (String) param.args[1] != null ? param.args[1].toString() : "";
for (String k : KEYS) {
    if (key.equals(k)) {
        param.setResult(0);
        return;
    }
}

作用可以拆成 3 步：

  1. 取出被查询的设置项名字，也就是第二个参数 param.args[1]
  2. 判断它是不是 development_settings_enabled 、 adb_enabled 或 clipboard
  3. 如果命中，就直接 param.setResult(0) ，不再执行原始方法

2.4 预期效果

按当前代码，调用方如果通过 Settings.Global.getInt(...) 或 Settings.Secure.getInt(...) 去读这些 key，会拿到 0 。

对应效果是：

  • development_settings_enabled 会表现成 “开发者选项关闭”
  • adb_enabled 会表现成 “ADB 关闭”
  • clipboard 这个 key 也会被强制返回 0

3. 剪贴板限制： ClipboardHook

文件：

  • ClipboardHook.java

3.1 Hook

它只 Hook 了一个方法：

  1. ClipboardManager.hasPrimaryClip()

3.2 关键逻辑

核心代码：

param.setResult(false);

作用：

  • 在 beforeHookedMethod(...) 里直接把返回值改成 false
  • 原始 hasPrimaryClip() 不再按真实状态返回

3.3 预期效果

按当前实现，调用方会认为：

  • 当前剪贴板里 “没有主剪贴内容”

但这里一定要说准确：

  • 这段代码不是全面禁止读取剪贴板
  • 它只让 hasPrimaryClip() 永远返回 false

所以当前真实效果更准确的说法是：

  • 对那些先调用 hasPrimaryClip() 再决定要不要读剪贴板的代码，这能让它们误以为剪贴板为空
  • 但这份代码并没有 Hook getPrimaryClip() 、 getPrimaryClipDescription() 等其他剪贴板读取方法

4. 调用堆栈处理： HideStack

文件：

  • HideStack.java

4.1 Hook

Thread.getStackTrace()

4.2 改调用堆栈

这个 Hook 不在 beforeHookedMethod(...) 里改结果，而是在 afterHookedMethod(...) 里处理原始返回值。

关键逻辑：

if (param.getResult() instanceof StackTraceElement[]) {
    StackTraceElement[] stackTraceList = (StackTraceElement[]) param.getResult();
    ArrayList<StackTraceElement> result = new ArrayList<>();
    if (stackTraceList != null && stackTraceList.length > 0) {
        for (StackTraceElement stackTraceElement : stackTraceList) {
            String className = stackTraceElement.getClassName();
            if (filter(className)) {
                result.add(stackTraceElement);
            }
        }
    }
    stackTraceList = new StackTraceElement[result.size()];
    for (int i = 0; i < result.size(); i++) {
        stackTraceList[i] = result.get(i);
    }
    param.setResult(stackTraceList);
}

作用：

  1. 先拿到原始 StackTraceElement[]
  2. 遍历每一帧
  3. 按 filter(...) 规则把不想暴露的类过滤掉
  4. 重新组装一个新的堆栈数组
  5. 用 param.setResult(...) 把返回值替换掉

4.3 过滤规则

filter(...) 的实现是：

return !className.contains("HookBridge") &&
        !className.contains("lsposed") &&
        !className.contains("LSPHooker_") &&
        !className.contains("Hook");

当前会过滤掉类名中包含以下内容的栈帧：

  • HookBridge
  • lsposed
  • LSPHooker_
  • Hook

4.4 预期效果

按当前实现，在已经安装这组 Hook 的进程里，调用 Thread.getStackTrace() 拿到的不是原始调用堆栈，而是 “过滤后” 的版本。

效果可以准确描述为：

  • 一部分和 LSPosed / Hook 桥相关的调用痕迹会从返回结果里被移除

这里也要明确当前实现的边界：

  • 过滤条件里用了 className.contains("Hook")
  • 所以不只是框架桥接类，任何类名里带 Hook 的栈帧都会被过滤掉
