SO 动态注入实战：主线程调用 JNI Native 函数

SO 动态注入实战：主线程调用 JNI Native 函数

概述

本文解决一个非常典型的 Android Native 逆向问题：

Java 层请求接口时需要 sign 参数，但 sign 由 so 中动态注册的 JNI 函数生成。静态分析能看到大概算法，动态运行时还会受 time(0) 、 Looper.myLooper() 、JNI 线程环境影响。如何在不重启 App 的情况下，把 Frida 注入到目标进程，直接调用 so 里的真实 Native 函数，并验证自己的 Python 复现是否正确？

最终运行效果有两个：

  1. 在已运行 App 进程中，通过 Frida 主线程调用 Native 函数：
mainthread.digest.result:
  thread_id = <main-tid>
  input     = "1"
  page      = 1
  out_hex   = CCEFDAFFBD56A00A95C15D6E75EE1BE4E4F989FF
  1. 使用 Python 复现的 sign(page, time) 批量请求接口，拉取 1-100 页数据并求和：
COUNT 1000
TOTAL 5012057

合法性提醒

本文只讨论授权测试、逆向学习和自有环境调试。动态注入、Hook、主动调用 Native 函数都可能触碰目标软件的安全边界。请不要对未授权应用、生产账号或第三方服务做破坏性测试。

环境与版本

下面是本文复现时使用和建议的环境。版本写得稍细，是因为 Frida、Android Runtime、JNI 调用约定这些东西对版本很敏感，差一个小版本就可能出现不同报错。是的，逆向里的 “应该差不多” 经常会在凌晨三点变成 “怎么又崩了”。

项目版本 / 配置说明
Android 设备arm64-v8a 真机，Android 14-16 均可按本文思路复现重点是 ABI 和 Frida Server 匹配
Frida Host17.15.3Host 端和设备端 frida-server 必须尽量同版本
frida-server17.15.3-android-arm64放到设备 /data/local/tmp/ 后以 root 或可调试权限启动
Python3.11+用于批量请求接口和校验签名
uv0.7+ 或系统 Python本文命令用 uv run --no-project python ，没有 uv 可直接用 python3
IDA / Ghidra / JADX版本不限用于确认 JNI_OnLoad 、动态注册函数和 so 内偏移

前置条件：

  • 设备已经连接 ADB，并能执行 adb shell 。
  • 目标 App 已经启动，且你能进入触发目标 so 加载的页面。
  • frida-server 已经启动，并且版本和 Host 端 Frida 一致。
  • 你已经通过 IDA/Ghidra 确认了目标函数在 so 中的运行时虚拟偏移，不是单纯文件偏移。

运行时偏移不是文件偏移

本文踩过一个很实在的坑：IDA 里看到的函数地址是 0x1B058 ，文件偏移附近是 0xF334 。Frida 运行时应使用：

runtime_address = module_base + 0x1B058

如果误用：

runtime_address = module_base + 0xF334

你很可能会落到数据区，结果就是 Hook 不命中，主动调用触发 illegal instruction 。这类坑很安静，但很会浪费时间。

项目结构

为了方便复现，建议把脚本按下面的相对路径组织。路径只是示例，不要照搬任何本地绝对目录。

so-dynamic-injection-demo/
├── frida/
│   ├── call-digest-main-thread.js       # 注入脚本：在主线程主动调用 so 函数
│   └── trace-digest.js                  # 可选：只 Hook 目标函数并打印入参/出参
├── python/
│   ├── app3_sign_pseudo.py              # Python 版 sign 复现，包含轮函数

└── README.md
文件职责
frida/call-digest-main-thread.js注入目标进程，等待主线程经过 epoll_wait ，在主线程里拿 JNIEnv 调用 digest()

提示

sign 不是题目答案。 sign 的作用是让接口接受当前页请求。真正要提交的是 1-100 页所有 value 的总和。

核心代码

1. Frida 主线程主动调用脚本

文件路径： frida/call-digest-main-thread.js

这段脚本做三件事：

  1. 读取当前进程中 libthree.so 的基址。
  2. 计算 digest = base + 0x1B058 。
  3. Hook 主线程会反复经过的 epoll_wait ，等回调发生在主线程时，调用 digest("1", out, 1, env) 。

为什么要绕到主线程？因为目标 Native 函数内部调用了：

android.os.Looper.myLooper()

如果你在 Frida 工作线程里直接调用， Looper.myLooper() 很可能返回 null ，走到另一条分支。这样算出来的 sign 和 App 真实请求不一致。

// frida/call-digest-main-thread.js
// 用途：注入已运行的 Android 进程，在主线程里主动调用 libthree.so 的 digest 函数。
//
// 运行示例：
//   frida -U -n 目标App名称 -l frida/call-digest-main-thread.js --runtime=v8
//
// 需要按实际目标替换：
//   MODULE_NAME   目标 so 名称
//   DIGEST_OFFSET IDA/Ghidra 中的运行时虚拟偏移
//   PAGE          要计算的 page
//   INPUT         Native sign 内部传入 digest 的字符串，一般是 String.valueOf(page)

'use strict';

// 目标 so 名称。这里使用示例名，复现时替换为自己的 so。
const MODULE_NAME = 'libthree.so';

// IDA 中 digest/sub_1B058 的虚拟地址偏移。
// 注意：这里不是文件偏移。Frida 地址 = Module.base + DIGEST_OFFSET。
const DIGEST_OFFSET = 0x1B058;

// 要模拟的请求页码。目标 JNI sign(int page) 会把 page 格式化成字符串。
const PAGE = 1;
const INPUT = String(PAGE);

// 只允许调用一次，避免主线程每次进入 epoll_wait 都重复触发。
let called = false;

// 把 NativePointer 指向的 n 字节转成大写 hex。
function readHex(ptrValue, length) {
  const parts = [];
  for (let i = 0; i < length; i++) {
    const b = ptrValue.add(i).readU8();
    parts.push(('0' + b.toString(16)).slice(-2));
  }
  return parts.join('').toUpperCase();
}

// 打印当前已加载模块，方便排查 so 是否已经加载。
function findTargetModule() {
  try {
    return Process.getModuleByName(MODULE_NAME);
  } catch (e) {
    console.log(`[error] ${MODULE_NAME} not loaded: ${e}`);
    console.log('[hint] 请先进入会加载目标 so 的页面，再注入脚本。');
    return null;
  }
}

function main() {
  const module = findTargetModule();
  if (module === null) return;

  // 目标函数真实地址。
  const digestPtr = module.base.add(DIGEST_OFFSET);

  // digest 原型来自 IDA 分析：
  //   void digest(char *input, unsigned char *out, int page, JNIEnv *env)
  //
  // 如果你的目标函数签名不同，一定要改 NativeFunction 的返回值和参数类型。
  const digest = new NativeFunction(digestPtr, 'void', [
    'pointer', // char *input
    'pointer', // unsigned char *out
    'int',     // int page
    'pointer', // JNIEnv *env
  ]);

  // Android 主线程通常阻塞在 libc.so 的 epoll_wait。
  // 我们 Hook 它，只是为了找到一次“当前回调就在主线程执行”的机会。
  const epollWait = Process.getModuleByName('libc.so').getExportByName('epoll_wait');

  // Linux/Android 中主线程 tid 通常等于 pid。
  // Frida 的 Process.id 就是当前进程 pid。
  const mainTid = Process.id;

  console.log(
    `[prepare] module=${MODULE_NAME} base=${module.base} digest=${digestPtr} ` +
      `epoll_wait=${epollWait} main_tid=${mainTid} input=${INPUT} page=${PAGE}`,
  );

  Interceptor.attach(epollWait, {
    onEnter() {
      // this.threadId 是当前回调所在 Linux tid。
      if (called || this.threadId !== mainTid) return;
      called = true;

      try {
        // 在主线程中获取当前线程绑定的 JNIEnv。
        // 如果这里返回 null，说明当前线程没有附着到 JVM，不能直接调用需要 JNIEnv 的函数。
        const env = Java.vm.tryGetEnv();
        if (env === null) {
          console.log(`[error] tryGetEnv returned null, tid=${this.threadId}`);
          return;
        }

        // 分配 Native 输入和输出缓冲区。
        const inputBuf = Memory.allocUtf8String(INPUT);
        const outBuf = Memory.alloc(20);

        // 主动调用 Native 函数。
        // 第三个参数是 page，不是输出长度。这个坑很小，但能把结果带沟里。
        const start = Date.now();
        digest(inputBuf, outBuf, PAGE, env.handle);

        // Native 返回的是 20 字节，Java 层通常再转大写 hex。
        const outHex = readHex(outBuf, 20);
        console.log(
          `[result] thread_id=${this.threadId} env=${env.handle} input=${INPUT} ` +
            `page=${PAGE} out_hex=${outHex} ms=${Date.now() - start}`,
        );
      } catch (e) {
        console.log(`[error] call digest failed: ${e}`);
        if (e.stack) console.log(e.stack);
      }
    },
  });
}

// Java.perform 可以保证 Java VM 可用，但不要在这里直接调用目标 digest。
// 真正调用放在 epoll_wait 的主线程回调里。
Java.perform(main);

2. 可选：只观察真实调用的 Hook 脚本

文件路径： frida/trace-digest.js

如果你不想主动调用，只想观察 App 自己什么时候调用 digest() ，可以用下面的脚本。它不会改变返回值，只打印入参和出参。

// frida/trace-digest.js
// 用途：Hook digest，观察真实调用。适合确认 App 是否真的走到了目标函数。

'use strict';

const MODULE_NAME = 'libthree.so';
const DIGEST_OFFSET = 0x1B058;

function readHex(ptrValue, length) {
  const parts = [];
  for (let i = 0; i < length; i++) {
    parts.push(('0' + ptrValue.add(i).readU8().toString(16)).slice(-2));
  }
  return parts.join('').toUpperCase();
}

function main() {
  const module = Process.getModuleByName(MODULE_NAME);
  const digestPtr = module.base.add(DIGEST_OFFSET);

  console.log(`[install] ${MODULE_NAME} base=${module.base} digest=${digestPtr}`);

  Interceptor.attach(digestPtr, {
    onEnter(args) {
      // digest(char *input, unsigned char *out, int page, JNIEnv *env)
      this.inputPtr = args[0];
      this.outPtr = args[1];
      this.page = args[2].toInt32();
      this.env = args[3];
      this.start = Date.now();

      let input = '<read failed>';
      try {
        input = this.inputPtr.readCString();
      } catch (_) {}

      console.log(
        `[enter] input=${input} page=${this.page} out=${this.outPtr} env=${this.env}`,
      );
    },
    onLeave() {
      let outHex = '<read failed>';
      try {
        outHex = readHex(this.outPtr, 20);
      } catch (_) {}

      console.log(`[leave] page=${this.page} out_hex=${outHex} ms=${Date.now() - this.start}`);
    },
  });
}

Java.perform(main);

注意

如果页面已经缓存了数据，真实请求可能不会再次调用 digest() 。这时 Hook 是装上了，但没有日志，不代表地址一定错。可以清理页面状态、返回列表重新进入、下拉刷新，或者改用上一节的主线程主动调用方式。

3. Python 版 sign 调用接口

文件路径： python/fetch_app3_sum.py

这段脚本假设你已经有一个 app3_sign_pseudo.py ，其中暴露两个函数：

def sign_pseudo(page: int, now: int | None = None, looper_present: bool = True) -> bytes:
    ...

def upper_hex(data: bytes) -> str:
    ...

sign_pseudo() 的内部就是从 sub_1B058 翻译出来的轮函数。由于完整轮函数较长，本文不把 500 多行重复贴进正文。复现时请把它放在 python/app3_sign_pseudo.py ，并保证下面两个测试能通过：

python3 python/app3_sign_pseudo.py \
  --page 1 \
  --time 1782489822 \
  --target CCEFDAFFBD56A00A95C15D6E75EE1BE4E4F989FF

预期：

target match      : True

批量请求脚本：

# python/fetch_app3_sum.py
# 用途：为 1-100 页实时计算 sign，请求接口，累加所有 value。
#
# 需要自行替换：
#   API_URL       目标接口地址
#   HEADERS       请求头，尤其是 User-Agent / Content-Type
#   app3_sign_pseudo.py 中的 sign_pseudo 实现

from __future__ import annotations

import gzip
import importlib.util
import json
import sys
import time
import urllib.parse
import urllib.request
from pathlib import Path


# 示例接口。复现时替换为自己的目标接口。
API_URL = "https://www.python-spider.com/api/app3"

# 尽量贴近 App 请求头。服务端如果校验 UA、Content-Type 或 gzip，要保持一致。
HEADERS = {
    "Host": "www.python-spider.com",
    "Accept-Language": "zh-CN,zh;q=0.8",
    "User-Agent": (
        "Mozilla/5.0 (Linux; U; Android 16; zh-cn; <DEVICE_MODEL> "
        "Build/<BUILD_ID>) AppleWebKit/533.1 "
        "(KHTML, like Gecko) Version/5.0 Mobile Safari/533.1"
    ),
    "Content-Type": "application/x-www-form-urlencoded",
    "Accept-Encoding": "gzip",
    "Cache-Control": "no-cache",
    "Connection": "close",
}


def load_sign_module():
    """加载同目录下的 app3_sign_pseudo.py。

    这里不用普通 import，是为了让读者可以直接把脚本放在任意演示目录中运行。
    """

    sign_file = Path(__file__).with_name("app3_sign_pseudo.py")
    spec = importlib.util.spec_from_file_location("app3_sign_pseudo", sign_file)
    if spec is None or spec.loader is None:
        raise RuntimeError(f"cannot load {sign_file}")

    module = importlib.util.module_from_spec(spec)

    # dataclass 在动态导入时需要能从 sys.modules 找到当前模块。
    sys.modules[spec.name] = module
    spec.loader.exec_module(module)
    return module


SIGN = load_sign_module()


def request_page_once(page: int, now: int) -> tuple[str, dict]:
    """用指定时间戳计算 sign，并请求单页数据。"""

    # Native 中 sign 是 20 字节，Java 层再转大写 hex。
    sign = SIGN.upper_hex(SIGN.sign_pseudo(page, now, True))

    body = urllib.parse.urlencode(
        {
            "page": page,
            "sign": sign,
        }
    ).encode()

    req = urllib.request.Request(API_URL, data=body, headers=HEADERS, method="POST")
    with urllib.request.urlopen(req, timeout=8) as resp:
        raw = resp.read()

        # 服务端如果返回 gzip，需要解压后再 JSON 解析。
        if resp.headers.get("Content-Encoding", "") == "gzip":
            raw = gzip.decompress(raw)

        return sign, json.loads(raw.decode("utf-8"))


def request_page(page: int) -> tuple[str, dict]:
    """请求单页数据，自动处理 time(0) 秒级偏差和临时网络错误。"""

    last_error: object = None

    # sign 使用 time(0)，客户端计算和服务端校验可能有 1-2 秒偏差。
    # 所以每次失败时尝试当前秒附近几个值。
    for attempt in range(1, 8):
        base = int(time.time())
        for delta in (0, -1, 1, -2, 2, -3, 3):
            try:
                sign, obj = request_page_once(page, base + delta)
                if str(obj.get("status")) == "1" and obj.get("data"):
                    return sign, obj
                last_error = obj
            except Exception as exc:
                last_error = repr(exc)

        # 简单退避，避免网络抖动或服务端限速时连打。
        time.sleep(1.0 + attempt * 0.4)

    raise RuntimeError(f"page {page} failed: {last_error}")


def main() -> None:
    """请求 1-100 页并求和。"""

    total = 0
    count = 0

    for page in range(1, 101):
        sign, obj = request_page(page)

        # 接口返回形态：
        #   {"status": "1", "state": "success", "data": [{"value": "927\r"}, ...]}
        values = [int(str(item["value"]).strip()) for item in obj["data"]]
        page_sum = sum(values)

        total += page_sum
        count += len(values)

        print(f"{page:03d} sum={page_sum:6d} count={len(values)} sign={sign}")

    print("COUNT", count)
    print("TOTAL", total)


if __name__ == "__main__":
    main()

流程拆解

整体链路可以拆成两条线：分析线和复现线。

第一步：JADX 找 Java 入口

Java 层通常能看到类似结构：

public class ChallengeThreeNativeLib {
    static {
        System.loadLibrary("three");
    }

    public native byte[] sign(int page);
}

调用处会把 byte[] 转成大写 hex：

private String toUpperHex(byte[] data) {
    StringBuilder sb = new StringBuilder();
    for (byte b : data) {
        sb.append(String.format("%02X", b & 0xff));
    }
    return sb.toString();
}

这说明 Native 返回的不是字符串，而是 20 字节原始结果。

第二步：IDA 找动态注册

JNI_OnLoad 中会出现 RegisterNatives ：

static JNINativeMethod methods[] = {
    {
        "sign",
        "(I)[B",
        (void *)_Z4signP7_JNIEnvP8_jobjecti
    }
};

env->RegisterNatives(clazz, methods, 1);

这意味着 Java 层调用 sign(int) 时，真正进入的是动态注册的函数，不一定是导出表里那个 Java_xxx_sign 。

注意

动态注册会覆盖你从导出符号直觉找到的静态 JNI 函数。分析时以 JNI_OnLoad -> RegisterNatives 为准。

第三步：确认 Native 链路

真实调用链可以整理成：

Java sign(int page)
  -> dynamic sign(JNIEnv *env, jobject thiz, jint page)
     -> sprintf("%d", page)
     -> malloc(20)
     -> digest(page_str, out, page, env)
     -> NewByteArray(20)
     -> SetByteArrayRegion(...)
  -> Java byte[] 转大写 hex

这里最容易传错的是 digest 第三个参数。它是 page ，不是输出长度。传成 20 也会得到 20 字节输出，但那是另一个输入条件下的结果，和 App 请求对不上。

第四步：主线程调用

digest() 内部调用了 Looper.myLooper() ，所以主动调用时线程很关键：

调用位置Looper.myLooper()结果
Frida 普通工作线程大概率 null走 false 分支，sign 不同
Android 主线程非 null走 App 真实请求分支

本文用 epoll_wait 找主线程执行机会，是因为 Android 主线程的消息循环会频繁进入它。这个方式不是稳定公开接口，但在调试中很实用。

原理分析

1. so 动态注入到底做了什么

这里的 “动态注入” 不是把 APK 重新打包，也不是修改磁盘上的 so，而是在目标进程运行时加载 Frida Agent。Frida Agent 能在进程内执行 JavaScript，并通过 Frida API：

  • 枚举模块： Process.getModuleByName()
  • 计算函数地址： module.base.add(offset)
  • 拦截函数： Interceptor.attach()
  • 主动调用函数： new NativeFunction(ptr, retType, argTypes)
  • 访问 Java VM： Java.vm.tryGetEnv()

所以它适合做运行时确认：

静态分析：我猜 sub_1B058 是 digest
动态注入：我直接调用 sub_1B058，看输出是否和 App 一致

2. 为什么必须区分虚拟地址和文件偏移

ELF 文件在磁盘上有文件偏移，加载到内存后有虚拟地址。IDA 默认展示的函数地址通常是基于 ELF 虚拟地址空间的地址。Frida 运行时模块基址也是内存虚拟地址。

正确计算：

runtime_address = module_base + ida_function_va

错误计算：

runtime_address = module_base + file_offset

如果你不确定当前地址是不是代码，可以用 Frida 读几条指令字节：

const p = Process.getModuleByName('libthree.so').base.add(0x1B058);
console.log(Instruction.parse(p).toString());

正常 AArch64 函数开头经常能看到类似：

sub sp, sp, #...
stp x29, x30, [sp, #...]

如果读到大段 00 00 00 00 或明显数据表，就该重新检查偏移来源。

3. 为什么 sign 每秒变化

目标 Native 中使用了 time(0) ，因此同一页的 sign 也会随时间变化：

sign = digest(page_str, page, time(0), looper_state)

这就是为什么下面这种做法会失败：

拿一次 page=1 的 sign
复制它请求 page=2 或过几秒再请求 page=1

正确做法是每次请求前实时计算：

now = int(time.time())
sign = sign_pseudo(page, now)

如果服务端允许 1-2 秒误差，可以在失败时尝试 now-1 、 now+1 。

4. 为什么最终答案不是 sign

sign 只是请求通行证。题目要求的是：

计算 1-100 页所有数字之和

接口每页返回 10 个数字，最终要提交的是：

sum(all page values)

在一次复现中，1-100 页共返回 1000 个数字，总和为：

5012057

常见错误与排查

1. unable to connect to remote frida-server: closed

原因通常是 Host 端 Frida 和设备端 frida-server 版本不一致。

排查：

frida --version
adb shell /data/local/tmp/frida-server --version

处理：

adb shell su -c "pkill frida-server"
adb push frida-server-对应版本-android-arm64 /data/local/tmp/frida-server
adb shell chmod 755 /data/local/tmp/frida-server
adb shell su -c "/data/local/tmp/frida-server >/data/local/tmp/frida.log 2>&1 &"

2. libthree.so not loaded

原因：目标页面还没进入，so 还没有被 System.loadLibrary() 加载。

处理：

  • 先用 App 操作进入目标页面。
  • 再执行 Frida 脚本。
  • 或 Hook android_dlopen_ext 等待目标 so 加载后再安装 Hook。

3. Hook 装上了但没有日志

原因可能有三种：

  1. 页面使用缓存，没有重新请求。
  2. 地址算错，Hook 到了非目标函数。
  3. 真实路径走了另一个动态注册函数。

排查：

  • 回到列表重新进入页面。
  • 读目标地址附近指令，确认是代码。
  • Hook RegisterNatives 打印动态注册表。
  • 对比 IDA 地址和 Frida module.base 。

4. 主动调用报 illegal instruction

常见原因：

  • 把文件偏移当成运行时虚拟偏移。
  • 调到了函数中间，而不是函数入口。
  • ARM64 BTI/PAC 等机制导致间接调用落点非法。

处理：

  • 用 IDA/Ghidra 确认函数入口。
  • 用 Instruction.parse() 验证入口指令。
  • 不要跨架构套用 offset。

5. tryGetEnv returned null

原因：当前线程没有附着到 JVM。

处理：

  • 不要在普通 Frida 工作线程里调用需要 JNIEnv* 的函数。
  • 在主线程回调中调用。
  • 或者自己使用 JavaVM->AttachCurrentThread ，但这又会改变 Looper.myLooper() 的状态，不适合本文目标。

6. Python 请求返回失败

可能原因：

  • sign 过期， time(0) 和服务端校验秒不同。
  • 请求头和 App 不一致。
  • 服务端限速或网络抖动。
  • page 参数和 sign 计算参数不一致。

排查：

  • 对 now-1 、 now 、 now+1 分别计算 sign 重试。
  • 打印响应体，不要只看 HTTP 状态码。
  • 先用 page=1 验证能返回数据，再批量跑。

总结

本文主线是：

  1. Java 层找到 native sign(int) 。
  2. JNI_OnLoad 中确认动态注册覆盖关系。
  3. IDA 定位真实 Native 链路： sign -> digest 。
  4. Frida 注入已运行进程，计算 module.base + 0x1B058 。
  5. 在主线程中主动调用 digest("1", out, 1, env) ，避免 Looper 分支错误。
  6. 用 Native 输出校验 Python 复现。
  7. 每页实时计算 sign，请求 1-100 页数据并求和。

这套方法适合处理：

  • JNI 动态注册导致 Java 方法和 Native 函数难对应。
  • sign 内含时间、线程状态、JNI 环境，静态复现容易偏一位。
  • 需要在不重启 App 的情况下动态确认 Native 算法。

可扩展方向：

  • Hook RegisterNatives 自动输出所有动态注册函数和模块偏移。
  • Hook NewByteArray / SetByteArrayRegion 自动抓 Native 返回的 byte []。
  • 用 Frida RPC 封装 sign(page) ，让 Python 批量请求时直接调用 App 内真实算法。
  • 将确认后的 Python 轮函数写成单元测试，固定样本持续回归。
