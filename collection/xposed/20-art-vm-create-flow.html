ART 虚拟机创建流程：从 app_process 到 JavaVM/JNIEnv

概述

做 Xposed、Native Hook、 RegisterNatives 监控或者 ArtMethod 入口替换时，经常会遇到几个看起来分散的问题：

  • JavaVM* 是什么时候创建的？
  • 为什么 JNIEnv* 不能跨线程保存？
  • Runtime::Current() 背后到底初始化了哪些东西？
  • Boot image、OAT、VDEX 和 Dex 加载是什么关系？
  • Zygote fork 前后，ART 的堆为什么能被多个应用共享一部分页面？

这些问题都指向同一条主线：ART 虚拟机的创建流程。

本文以 Android SDK 37（Android 17 / API 37） 的运行环境为主线，先用一个可运行的 JNI 探针验证 JavaVM 和 JNIEnv 的关系，再沿着 ART 的源码调用链拆解：

app_process
  -> AndroidRuntime::start()
  -> AndroidRuntime::startVm()
  -> JNI_CreateJavaVM()
  -> Runtime::Create()
  -> Runtime::Init()
  -> Runtime::Start()
  -> ZygoteInit.main() / RuntimeInit.main()

需要提前说明： Runtime 、 Thread 、 JavaVMExt 、 JNIEnvExt 、 OatFileManager 、 ArtMethod 都是 ART 内部实现细节，不是 Android SDK 的稳定公开 API。Android 17/API 37 仍然可能随预览版本、厂商分支和 AOSP tag 调整内部实现。本文可以帮助理解和调试，但不要把内部结构偏移、私有函数符号或源码路径直接跨 Android 版本套用。

  • Boot image/OAT 文件路径可能受 APEX、分区布局、系统预编译策略影响。
  • 部分 libart 符号会被隐藏或裁剪，不能依赖 dlsym 一定能找到内部函数。
  • ArtMethod 、 Thread 、 JNIEnvExt 等内部结构布局可能变化。

最终目标

读完并运行示例后，应该能验证下面几个现象：

JNI_OnLoad 中可以拿到进程级 JavaVM*
Java 调用 native 方法时，当前 Java 线程已经有 JNIEnv*
原生 pthread 默认没有 JNIEnv*
原生 pthread 调用 AttachCurrentThread 后才会得到 JNIEnv*
DetachCurrentThread 后，同一个原生线程再次 GetEnv 会返回 JNI_EDETACHED

同时能从源码层理解：

  • JNI_CreateJavaVM() 并不是单纯创建一个 JNI 表，而是 ART Runtime 初始化入口。
  • Runtime::Init() 会创建堆、OAT 管理器、ClassLinker、JavaVMExt 等关键组件。
  • Runtime::Start() 会让运行时进入可执行 Java/JNI 调用的状态。
  • OAT 加载不是简单打开文件，而要经过校验、编译状态判断、class loader context 检查和 fallback。

package com.example.artvmprobe

import android.app.Activity
import android.os.Bundle
import android.view.Gravity
import android.widget.TextView

class MainActivity : Activity() {

    companion object {
        init {
            // 加载 libart_vm_probe.so，加载成功后 ART 会回调 native 层 JNI_OnLoad。
            System.loadLibrary("art_vm_probe")
        }
    }

    // 在当前 Java 调用线程里打印 JavaVM/JNIEnv 状态。
    private external fun dumpFromMainThread(): String

    // 创建一个 pthread，验证原生线程 attach 前后 GetEnv 的差异。
    private external fun startNativeThreadProbe()

    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)

        // 用最小 UI 展示主线程探针结果，不引入额外布局文件。
        val output = TextView(this).apply {
            textSize = 16f
            gravity = Gravity.START
            setPadding(48, 72, 48, 48)
            text = dumpFromMainThread() + "\n\nTap screen to create a native thread."
        }

        output.setOnClickListener {
            // 点击后启动 native 线程，详细日志看 logcat。
            startNativeThreadProbe()
            output.text =
                dumpFromMainThread() + "\n\nNative thread probe started. Check logcat tag ArtVmProbe."
        }

        setContentView(output)
    }
}

art_vm_probe.cpp

// art_vm_probe.cpp：验证 JavaVM 是进程级对象，JNIEnv 是线程级对象。
#include <android/log.h>
#include <jni.h>
#include <pthread.h>
#include <sstream>
#include <string>
#include <sys/syscall.h>
#include <unistd.h>

// JavaVM 可以跨线程保存；JNIEnv 不可以跨线程保存。
static JavaVM* g_vm = nullptr;
static constexpr const char* TAG = "ArtVmProbe";

// 简化 Android 日志输出。
#define LOGD(...) __android_log_print(ANDROID_LOG_DEBUG, TAG, __VA_ARGS__)

static long current_tid() {
    // gettid 比 pthread_self 更方便和 logcat / maps 对照。
    return static_cast<long>(syscall(__NR_gettid));
}

static std::string describe_current_thread(const char* where) {
    std::ostringstream os;

    if (g_vm == nullptr) {
        // 理论上 System.loadLibrary 成功后 JNI_OnLoad 会先保存 g_vm。
        os << where << "\nJavaVM is null";
        return os.str();
    }

    JNIEnv* env = nullptr;
    // GetEnv 只查询当前线程是否已经附加到 VM，不会自动 attach。
    jint get_env_result = g_vm->GetEnv(
            reinterpret_cast<void**>(&env),
            JNI_VERSION_1_6
    );

    os << where
       << "\npid=" << getpid()
       << ", tid=" << current_tid()
       << "\nJavaVM*=" << g_vm
       << "\nGetEnv result=" << get_env_result
       << "\nJNIEnv*=" << env;

    std::string text = os.str();
    LOGD("%s", text.c_str());
    return text;
}

extern "C"
JNIEXPORT jint JNICALL
JNI_OnLoad(JavaVM* vm, void*) {
    // native 库加载时由 ART 回调。这里保存进程级 JavaVM。
    g_vm = vm;

    JNIEnv* env = nullptr;
    // JNI_OnLoad 运行在线程已附加到 VM 的上下文里，通常能拿到 JNIEnv。
    jint get_env_result = vm->GetEnv(
            reinterpret_cast<void**>(&env),
            JNI_VERSION_1_6
    );

    LOGD("JNI_OnLoad: JavaVM*=%p, GetEnv=%d, JNIEnv*=%p",
         vm,
         get_env_result,
         env);

    return JNI_VERSION_1_6;
}

extern "C"
JNIEXPORT jstring JNICALL
Java_com_example_artvmprobe_MainActivity_dumpFromMainThread(JNIEnv* env, jclass) {
    // 这个 env 来自 Java 调 native 的当前线程，只能在当前线程使用。
    std::string text = describe_current_thread("Java caller thread");
    return env->NewStringUTF(text.c_str());
}

static void* native_thread_main(void*) {
    if (g_vm == nullptr) {
        LOGD("native thread: JavaVM is null");
        return nullptr;
    }

    JNIEnv* env = nullptr;
    // pthread 是 native 自己创建的线程，默认没有附加到 ART。
    jint before_attach = g_vm->GetEnv(
            reinterpret_cast<void**>(&env),
            JNI_VERSION_1_6
    );

    LOGD("native thread before attach: tid=%ld, GetEnv=%d, JNIEnv*=%p",
         current_tid(),
         before_attach,
         env);

    JavaVMAttachArgs args{};
    args.version = JNI_VERSION_1_6;
    // 线程名会出现在部分调试输出中，便于定位。
    args.name = const_cast<char*>("art-vm-probe");
    args.group = nullptr;

    // attach 后，ART 会为当前 native 线程准备 Thread / JNIEnvExt。
    jint attach_result = g_vm->AttachCurrentThread(&env, &args);
    LOGD("native thread after attach: AttachCurrentThread=%d, JNIEnv*=%p",
         attach_result,
         env);

    if (attach_result == JNI_OK && env != nullptr) {
        // attach 成功后才能安全调用 JNI 函数。
        jclass string_class = env->FindClass("java/lang/String");
        LOGD("native thread JNI call: FindClass(java/lang/String)=%p", string_class);

        if (string_class != nullptr) {
            // 手动释放局部引用，示范 JNI 引用表的基本管理习惯。
            env->DeleteLocalRef(string_class);
        }

        // native 自建线程退出前必须 detach，释放 ART 线程相关状态。
        jint detach_result = g_vm->DetachCurrentThread();
        JNIEnv* after_detach_env = nullptr;
        // detach 后再次 GetEnv 应回到 JNI_EDETACHED。
        jint after_detach = g_vm->GetEnv(
                reinterpret_cast<void**>(&after_detach_env),
                JNI_VERSION_1_6
        );

        LOGD("native thread after detach: DetachCurrentThread=%d, GetEnv=%d, JNIEnv*=%p",
             detach_result,
             after_detach,
             after_detach_env);
    }

    return nullptr;
}

extern "C"
JNIEXPORT void JNICALL
Java_com_example_artvmprobe_MainActivity_startNativeThreadProbe(JNIEnv*, jclass) {
    pthread_t thread;
    // 创建一个独立 native 线程，避免混淆 Java 调用线程和 native 自建线程。
    int create_result = pthread_create(&thread, nullptr, native_thread_main, nullptr);
    if (create_result != 0) {
        LOGD("pthread_create failed: %d", create_result);
        return;
    }

    // 示例不需要 join，线程结束后由系统回收 pthread 资源。
    pthread_detach(thread);
}

这段代码有两个关键点：

  1. 只把 JavaVM* 存到全局变量，不保存 JNIEnv* 。
  2. 新建的 pthread 先 GetEnv() ，再 AttachCurrentThread() ，最后 DetachCurrentThread() 。

这正好对应 ART 内部的设计： JavaVM 是进程级对象， JNIEnv 是线程级对象。

核心流程拆解

1. 从 app_process 进入 AndroidRuntime

Android 应用进程不是从普通 main() 直接进入 Activity 的。系统先启动 app_process ，它创建一个 AppRuntime 对象。 AppRuntime 继承自 AndroidRuntime 。

以 Android 17/API 37 的典型 Zygote 模式为例，大致流程仍然可以抓住这条主线：

app_process main()
  -> AppRuntime runtime(...)
  -> runtime.start("com.android.internal.os.ZygoteInit", args, true)

非 Zygote 的命令行 Java 进程则可能进入：

runtime.start("com.android.internal.os.RuntimeInit", args, false)

对普通 App 来说，最常见路径是：

init 启动 zygote
  -> zygote 创建 ART Runtime
  -> zygote 预加载类和资源
  -> zygote fork 出 app 进程
  -> app 进程继承已经初始化过的 ART 状态

这就是 Xposed、LSPosed 这类框架喜欢在 Zygote 或应用进程早期介入的原因：越早进入，越能影响后续类加载、方法解析和 native 注册。

2. AndroidRuntime::start () 做了什么

AndroidRuntime::start() 是 Native 世界进入 Java 世界的桥。

下面是按 ART/AndroidRuntime 调用关系整理的等价伪代码，不是逐字摘录。API 37 对应源码可能有局部重构，阅读时以函数名和调用链为准：

// 等价伪代码：展示 AndroidRuntime::start 的主干职责。
void AndroidRuntime_start(const char* class_name, Args args, bool zygote) {
    // 初始化 JNI Invocation，准备调用 libart 的 JNI_CreateJavaVM。
    init_jni_invocation();

    JavaVM* vm = nullptr;
    JNIEnv* env = nullptr;

    // 创建 ART Runtime，并返回进程级 JavaVM 和当前线程 JNIEnv。
    startVm(&vm, &env, zygote);

    // 给子类/平台留出的 VM 创建完成回调。
    onVmCreated(env);

    // 注册 Android Framework 中的大量 native 方法。
    startReg(env);

    // 找到 ZygoteInit 或 RuntimeInit 的 Java main 方法。
    jclass start_class = find_class(class_name);
    jmethodID main = get_static_main_method(start_class);

    // 从 native 世界进入 Java 世界。
    env->CallStaticVoidMethod(start_class, main, args);
}

关键动作有四个：

阶段作用
JniInvocation.Init()找到并准备 libart 的 JNI Invocation 接口
startVm()组装 VM 参数，调用 JNI_CreateJavaVM()
startReg()注册 Android Framework 的 native 方法
调用 Java main进入 ZygoteInit.main() 或 RuntimeInit.main()

注意： startReg() 发生在 VM 创建之后。也就是说， RegisterNatives 这类注册行为不是虚拟机创建之前的事情，而是 VM 已经可用后才开始批量注册。

3. startVm () 负责收集启动参数

AndroidRuntime::startVm() 会把系统属性、命令行参数和运行时选项整理成 JavaVMInitArgs 。

典型参数包括：

-Xzygote
-Xms / -Xmx
-Xcheck:jni
-Xjnitrace
-Xgc
-Xcompiler-option
-Djava.class.path
-Djava.library.path

整理完成后，真正创建 VM 的调用是：

// 真实代码由 AndroidRuntime::startVm 组装 JavaVMInitArgs 后调用。
JNI_CreateJavaVM(&java_vm, &env, &init_args);

从 JNI 规范看， JNI_CreateJavaVM() 是 Invocation API 的创建入口。从 ART 实现看，它会继续创建整个 Runtime 。

4. JNI_CreateJavaVM () 进入 ART Runtime

在较新的 AOSP 分支中， JNI_CreateJavaVM() 通常可以从 art/runtime/jni/java_vm_ext.cc 一类路径追到；旧版本也可能位于 art/runtime/java_vm_ext.cc 。API 37 读源码时建议直接搜索函数名。

等价伪代码如下：

// 等价伪代码：展示 JNI_CreateJavaVM 如何把外部 JNI 入口转成 ART Runtime 创建。
jint JNI_CreateJavaVM(JavaVM** out_vm, JNIEnv** out_env, void* raw_args) {
    // 把 JavaVMInitArgs 转换成 ART RuntimeOptions。
    RuntimeOptions options = parse_java_vm_init_args(raw_args);

    // 创建 Runtime 单例，并在内部执行 Runtime::Init。
    if (!Runtime::Create(options)) {
        return JNI_ERR;
    }

    // 初始化 native loader，后续 System.loadLibrary/JNI_OnLoad 会依赖它。
    initialize_native_loader();

    Runtime* runtime = Runtime::Current();
    // 启动 Runtime，让线程、类、JNI 桥接等进入可运行状态。
    if (!runtime->Start()) {
        cleanup_runtime();
        return JNI_ERR;
    }

    // 返回当前线程的 JNIEnv 和进程级 JavaVM。
    *out_env = Thread::Current()->GetJniEnv();
    *out_vm = runtime->GetJavaVM();
    return JNI_OK;
}

这一步说明了一个很重要的事实：

JNI_CreateJavaVM()
  不只是创建 JavaVMExt
  还会创建 Runtime
  初始化 Heap / ClassLinker / OatFileManager
  启动当前线程
  最后返回当前线程的 JNIEnv

所以在 Android 应用进程里，业务 native 库不应该也不能再调用一次 JNI_CreateJavaVM() 。一个进程里通常只有一个 ART Runtime 和一个 JavaVM。

5. Runtime::Create () 创建单例

Runtime::Create() 的职责很克制：检查是否已有实例、解析 options、创建 Runtime 对象，然后调用 Init() 。

等价流程：

Runtime::Create(options)
  -> 如果 Runtime::instance_ 已存在，失败
  -> new Runtime()
  -> Runtime::Init(options)
  -> 设置 Runtime::instance_

这也是为什么普通 Android App 内不能自己再创建第二个 VM：ART Runtime 本身按进程级单例设计。

6. Runtime::Init () 初始化核心子系统

Runtime::Init() 是最密集的一步。它会把 ART 从 “有一个 C++ Runtime 对象” 推进到 “运行时核心组件基本可用”。

按 ART Runtime 的主线，可以简化成：

Runtime::Init()
  -> 初始化原子操作、锁、监视器等基础设施
  -> 创建 OatFileManager
  -> 解析 GC、堆大小、compiler filter、image 等运行时参数
  -> 创建 gc::Heap
  -> 创建 InternTable、MonitorList、ThreadList 等全局结构
  -> 创建 JavaVMExt
  -> 注册 JNIEnvExt 的 GetEnv handler
  -> Thread::Startup()
  -> 把当前 native 线程附加为 ART Thread
  -> 创建 ClassLinker
  -> 从 boot image 初始化类链接器，或走无 image 初始化
  -> 初始化 verifier、native bridge、agents 等组件

这个阶段最值得关注的对象如下：

对象作用
gc::Heap管理 Java 对象堆、GC、各类 space
OatFileManager管理已经打开的 OAT 文件，协助 Dex/OAT 加载
JavaVMExtART 对 JNI JavaVM 的内部实现
JNIEnvExtART 对 JNI JNIEnv 的内部实现，线程级
ThreadList管理所有附加到 Runtime 的线程
ClassLinker类加载、解析、链接、方法和字段解析的核心
InternTable字符串驻留表
MonitorListJava monitor 和锁相关管理

这里的 JavaVMExt 和 JNIEnvExt 对 Xposed/Native Hook 很关键：很多 JNI 调用最终都是通过函数表分发到 ART 实现，CheckJNI 也会通过替换函数表增加检查。

7. Runtime::Start () 让运行时进入工作状态

Runtime::Start() 会完成一些必须在 Init() 之后、执行 Java 之前做的事情。

简化流程：

Runtime::Start()
  -> 标记 Runtime started
  -> 确保 java.lang.Class、java.lang.reflect.Field 等基础类初始化
  -> 初始化 native methods 相关桥接
  -> 启动 SignalCatcher、JDWP、daemon 等运行时线程或组件
  -> 创建 GC 线程池
  -> 加载 libjavacore.so、libopenjdk.so 等核心库
  -> 进入可执行 Java/JNI 调用的状态

Runtime::Start() 成功后， JNI_CreateJavaVM() 才会把当前线程的 JNIEnv* 和进程级 JavaVM* 返回给 AndroidRuntime::startVm() 。

8. 回到 Java main

VM 创建完成后， AndroidRuntime::start() 会调用：

com.android.internal.os.ZygoteInit.main()

Zygote 会继续做预加载、启动 system_server、监听 socket，然后 fork 应用进程。应用进程 fork 出来后会进入 RuntimeInit 、 ActivityThread 等 Java 层流程。

可以把完整链路理解成：

运行时函数的创建和初始化

这里的 “运行时函数” 可以分成三类理解。

1. JavaVM 的 Invocation 函数表

JavaVM* 在 JNI 里不是一个普通业务对象，而是带函数表的接口。ART 内部用 JavaVMExt 实现它。

它的核心职责包括：

JNI Invocation 函数ART 内部意义
DestroyJavaVM销毁 Runtime，Android App 中一般不会主动使用
AttachCurrentThread把当前 native 线程注册为 ART Thread，并创建 / 返回 JNIEnvExt
DetachCurrentThread从 Runtime 解绑当前线程
GetEnv获取当前线程对应的 JNIEnv*
AttachCurrentThreadAsDaemon以 daemon 方式附加线程

示例里 g_vm->GetEnv() 、 g_vm->AttachCurrentThread() 、 g_vm->DetachCurrentThread() 走的就是这张表。

2. JNIEnv 的 Native 函数表

JNIEnv* 也是函数表接口。ART 内部用 JNIEnvExt 表示当前线程的 JNI 环境。

JNIEnvExt 里和日常开发最相关的是：

字段 / 概念作用
当前 Thread*表示这个 JNIEnv 绑定到哪个 ART 线程
JavaVMExt*反向找到进程级 VM
local reference table管理局部引用，例如 jobject 、 jclass
monitor table记录 JNI monitor enter/exit
JNI 函数表FindClass 、 CallObjectMethod 、 NewStringUTF 等函数入口
CheckJNI 状态开启后换成带检查的函数表

这解释了为什么不能跨线程保存 JNIEnv* ：

JNIEnv* 指向的是当前线程的 JNIEnvExt
JNIEnvExt 内部又持有当前 Thread、局部引用表、monitor 状态
把它拿到另一个线程使用，相当于用错线程的运行时上下文

正确做法是：

// 全局只保存 JavaVM，不保存 JNIEnv。
static JavaVM* g_vm = nullptr;

// JNI_OnLoad 中保存 JavaVM*
JNIEXPORT jint JNICALL JNI_OnLoad(JavaVM* vm, void*) {
    g_vm = vm;
    return JNI_VERSION_1_6;
}

// 每个 native 线程自己 attach 并获取 JNIEnv*
void run_on_native_thread() {
    JNIEnv* env = nullptr;
    // 只有当前线程未附加时才需要 AttachCurrentThread。
    if (g_vm->GetEnv(reinterpret_cast<void**>(&env), JNI_VERSION_1_6) == JNI_EDETACHED) {
        g_vm->AttachCurrentThread(&env, nullptr);

        // 只在当前线程使用 env。
        g_vm->DetachCurrentThread();
    }
}

3. Android Framework native 方法注册

Runtime 启动后， AndroidRuntime::startReg(env) 会注册 Android Framework 的 native 方法。

这类注册通常通过 RegisterNatives 完成，例如：

Java 层类
  -> native 方法声明
  -> C/C++ JNINativeMethod 表
  -> RegisterNatives 绑定
  -> Java 调用时进入 native 函数指针

所以如果你 Hook RegisterNatives ，看到大量系统类注册是正常现象。它发生在 VM 创建后、进入 Java 主流程前后，是 Android 启动过程的一部分。

内存管理

ART 的内存管理不是只靠一个 malloc 池。 Runtime::Init() 创建 gc::Heap 时，会按启动参数、镜像文件、GC 策略和是否 Zygote 创建多个 space。

1. Heap 创建入口

简化流程：

Runtime::Init()
  -> 解析 -Xms、-Xmx、-Xgc、image、heap growth limit 等参数
  -> new gc::Heap(...)

gc::Heap 构造时会做几件关键事情：

gc::Heap()
  -> 加载 boot image space
  -> 创建 non-moving space
  -> 创建 main allocation space 或 region space
  -> 创建 large object space
  -> 创建 card table、mark bitmap、live bitmap
  -> 创建不同 GC collector

具体创建哪类 space，取决于 collector 类型和运行模式。Android 17/API 37 中仍可按下面的概念理解，但具体类名、默认 collector 和初始化细节要以对应源码为准：

Space作用
Boot image space映射系统预编译的 boot image，包含核心类对象
Zygote spaceZygote fork 前整理出来的共享对象区域
Non-moving space存放不希望移动的对象，便于 JNI、类对象等场景
Main malloc space常规对象分配空间，可能基于 rosalloc/dlmalloc
Region space常见于 concurrent copying collector
Large object space大对象单独分配，避免频繁移动或复制

不要把某一种 space 布局当成所有 Android 版本的固定事实。ART 会根据设备架构、GC 策略、是否 low memory、是否 debuggable、是否 Zygote 等条件变化。

2. Boot image 为什么重要

Boot image 是 ART 启动性能的关键。它把核心类、字符串、方法元数据以及相关 OAT 信息提前准备好，启动时通过内存映射加载。

从 Runtime 视角看：

Heap 加载 boot image space
  -> ClassLinker 从 boot image 初始化
  -> InternTable 加入 image 中的字符串
  -> OatFileManager 能通过 image space 找到 boot oat file

这能避免每个应用进程都从零解析核心类，也能让 Zygote fork 后的应用共享大量只读页面。

3. Zygote space 与 Copy-on-Write

Zygote 在 fork 应用之前会预加载类和资源。预加载产生的对象如果保持稳定，就可以在 fork 后通过写时复制机制共享。

简化流程：

Zygote 创建 Runtime
  -> 预加载核心类和资源
  -> Runtime::PreZygoteFork()
  -> Heap::PreZygoteFork()
  -> 整理/压缩 zygote space
  -> fork app
  -> app 读共享页，写入时触发 COW

这就是为什么在 Zygote 阶段随意分配大对象或修改全局状态有风险：它可能增加所有子进程的内存成本，也可能让本应共享的页面过早变脏。

4. GC Root 与 JNI 引用

ART GC 需要知道哪些对象仍然可达。常见 root 来源包括：

线程栈
JNI 局部引用
JNI 全局引用
类静态字段
InternTable
ClassLinker
Monitor
Runtime 内部常量对象

JNIEnvExt 的 local reference table 和 JavaVMExt 的 global reference table 都会参与 root 遍历。这也是 JNI 引用管理必须谨慎的原因：

  • 局部引用太多不释放，可能撑爆 local reference table。
  • 全局引用不删除，会造成对象长期不可回收。
  • 跨线程误用 JNIEnv* ，可能破坏局部引用表语义。

OAT 文件管理

1. OAT、VDEX、DEX 的关系

简化理解：

文件内容作用
DEXDalvik 字节码、类、方法、字段、字符串等Java/Kotlin 编译后的字节码载体
VDEX验证后的 Dex 信息、quickening 相关数据等加速校验和加载，减少重复处理
OAT/ODEXAOT 编译产物、方法机器码、OatDexFile 元数据让 ART 可以直接执行或辅助解释执行
ART image预初始化对象和类元数据镜像加速 boot class path 初始化

Android 17/API 37 上常见路径会受 APEX、系统分区和厂商编译策略影响。下面只列出便于理解的路径形态，不保证每台设备都完全一致：

/system/framework/<isa>/boot.oat
/system/framework/<isa>/boot.vdex
/system/framework/<isa>/boot.art
/data/app/<package>/oat/<isa>/base.odex
/data/dalvik-cache/<isa>/...

这些路径只是形态示例。不同 Android 版本、厂商 ROM、系统分区布局和 APEX 策略都会改变实际位置。

2. Runtime 什么时候创建 OatFileManager

在 ART Runtime 初始化阶段， Runtime::Init() 会较早准备 OAT 管理相关结构。可简化理解为：

Runtime::Init()
  -> oat_file_manager_ = new OatFileManager

它负责跟踪已经打开的 OAT 文件，并提供：

功能说明
RegisterOatFile把 OAT 文件登记到运行时
FindOpenedOatFileFromDexLocation根据 Dex 位置查找已加载 OAT
GetBootOatFiles从 boot image space 中拿 boot OAT
OpenDexFilesFromOat按 Dex 位置打开对应 OAT，并返回 DexFile
DumpForSigQuit在 tombstone/sigquit 信息中输出 OAT 状态

对 Hook 来说， OpenDexFilesFromOat 是一个很值得关注的位置，因为应用 Dex、插件 Dex、二级 Dex 加载都可能走到这类逻辑。

3. OpenDexFilesFromOat 的简化流程

按 ART 主线， OatFileManager::OpenDexFilesFromOat() 或对应加载逻辑可以简化成：

OpenDexFilesFromOat(dex_location, class_loader, dex_elements)
  -> 根据 class loader 构造 ClassLoaderContext
  -> 创建 OatFileAssistant
  -> 尝试加锁，避免并发生成/加载 OAT
  -> 判断 OAT 是否 up-to-date
  -> 必要时尝试 MakeUpToDate，也就是触发 dex2oat
  -> 选择 best oat file
  -> 检查 class 冲突
  -> RegisterOatFile
  -> 如果可执行，尝试打开 app image
  -> 从 OAT 中打开 DexFile
  -> 如果失败，fallback 到原始 Dex

这里有几个容易踩坑的点：

  • OAT 文件存在，不代表一定会执行其中的机器码。
  • OAT 可能因为 boot image checksum、compiler filter、class loader context 不匹配而被降级使用或拒绝。
  • Debuggable 应用、profile 状态、系统编译策略都会影响最终选择。
  • 如果原始 Dex 不存在，只剩 OAT/VDEX，fallback 行为会更复杂，也更依赖版本。

4. OAT 和 ArtMethod 的关系

类加载和方法解析完成后， ArtMethod 可以指向解释器入口、JNI bridge、quick compiled code 等不同入口。

简化关系：

DexFile
  -> method_id / code_item
  -> ClassLinker 解析类和方法
  -> ArtMethod
  -> entry point
  -> interpreter / JNI bridge / quick compiled code

OAT 中的 compiled code 会影响 quick entry。前文的 ArtMethod 入口替换，本质上就是改写方法运行时入口。但这类操作强依赖版本、ABI、编译状态和调用路径，不是稳定 API。

JavaVM 和 JNIEnv

1. JavaVM 是进程级

在 Android 应用进程里， JavaVM* 可以理解为 JNI 看到的 VM 入口。它背后对应 ART 的 JavaVMExt 。

常见用法：

// JNI_OnLoad 由 ART 在 native 库加载成功后回调。
static JavaVM* g_vm = nullptr;

JNIEXPORT jint JNICALL JNI_OnLoad(JavaVM* vm, void*) {
    // 保存进程级 JavaVM，供后续 native 线程 attach 使用。
    g_vm = vm;
    return JNI_VERSION_1_6;
}

保存 JavaVM* 是合理的，因为它是进程级对象。很多 native 库都会这么做，用于后续在原生线程里 attach 到 VM。

2. JNIEnv 是线程级

JNIEnv* 只在当前线程有效。Java 调用 native 方法时，ART 会把当前线程对应的 JNIEnv* 作为第一个参数传入：

extern "C"
JNIEXPORT void JNICALL
Java_com_example_Foo_nativeCall(JNIEnv* env, jobject thiz) {
    // env 只属于当前 Java 调用线程，不要保存到全局跨线程使用。
}

原生线程要使用 JNI，必须先 attach：

JNIEnv* env = nullptr;
// 原生线程先查询自己是否已经附加到 VM。
if (g_vm->GetEnv(reinterpret_cast<void**>(&env), JNI_VERSION_1_6) == JNI_EDETACHED) {
    // 未附加时，主动 attach 并获取当前线程的 JNIEnv。
    if (g_vm->AttachCurrentThread(&env, nullptr) == JNI_OK) {
        // 可以在当前线程安全使用 env。
        g_vm->DetachCurrentThread();
    }
}

如果一个 native 线程生命周期很长，可以在线程启动时 attach，线程退出前 detach。不要在高频短任务中反复 attach/detach，否则会有额外开销。

3. JNI_OnLoad 发生在什么阶段

当 Kotlin/Java 层调用：

// 触发 ART 加载 libart_vm_probe.so，并调用 JNI_OnLoad。
System.loadLibrary("art_vm_probe")

ART 会通过 native loader 加载 .so ，并调用该库的 JNI_OnLoad 。此时 VM 已经创建完成，所以 JNI_OnLoad(JavaVM* vm, ...) 能收到有效的 JavaVM* 。

这也解释了一个常见误区：

JNI_OnLoad 不是创建 JavaVM 的地方
JNI_OnLoad 是某个 native 库被已存在的 JavaVM 加载后得到回调的地方

关键代码解释

1. 为什么 JNI_OnLoad 能拿到 JavaVM

示例代码：

// 这里的 vm 是当前进程已有的 JavaVM，不是 JNI_OnLoad 自己创建的。
JNIEXPORT jint JNICALL
JNI_OnLoad(JavaVM* vm, void*) {
    g_vm = vm;
    return JNI_VERSION_1_6;
}

JNI_OnLoad 是 native 库加载完成后的回调。调用它之前，ART Runtime 已经创建完成， JavaVMExt 已经存在。因此这里拿到的 vm 不是我们创建的，而是当前进程已有的 VM。

2. 为什么主线程 GetEnv 返回 JNI_OK

示例里 Java 调用：

// Kotlin/Java 调用 native 方法时，ART 会把当前线程的 JNIEnv 传给 native 层。
dumpFromMainThread()

进入 native 后：

// GetEnv 返回 JNI_OK 表示当前线程已经附加到 VM。
jint get_env_result = g_vm->GetEnv(
        reinterpret_cast<void**>(&env),
        JNI_VERSION_1_6
);

这个调用返回 JNI_OK ，因为当前线程本来就是 Java 线程，已经在 ART 的 ThreadList 中，也已经有对应 JNIEnvExt 。

3. 为什么 pthread 一开始没有 JNIEnv

原生线程由 pthread_create() 创建，它只属于 Linux 线程调度系统，并不会自动成为 ART 线程。

所以第一次：

// native 自建线程 attach 前，这个调用通常返回 JNI_EDETACHED。
g_vm->GetEnv(reinterpret_cast<void**>(&env), JNI_VERSION_1_6);

会返回 JNI_EDETACHED 。这时不能调用 env->FindClass() ，因为 env 为空。

4. AttachCurrentThread 实际做了什么

调用：

// attach 成功后，env 才可以在当前 native 线程中使用。
g_vm->AttachCurrentThread(&env, &args);

可以简化理解为：

AttachCurrentThread
  -> 检查当前线程是否已经 attach
  -> 为当前 native thread 创建 ART Thread 对象
  -> 创建或绑定 JNIEnvExt
  -> 加入 Runtime 的 ThreadList
  -> 返回当前线程的 JNIEnv*

这就是为什么 attach 后可以调用：

// attach 成功后可以调用 JNI 函数，例如查找 boot class path 中的 String 类。
env->FindClass("java/lang/String");

5. DetachCurrentThread 为什么必要

原生线程退出前应该调用：

// native 自建线程退出前释放 ART 线程状态。
g_vm->DetachCurrentThread();

否则 Runtime 可能仍然认为这个线程处于附加状态，相关线程对象、局部引用表、monitor 状态无法按预期清理。

如果线程是 Java 层创建的，例如 new Thread { nativeCall() } ，通常不需要手动 detach，因为它本来由 ART 管理。手动 attach/detach 主要针对 native 自己创建的线程。

原理说明

1. ART 创建流程的本质

ART 虚拟机创建可以分成三层：

层级入口结果
Android 进程入口app_process 、 AndroidRuntime::start()准备进入 Java 世界
JNI Invocation 入口JNI_CreateJavaVM()创建 ART Runtime 并返回 JavaVM/JNIEnv
ART 内部入口Runtime::Create/Init/Start初始化堆、类链接、线程、OAT、JNI 表等组件

从外面看是 “创建 JavaVM”，从里面看是 “创建整个运行时”。

2. 为什么一个进程通常只有一个 JavaVM

ART 的 Runtime 使用进程级单例。 Runtime::Create() 会检查当前进程是否已经存在 Runtime。

普通 Android App 中，Zygote fork 出应用时 Runtime 已经存在。业务 native 库只是被这个 Runtime 加载，不应该尝试再创建一个 VM。

3. 为什么 Xposed 关心 Zygote

Zygote 阶段已经创建 Runtime，并会预加载大量类。后续 App 进程是 fork 出来的。

因此在 Zygote 里改动：

  • 可能影响所有子进程。
  • 可能影响共享内存页面。
  • 可能比 App 自己加载类更早。
  • 也更容易造成系统级崩溃。

所以 Zygote Hook 的能力很强，风险也更高。

4. 为什么 OAT 管理影响 Hook

Hook Java 方法时，最终通常会落到下面几种执行路径之一：

解释执行
JNI bridge
quick compiled code
instrumentation entry
deoptimized entry

OAT 是否存在、是否可执行、方法是否已编译、是否被 deopt，都会影响 ArtMethod 当前入口。直接修改 entry point 的方案必须先确认目标方法当前处在哪条路径。

常见问题

1. JNI_OnLoad 没有日志

排查顺序：

  1. 确认 Java 代码执行了 System.loadLibrary("art_vm_probe") 。
  2. 确认 .so 名称是 libart_vm_probe.so 。
  3. 确认 ABI 匹配，例如设备是 arm64，APK 里有 arm64-v8a 。
  4. 用 adb logcat | grep dlopen 查看是否有加载失败。
  5. 检查 C++ 函数签名是否写成了 JNIEXPORT jint JNICALL JNI_OnLoad(JavaVM*, void*) 。

2. native 线程里 GetEnv 返回 -2

这是正常结果，表示当前线程还没有 attach 到 VM。

解决方式：

// 如果当前线程未附加，GetEnv 会返回 JNI_EDETACHED。
JNIEnv* env = nullptr;
if (g_vm->GetEnv(reinterpret_cast<void**>(&env), JNI_VERSION_1_6) == JNI_EDETACHED) {
    // attach 后 env 只在当前线程有效。
    g_vm->AttachCurrentThread(&env, nullptr);
}

线程退出前记得 DetachCurrentThread() 。

3. 保存全局 JNIEnv* 后偶发崩溃

JNIEnv* 不能跨线程保存。全局只保存 JavaVM* 。

错误模式：

// 错误示例：JNIEnv 是线程级对象，不能作为跨线程全局变量保存。
static JNIEnv* g_env = nullptr; // 不要这样做

正确模式：

// 正确示例：全局保存进程级 JavaVM。
static JavaVM* g_vm = nullptr;

每个线程需要 JNI 时，自己通过 GetEnv() 或 AttachCurrentThread() 获取当前线程的 JNIEnv* 。

4. FindClass 在 native 线程里找不到业务类

native 线程 attach 后没有天然的业务 ClassLoader 上下文， FindClass 可能只从 boot class path 找类。

常见做法：

  • 在 Java 调 native 时传入 ClassLoader 。
  • 保存业务类的 jclass 全局引用。
  • 通过传入的 ClassLoader.loadClass() 查找目标类。

注意全局引用用完要 DeleteGlobalRef() 。

5. 找不到 OAT 文件或 OAT 不执行

可能原因：

  • 应用处于 debuggable 状态，编译策略不同。
  • compiler filter 是 verify 或 speed-profile ，不一定有完整机器码。
  • profile 尚未收集， speed-profile 没有触发编译。
  • OAT 与 boot image checksum 不匹配，被降级或 fallback。
  • Android 版本路径变化，文件不在旧位置。

可以用下面命令观察：

# 查看当前包的 dexopt 状态。
adb shell dumpsys package dexopt | grep -A 8 <package>

# 强制以 speed 模式重新编译，便于观察 OAT/VDEX 变化。
adb shell cmd package compile -m speed -f <package>

把 <package> 替换成实际包名。

6. 源码行号和本文对不上

本文按 Android SDK 37/API 37 的运行环境讲流程。AOSP 具体源码请使用 API 37 对应分支 /tag；不同 tag 的代码结构可能变化。

排查方式：

  • 确认源码 tag。
  • 用函数名搜索，不要依赖行号。
  • 优先看调用关系，而不是字段偏移。
  • 对比不同 Android 版本源码时，特别关注 ART APEX、bootclasspath、hidden API、GC 策略和 JNI 文件路径变化。

扩展方向

可以沿着下面几条线继续深入：

  1. 对比 Android 14、Android 15、Android 16、Android 17 的 Runtime::Init() 差异。
  2. Hook RegisterNatives ，观察 startReg() 和业务库 JNI_OnLoad() 的注册顺序。
  3. 观察 OatFileManager::OpenDexFilesFromOat() ，记录插件化、热修复、二级 Dex 的加载路径。
  4. 结合 ArtMethod 入口替换，观察解释执行、AOT、JIT、deopt 后 entry point 的变化。
  5. 使用 JVMTI 做更稳定的调试和 instrumentation，减少对私有结构的依赖。
  6. 阅读 ClassLinker ，理解类加载、解析、链接和初始化如何影响 Hook 时机。

总结

ART 虚拟机创建流程可以抓住一条主线：

app_process 启动 AndroidRuntime
  -> AndroidRuntime 调 JNI_CreateJavaVM
  -> JNI_CreateJavaVM 创建并启动 Runtime
  -> Runtime 初始化 Heap、OAT、ClassLinker、JavaVMExt、JNIEnvExt
  -> 返回 JavaVM 和当前线程 JNIEnv
  -> 注册 Android native 方法
  -> 进入 ZygoteInit 或 RuntimeInit 的 Java main

理解这条线以后，很多 Xposed 和 Native Hook 里的问题会变得更清楚：

  • JavaVM* 可以全局保存，因为它是进程级入口。
  • JNIEnv* 不能跨线程保存，因为它绑定当前 ART Thread。
  • Zygote 阶段影响面大，因为 Runtime 和大量预加载状态会被 fork 继承。
  • OAT 是否存在不等于方法一定走 AOT 机器码。
  • ART 内部结构强版本相关，实验和工程化要分开看。

如果只记一句话：JNI_CreateJavaVM() 是外部名字， Runtime::Create/Init/Start 才是 ART 虚拟机真正成形的过程。
