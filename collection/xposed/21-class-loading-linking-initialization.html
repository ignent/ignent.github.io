ART 类的加载、链接、初始化流程

概述

上一篇从 app_process -> AndroidRuntime -> JNI_CreateJavaVM -> Runtime::Init/Start 讲了 ART 虚拟机如何创建。这一篇继续往下看：虚拟机起来以后，一个 Java 类是怎样从 Dex 里的 class_def 变成运行时里的 mirror::Class ，并最终执行 <clinit> 的。

本文以 Android SDK 37（Android 17 / API 37） 作为复现环境，源码说明以 AOSP main 和 API 37 对应分支 /tag 的函数名为准。ART 内部结构不是稳定公开 API，不要把字段偏移、类状态枚举值、源码路径直接跨版本硬套。

先给结论：

Dex class_def
  -> ClassLinker::FindClass
  -> ClassLinker::DefineClass
  -> SetupClass
  -> LoadClass
  -> LoadSuperAndInterfaces
  -> LinkClass
  -> EnsureInitialized / InitializeClass
  -> 执行 <clinit>

理解这条链，对 Xposed/LSPosed、Dex 分析、 ArtMethod Hook、类加载时机判断都很有用。很多 “Hook 太早找不到类”“类已经加载但静态字段还没赋值”“ Class.forName 为什么触发了静态代码块” 的问题，本质上都和这几个阶段有关。

ProbeTarget.kt

package com.example.classflow

import android.util.Log

open class ProbeTarget {
    companion object {
        private const val TAG = "ClassFlow"

        // 编译期常量。读取它通常不会触发类初始化，因为值会被内联到调用方。
        const val CONST_VALUE = 7

        // 非编译期常量。读取它需要类完成初始化。
        val RUNTIME_VALUE: Long = System.nanoTime()

        init {
            // <clinit> 的可见标记：只要看到这行日志，就说明类初始化真正发生了。
            Log.d(TAG, "ProbeTarget <clinit>")
        }

        @JvmStatic
        fun hello(): String {
            // 调用静态方法也会触发类初始化。
            return "hello:$RUNTIME_VALUE"
        }
    }
}

ProbeChild.kt

package com.example.classflow

import android.util.Log

class ProbeChild : ProbeTarget() {
    companion object {
        private const val TAG = "ClassFlow"

        init {
            // 子类初始化前，父类必须先完成初始化。
            Log.d(TAG, "ProbeChild <clinit>")
        }

        @JvmStatic
        fun childHello(): String {
            return "child"
        }
    }
}

MainActivity.kt

package com.example.classflow

import android.app.Activity
import android.os.Bundle
import android.util.Log
import android.widget.TextView

class MainActivity : Activity() {
    private val TAG = "ClassFlow"

    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)

        val output = TextView(this).apply {
            textSize = 16f
            setPadding(48, 72, 48, 48)
            text = "Tap to run class loading probe.\nCheck logcat tag ClassFlow."
        }
        setContentView(output)

        output.setOnClickListener {
            // 点击后再运行，避免 Activity 创建时机干扰日志观察。
            val result = runProbe()
            output.text = result
        }
    }

    private fun runProbe(): String {
        val report = StringBuilder()
        val loader = classLoader

        log(report, "step 1: before Class.forName(false)")

        try {
            // initialize=false：请求加载并解析 Class 对象，但不主动执行 <clinit>。
            val targetClass = Class.forName(
                    "com.example.classflow.ProbeTarget",
                    false,
                    loader
            )
            log(report, "step 2: after Class.forName(false): " + targetClass.name)

            // 读取编译期常量通常不触发 ProbeTarget 初始化。
            val constValue = ProbeTarget.CONST_VALUE
            log(report, "step 3: read CONST_VALUE=$constValue")

            // initialize=true：主动确保类初始化，会执行 ProbeTarget.<clinit>。
            Class.forName("com.example.classflow.ProbeTarget", true, loader)
            log(report, "step 4: after Class.forName(true)")

            // 静态方法调用发生在类已初始化之后，不会重复执行 <clinit>。
            log(report, "step 5: call hello=" + ProbeTarget.hello())

            // 初始化子类前，ART 必须确保父类已经初始化。
            Class.forName("com.example.classflow.ProbeChild", true, loader)
            log(report, "step 6: after child Class.forName(true)")
        } catch (e: ClassNotFoundException) {
            // 类描述符找不到时，对应源码流程会走异常路径。
            log(report, "error: $e")
        }

        return report.toString()
    }

    private fun log(report: StringBuilder, message: String) {
        Log.d(TAG, message)
        report.append(message).append('\n')
    }
}

mirror::Object 简介

1. mirror 是什么

ART 里有一组 art::mirror 类型，用 C++ 描述 Java 堆里的对象布局。它们不是普通业务 C++ 对象，而是 Java heap object 的 C++ 视图。

常见类型包括：

mirror 类型Java / 运行时含义
mirror::Object所有 Java 对象的基础布局
mirror::ClassJava 层 java.lang.Class 的运行时对象
mirror::StringJava 字符串
mirror::Array数组基类
mirror::ObjectArray<T>对象数组
mirror::PrimitiveArray<T>基本类型数组
mirror::DexCacheDex 解析缓存，例如已解析类、方法、字段、字符串
mirror::ThrowableJava 异常对象
mirror::StackTraceElementJava 堆栈元素

可以用下面的 Mermaid 图表达：

这里要注意：图里展示的是理解模型。字段名、辅助字段、压缩引用、读屏障、对象头布局都可能随 ART 版本变化。API 37 对应源码里， mirror::Object 的关键字段仍然可以抓住两个：

// mirror::Object 的简化示意，不是完整源码。
class Object {
    // 指向当前对象所属的 mirror::Class。
    HeapReference<Class> klass_;

    // monitor、锁状态、identity hash code 等信息。
    uint32_t monitor_;
};

2. 每个对象都知道自己属于哪个类

klass_ 是理解 ART 对象模型的入口。任意 Java 对象都能通过对象头找到自己的类：

Java 对象实例
  -> mirror::Object::klass_
  -> mirror::Class
  -> dex_cache / super_class / vtable / iftable / fields / methods

这也是为什么 Hook、反射、GC、类型检查都离不开 mirror::Class 。

例如：

操作运行时会关心什么
obj.getClass()从对象头拿 klass_
instanceof判断当前类和目标类的继承 / 接口关系
虚方法调用通过类的 vtable/imt 找目标方法
字段访问使用类链接阶段计算好的字段偏移
GC 扫描根据类里的引用字段布局访问对象引用

3. monitor_ 不只是锁

monitor_ 保存的是 lock word。它和下面这些行为相关：

  • synchronized
  • Object.wait/notify/notifyAll
  • identity hash code
  • monitor 膨胀

所以一个 Java 对象看起来只是业务字段，实际对象头还必须支持类型、锁、hash、GC 等运行时能力。

mirror::Class 与 ClassStatus

mirror::Class 也是 Java 堆里的对象，它本身继承自 mirror::Object 。这件事很绕，但很关键：

某个 Java 对象 obj
  -> obj.klass_ 指向 `Foo::class.java` 对应的 mirror::Class

`Foo::class.java` 这个 Class 对象
  -> 它自己也是对象
  -> 它的 klass_ 指向 java.lang.Class 对应的 mirror::Class

mirror::Class 保存了类运行时需要的大量信息：

信息作用
status_当前类处于加载、链接、验证、初始化哪个阶段
super_class_父类
dex_cache_Dex 解析缓存
class_loader_定义这个类的 ClassLoader
iftable_接口表
vtable_虚方法分发表
direct/virtual methods直接方法、虚方法，对应 ArtMethod
instance/static fields实例字段、静态字段，对应 ArtField

类状态大致可以这样理解：

kNotReady
  -> kIdx
  -> kLoaded
  -> kResolving
  -> kResolved
  -> kVerified
  -> kInitializing
  -> kInitialized
  -> kVisiblyInitialized

简化含义如下：

状态含义
kNotReady刚分配出来的 mirror::Class
kIdx已从 Dex 读到基本索引信息
kLoaded父类和接口索引已解析
kResolving正在链接，可能从临时 Class 克隆出最终大小的 Class
kResolved字段、方法、vtable/iftable 等链接完成
kVerified字节码验证完成
kInitializing某个线程正在执行类初始化
kInitialized<clinit> 已完成
kVisiblyInitialized初始化结果对所有线程可见，可做更便宜的初始化检查

异常状态也很重要：

状态含义
kErrorUnresolved加载 / 链接失败，类还没解析完成
kErrorResolved已解析过，但初始化等后续阶段失败

这解释了为什么一次类初始化失败后，后续再访问可能直接抛出 NoClassDefFoundError 或相关错误。

ClassLinker 创建流程

1. Runtime::Init 中创建 ClassLinker

上一篇讲过 Runtime::Init() 会创建堆、线程列表、JNI 环境、OAT 管理等组件。 ClassLinker 也是在这个阶段创建的。

按 AOSP main 的主线，简化伪代码如下：

// Runtime::Init 中的简化流程，不是完整源码。
bool Runtime_Init(RuntimeOptions options) {
    // 前面已经创建 heap、intern_table、thread_list 等运行时基础设施。

    if (is_aot_compiler) {
        // AOT 编译器场景会使用编译器回调创建 AOT 版本的 ClassLinker。
        class_linker_ = compiler_callbacks->CreateAotClassLinker(intern_table_);
    } else {
        // 普通运行时创建 ClassLinker。
        class_linker_ = new ClassLinker(
                intern_table_,
                options.fast_class_not_found_exception
        );
    }

    if (heap->HasBootImageSpace()) {
        // 常规 Android 设备通常从 boot image 初始化。
        class_linker_->InitFromBootImage(&error_msg);
    } else {
        // 没有 boot image 时，从 boot class path 的 dex 文件启动。
        class_linker_->InitWithoutImage(std::move(boot_class_path), &error_msg);
    }

    return true;
}

可以看到， ClassLinker 创建依赖几个前置条件：

  • Heap 已经存在，因为类对象本身在 Java 堆里。
  • InternTable 已经存在，因为类名、字符串驻留会用到。
  • 当前线程已经能以 ART Thread 的身份运行。
  • Boot image 或 boot class path 已经准备好。

2. ClassLinker 构造函数做什么

ClassLinker::ClassLinker(...) 本身不会立刻加载所有类。它主要准备管理结构，例如：

成员 / 结构作用
boot_class_table_boot class loader 对应的类表
class_roots_ART 运行时核心类根，例如 java.lang.Object 、 java.lang.Class
resolution stubs方法解析、接口调用、JNI 桥等运行时入口
pointer size运行时 / 镜像指针大小
class lookup cache数组类、类查找等缓存

构造只是 “搭架子”，真正把核心类接进来是在 InitFromBootImage() 或 InitWithoutImage() 。

ClassLinker 的初始化

1. 有 boot image：InitFromBootImage

Android 设备常见路径是有 boot image。Boot image 中已经保存了一批核心类对象、字符串、方法元数据、DexCache 等。

简化流程：

ClassLinker::InitFromBootImage()
  -> 从 Heap 的 boot image space 找 image roots
  -> 建立 class_roots_
  -> 注册 boot image 中的 oat/dex 信息
  -> 把 boot image 的类加入 boot_class_table_
  -> 初始化 java.lang.Object、java.lang.Class 等核心类关系
  -> 设置 resolution stubs / runtime entrypoints
  -> 标记 ClassLinker init_done_

这种方式快，因为很多核心类已经是 “预构造” 的对象。Zygote fork 后，应用进程还能共享大量只读页。

2. 没有 boot image：InitWithoutImage

命令行运行、测试环境、特殊构建可能没有 boot image。这时 ClassLinker 需要从 boot class path 的 Dex 文件启动。

简化流程：

ClassLinker::InitWithoutImage(boot_class_path)
  -> 注册 boot class path DexFile
  -> 手动查找/加载 java.lang.Object
  -> 加载 java.lang.Class
  -> 建立基础 class roots
  -> 加载 String、Throwable、ClassLoader、DexCache 等核心类
  -> 完成基础字段偏移和类关系校验
  -> 标记 ClassLinker init_done_

这条路径更慢，但非常适合理解 ART 如何从 Dex “自举” 出类系统。

3. 为什么 Object 和 Class 特别

普通类可以依赖已有的类系统加载。但 java.lang.Object 和 java.lang.Class 是类系统的根：

所有对象都继承 Object
所有对象都通过 klass_ 指向 Class
Class 自己也是 Object
Class 的 klass_ 又是 java.lang.Class

这会形成一个启动鸡生蛋问题。ART 通过 boot image 或特殊的初始化顺序解决它。

类的加载、链接

1. FindClass：入口

运行时要找一个类，常见入口是：

ClassLinker::FindClass(self, descriptor, class_loader)

描述符是 Dex/ART 使用的类名形式：

Java 写法Descriptor
java.lang.StringLjava/lang/String;
intI
int[][I
java.lang.String[][Ljava/lang/String;

FindClass 的大致流程：

FindClass(descriptor, class_loader)
  -> 如果是基本类型，返回 primitive class
  -> 如果是数组，创建或查找数组类
  -> 先查 class table，看是否已经加载
  -> boot class loader 走 boot class path
  -> app class loader 走 BaseDexClassLoader 的 dex path
  -> 找到 DexFile + ClassDef 后 DefineClass

这也是 Xposed 里常说 “要用目标 App 的 ClassLoader” 的原因：同一个类名在不同 ClassLoader 下可以是不同的类。

2. DefineClass：把 ClassDef 变成 mirror::Class

当 ClassLinker 找到了 Dex 中的 class_def ，就进入 DefineClass 。

简化伪代码：

// ClassLinker::DefineClass 的简化版，不是完整源码。
mirror::Class* DefineClass(descriptor, class_loader, dex_file, class_def) {
    // 分配一个 mirror::Class 对象，初始状态类似 kNotReady。
    mirror::Class* klass = AllocClass(class_size);

    // 记录 DexCache、ClassLoader、descriptor、access flags 等基础信息。
    klass->SetDexCache(dex_cache);
    SetupClass(dex_file, class_def, klass, class_loader);

    // 读取 Dex 中的字段、方法、注解、访问标志等。
    LoadClass(dex_file, class_def, klass);

    // 解析父类和接口。
    LoadSuperAndInterfaces(klass, dex_file);

    // 链接字段、方法、vtable、iftable，并插入 class table。
    LinkClass(descriptor, klass, interfaces);

    return klass;
}

3. SetupClass：填基础身份

SetupClass 负责设置类的基本身份：

  • descriptor
  • access flags
  • class loader
  • Dex class def index
  • DexCache
  • 是否接口、注解、枚举、final 等标志

这一步之后，类对象已经知道 “我是谁、来自哪个 Dex、由哪个 ClassLoader 定义”。

4. LoadClass：读字段和方法

LoadClass 会把 Dex 里的字段和方法读成 ART 运行时结构：

Dex 内容ART 运行时结构
encoded fieldArtField
encoded methodArtMethod
method access flagsruntime access flags
code item / oat classmethod entrypoint 相关信息
annotations注解相关结构

这一步会让类进入 “已经有字段 / 方法元数据” 的状态，但字段偏移、虚方法表等还没完全确定。

5. LoadSuperAndInterfaces：解析父类和接口

类不能孤立存在。链接前必须知道：

  • 父类是谁。
  • 实现了哪些接口。
  • 接口继承关系如何。
  • 父类 / 接口是否能被当前类访问。

如果父类或接口找不到，类会进入错误状态，并向 Java 层表现为 ClassNotFoundException 、 NoClassDefFoundError 或链接错误。

6. LinkClass：真正链接

LinkClass 是 “能不能安全使用这个类” 的关键阶段。

它通常会做：

LinkClass
  -> LinkMethods
  -> LinkInstanceFields
  -> LinkStaticFields
  -> 计算对象实例大小
  -> 建立 vtable
  -> 建立 iftable / IMT
  -> 处理接口默认方法、miranda method、冲突方法
  -> 设置字段偏移
  -> 设置 ClassStatus::kResolved
  -> 插入 class table 或替换临时类

链接完成后，类已经可以用于类型检查、字段偏移计算、方法分发等。但这仍不等于 <clinit> 已执行。

类的初始化

1. 初始化触发条件

Java 语义上，下面行为通常会触发类初始化：

  • 创建类实例。
  • 调用类的静态方法。
  • 写入类的静态字段。
  • 读取类的非编译期常量静态字段。
  • Class.forName(name) 默认初始化。
  • Class.forName(name, true, loader) 明确初始化。

下面行为通常不会主动触发初始化：

  • Class.forName(name, false, loader) 。
  • 读取编译期常量 const val X = 1 。
  • 获取类字面量 Foo::class.java 。
  • 创建数组类 Foo[] 。

具体细节要以 Java 语言规范和 Android 运行时行为为准。

2. EnsureInitialized 与 InitializeClass

ART 里常见入口是：

ClassLinker::EnsureInitialized(self, klass, can_init_fields, can_init_parents)

它会检查类是否已经初始化；如果没有，就进入：

ClassLinker::InitializeClass(...)

简化流程：

InitializeClass(klass)
  -> 如果已经 initialized，直接返回
  -> 如果其他线程正在初始化，等待
  -> 如果父类未初始化，先初始化父类
  -> 如果接口有 default methods，按规则初始化相关接口
  -> 设置状态为 kInitializing
  -> 准备静态字段默认值
  -> 执行 <clinit>
  -> 成功后设置 kInitialized
  -> 后续变成 kVisiblyInitialized
  -> 失败则设置错误状态并保存异常

这解释了示例日志：

Class.forName(false)
  -> 可以返回 Class 对象
  -> 不执行 ProbeTarget <clinit>

Class.forName(true)
  -> EnsureInitialized
  -> InitializeClass
  -> 执行 ProbeTarget <clinit>

3. 父类先于子类初始化

示例中：

Class.forName("com.example.classflow.ProbeChild", true, loader);

如果 ProbeTarget 还没初始化，ART 必须先初始化父类，再初始化子类。

顺序应该是：

ProbeTarget <clinit>
ProbeChild <clinit>

如果父类初始化失败，子类初始化也不能继续。

4. 多线程初始化等待

类初始化必须保证最多一个线程执行 <clinit> 。如果线程 A 正在初始化某个类，线程 B 也来初始化同一个类，线程 B 会等待。

简化模型：

Thread A
  -> status = kInitializing
  -> run <clinit>

Thread B
  -> 发现 status = kInitializing
  -> WaitForInitializeClass
  -> A 完成后继续

这能避免静态字段被并发初始化出不一致状态。

从代码现象映射到 ART 流程

1. Class.forName(false)

// 只要求得到 Class 对象，不主动运行 <clinit>。
Class.forName("com.example.classflow.ProbeTarget", false, loader);

可能发生：

FindClass
  -> class table 未命中
  -> DefineClass
  -> LoadClass
  -> LoadSuperAndInterfaces
  -> LinkClass

通常不会发生：

InitializeClass
  -> run <clinit>

2. Class.forName(true)

// 要求类完成初始化。
Class.forName("com.example.classflow.ProbeTarget", true, loader);

可能发生：

FindClass
  -> 如果已经 resolved，直接拿 Class
EnsureInitialized
  -> InitializeClass
  -> run <clinit>

3. 静态方法调用

// 调用静态方法前，类必须完成初始化。
ProbeTarget.hello();

如果类尚未初始化，ART 会先做初始化检查。解释器、AOT、JIT、nterp 的具体入口不同，但语义上必须保证 <clinit> 已执行。

对 Xposed/Hook 的意义

1. 找不到类，通常是 ClassLoader 时机不对

如果 Hook 代码太早执行，目标 App 的 PathClassLoader 还没加载目标 Dex， findClass 就会失败。

常见策略：

  • 等到 handleLoadPackage 提供目标 classLoader 后再找类。
  • Hook Application.attach(Context) ，拿 context.getClassLoader() 。
  • 对插件化 App，继续追踪插件 Dex 的 ClassLoader。
  • 不要用模块自身 ClassLoader 去找目标 App 的类。

2. 类已加载，不代表静态字段已就绪

如果你通过 Class.forName(name, false, loader) 或 Dex 扫描拿到了类，不代表静态字段已经初始化。

例如：

// initialize=false 不执行 <clinit>。
val clazz: Class<*> = Class.forName(name, false, loader)

这时读取某些静态字段可能触发初始化，也可能拿不到预期值。Hook 静态初始化相关逻辑时，要清楚自己介入的是加载、链接还是初始化阶段。

3. Hook <clinit> 风险更高

静态初始化涉及类状态锁、父类初始化、异常缓存和多线程等待。Hook <clinit> 时要特别小心：

  • 不要在 <clinit> 里再次触发同一个类初始化。
  • 不要过早访问目标类的复杂静态字段。
  • 注意初始化失败会影响后续所有访问。
  • 避免在系统核心类初始化阶段做耗时或可能抛异常的逻辑。

源码追踪方法

如果你有 AOSP 源码，可以在源码根目录搜索：

# 追踪 Runtime 中 ClassLinker 的创建和初始化。
rg -n "class_linker_|new ClassLinker|InitFromBootImage|InitWithoutImage|EnsureInitialized" \
  art/runtime/runtime.cc
# 追踪类查找、定义、加载、链接和初始化。
rg -n "ClassLinker::FindClass|ClassLinker::DefineClass|ClassLinker::LoadClass|ClassLinker::LinkClass|ClassLinker::InitializeClass|ClassLinker::EnsureInitialized" \
  art/runtime/class_linker.cc
# 观察 mirror::Object、mirror::Class 和类状态。
rg -n "klass_|monitor_|ClassStatus|status_|IsLoaded|IsResolved|IsInitialized" \
  art/runtime/mirror/object.h \
  art/runtime/mirror/class.h \
  art/runtime/class_status.h

不同 AOSP 分支中文件位置可能变化，尤其是 ART APEX、JNI、OAT 相关文件。建议优先搜索函数名。

常见问题

1. Class.forName(false) 为什么还是能返回 Class

因为它可以完成加载 / 链接，得到 java.lang.Class 对象，但不要求执行 <clinit> 。这正是示例里 ProbeTarget <clinit> 没有立刻出现的原因。

2. Foo::class.java 会触发静态代码块吗

通常不会。类字面量需要拿到 Class 对象，但不主动初始化类。

3. 读取 static final 一定不触发初始化吗

不一定。编译期常量可能被内联，不触发初始化；但如果值不是编译期常量，例如来自方法调用、对象创建、数组创建，就需要初始化。

object ConstantProbe {
    // 通常会被内联。
    const val A = 1

    // 不是编译期常量，读取前需要初始化。
    val B: Long = System.nanoTime()
}

4. 为什么 Hook 时类名对了还是找不到

通常是 ClassLoader 不对，或者目标 Dex 还没有加入当前 ClassLoader。插件化、加固、动态下发 Dex 都会让这个问题更常见。

5. 初始化失败后为什么后面都失败

类初始化失败会把类置为错误状态。后续再访问时，运行时会根据错误状态直接抛异常，不会像第一次一样重新完整初始化。

限制与风险

  1. mirror::Object 、 mirror::Class 、 ClassLinker 是 ART 内部实现，不是稳定 API。
  2. API 37 对应源码和 AOSP main 可能存在差异，写文章或做实验时要固定 tag。
  3. 类加载和初始化可能执行用户代码，例如 <clinit> ，Hook 时要考虑副作用。
  4. 在 Zygote 或系统类初始化阶段做复杂 Hook，风险比普通 App 类更高。
  5. 多 ClassLoader 场景下，同名类不等于同一个类。

扩展方向

可以继续深入：

  1. 跟踪 BaseDexClassLoader 、 DexPathList 、 DexFile 到 ClassLinker::FindClass 的 JNI/Native 边界。
  2. 观察插件化框架添加 Dex 后， ClassLinker 如何从新的 Dex path 找到类。
  3. 分析 LinkMethods 如何构建 vtable、iftable、IMT。
  4. 对比解释器、AOT、JIT、nterp 下的类初始化检查入口。
  5. 结合 ArtMethod 入口替换，观察类未初始化方法和已初始化方法的 entry point 差异。

总结

类的生命周期可以用一句话概括：

加载让 Class 出现，链接让 Class 可用，初始化让静态状态真正生效。

在 ART 中，这条链主要由 ClassLinker 推动：

FindClass
  -> DefineClass
  -> SetupClass
  -> LoadClass
  -> LoadSuperAndInterfaces
  -> LinkClass
  -> EnsureInitialized / InitializeClass

理解这条链之后，再看 Xposed 的 findClass 、 hookMethod 、 <clinit> Hook、插件 Dex 加载，就能分清楚自己介入的是 “类还没找到”“类已加载但未初始化”，还是 “类已经完成初始化” 的不同阶段。
