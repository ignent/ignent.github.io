libxposed 模块入口与生命周期

概述

基于一份 libxposed 模块模板代码，解释 libxposed 102 API 模块 是怎样被 LSPosed 识别、加载并执行 Hook 逻辑的。

这份模板目前不是一个完整业务 Hook，而是一个 “模块骨架”。它已经具备这些关键能力：

  • 通过 META-INF/xposed/module.prop 声明模块能力和 API 版本
  • 通过 META-INF/xposed/java_init.list 指定 Kotlin 入口类
  • 通过 scope.list 设置默认作用域
  • 在 HookEntry.kt 中接收模块加载、包加载、包就绪、system_server 启动、热重载等生命周期回调
  • 使用 libxposed 的 hook(...).intercept { ... } 和 getInvoker(...) 演示新 API 的 Hook 链调用方式
  • 通过 MainActivity + native-lib.cpp 保留一个标准 JNI 示例，方便后续扩展 Native 逻辑

读完本文，你应该能知道每个文件的作用、LSPosed 的加载流程、代码执行顺序，以及如何把模板里的示例类替换成自己的目标类。

项目结构

核心文件如下：

libxposed-template/
├── app/build.gradle.kts
├── app/src/main/AndroidManifest.xml
├── app/src/main/java/com/lsposedtemplate/
│   ├── HookEntry.kt
│   └── MainActivity.kt
├── app/src/main/cpp/
│   ├── CMakeLists.txt
│   └── native-lib.cpp
├── app/src/main/keepRules/rules.keep
└── app/src/main/resources/META-INF/xposed/
    ├── java_init.list
    ├── module.prop
    ├── native_init.list
    └── scope.list

一、模块声明文件

1. module.prop

文件路径：

app/src/main/resources/META-INF/xposed/module.prop

当前内容：

minApiVersion=101
targetApiVersion=102
staticScope=true
autoHotReload=true

这几个字段决定 LSPosed 如何看待这个模块。

minApiVersion=101 表示模块至少需要 libxposed API 101。设备上的框架 API 太旧时，模块不应被加载。

targetApiVersion=102 表示模块按 API 102 编写。模板的依赖版本也是 io.github.libxposed:api:102.0.0 ，两者是对应关系。

staticScope=true 表示模块使用静态作用域。LSPosed 可以读取 APK 内的 scope.list ，给模块提供默认目标包列表。

autoHotReload=true 表示支持自动热重载。模块更新后，框架可以走 onHotReloading() 和 onHotReloaded() 这套流程，而不是完全依赖重启目标进程。

2. java_init.list

文件路径：

app/src/main/resources/META-INF/xposed/java_init.list

当前内容：

com.lsposedtemplate.HookEntry

当目标进程启动并命中模块作用域时，LSPosed 会读取这个列表，加载 com.lsposedtemplate.HookEntry ，然后调用它的生命周期方法。

模板里的入口类长这样：

class HookEntry : XposedModule() {
    companion object {
        const val TAG = "0X->"
    }
}

它继承了 io.github.libxposed.api.XposedModule 。这和传统 API 中实现 IXposedHookLoadPackage 不同：传统入口通常只关心 handleLoadPackage() ，而 libxposed 把不同阶段拆成多个更明确的回调。

3. scope.list

文件路径：

app/src/main/resources/META-INF/xposed/scope.list

当前内容：

com.android.settings

这表示模块默认希望作用在：

  • com.android.settings

实际是否生效还要看 LSPosed 管理器里是否启用模块、是否勾选作用域，以及目标进程是否重启。 scope.list 是模块作者给出的默认目标列表。

二、Gradle 打包配置

1. libxposed 依赖为什么是 compileOnly

文件路径：

app/build.gradle.kts

相关依赖：

dependencies {
    compileOnly(libs.libxposed.api)
    implementation(libs.service)
    implementation(libs.dexkit)
}

libxposed.api 使用 compileOnly ，意思是：

  • 编译时需要它，因为 HookEntry.kt 要引用 XposedModule 、 PackageLoadedParam 等类型
  • 打包进 APK 时不带它，因为目标设备上的 LSPosed 框架会提供运行时 API

如果误用 implementation(libs.libxposed.api) ，就可能把 API 类一起打进 APK，造成类加载冲突或版本不一致。Xposed API 类通常应由框架提供，模块只在编译期依赖。

2. META-INF/xposed 如何进入 APK

当前打包配置：

packaging {
    resources {
        merges += "META-INF/xposed/*"
        excludes += "**"
    }
}

拆开看：

merges += "META-INF/xposed/*" 表示 META-INF/xposed/ 下的模块声明文件要保留并合并进最终 APK。

excludes += "**" 表示其他普通 Java resources 默认排除，减少无关资源进入 APK。

最终结果是：LSPosed 需要读取的 module.prop 、 java_init.list 、 scope.list 会留在 APK 里。

可以用下面命令检查 APK：

unzip -l app/build/outputs/apk/debug/app-debug.apk | grep 'META-INF/xposed'

预期能看到类似：

META-INF/xposed/module.prop
META-INF/xposed/java_init.list
META-INF/xposed/native_init.list
META-INF/xposed/scope.list

3. R8 keep 规则

文件路径：

app/src/main/keepRules/rules.keep

关键内容：

-dontwarn io.github.libxposed.annotation.**
-adaptresourcefilecontents META-INF/xposed/java_init.list
-keep,allowoptimization,allowobfuscation public class * extends io.github.libxposed.api.XposedModule {
    public <init>();
}

这几行主要解决 release 混淆后的入口问题。

-keep ... extends XposedModule 保证继承 XposedModule 的入口类不会被删掉，并保留公开无参构造函数。LSPosed 需要能创建入口类实例，如果构造函数被移除，模块就无法初始化。

-adaptresourcefilecontents META-INF/xposed/java_init.list 表示如果 R8 改了入口类名，要同步改 java_init.list 里的文本。否则 APK 里可能写着旧类名，运行时却已经被混淆成新类名，LSPosed 就找不到入口。

当前 debug 构建通常不混淆，但 release 包必须考虑这个问题。

三、整体加载流程

按当前模板，模块加载可以理解成下面这条链：

安装 APK
  ↓
LSPosed 扫描 APK 中的 META-INF/xposed/module.prop
  ↓
读取 minApiVersion、targetApiVersion、staticScope、autoHotReload
  ↓
读取 java_init.list，找到 com.lsposedtemplate.HookEntry
  ↓
目标包进程启动，并且命中 scope.list 或管理器作用域
  ↓
框架在目标进程中创建 HookEntry 实例
  ↓
调用 onModuleLoaded()
  ↓
包代码加载到一定阶段后调用 onPackageLoaded()
  ↓
应用组件和 classLoader 准备完成后调用 onPackageReady()
  ↓
在 onPackageReady() 中读取远程偏好、安装 Hook、调用 Invoker 示例

如果是 system_server ，还会走：

system_server 启动
  ↓
调用 onSystemServerStarting()

四、HookEntry 生命周期回调

1. onModuleLoaded：模块刚被加载

代码：

override fun onModuleLoaded(param: ModuleLoadedParam) {
    log(Log.INFO, TAG, "onModuleLoaded: " + param.processName)
    log(Log.INFO, TAG, "framework: $frameworkName($frameworkVersionCode) API $apiVersion")

    val hasProp: (Long) -> Boolean = { prop -> frameworkProperties.and(prop) != 0L }
    log(Log.INFO, TAG, "system supported: " + hasProp(PROP_CAP_SYSTEM))
    log(Log.INFO, TAG, "remote supported: " + hasProp(PROP_CAP_REMOTE))
    log(Log.INFO, TAG, "api protection: " + hasProp(PROP_RT_API_PROTECTION))
}

这个回调说明模块类已经被框架加载成功。模板做了三类日志：

  • 当前进程名： param.processName
  • 框架信息： frameworkName 、 frameworkVersionCode 、 apiVersion
  • 框架能力：是否支持 system、remote、API protection

frameworkProperties 是一个 bit mask。代码里的 hasProp 用按位与判断某个能力位是否存在：

frameworkProperties.and(prop) != 0L

预期效果是在 Logcat 看到类似：

0X->: onModuleLoaded: com.yuanrenxue.challenge
0X->: framework: LSPosed(... ) API 102
0X->: system supported: true
0X->: remote supported: true
0X->: api protection: true

如果这些日志没有出现，优先检查模块是否启用、作用域是否勾选、目标进程是否重启、 java_init.list 是否被打进 APK。

2. onPackageLoaded：包加载阶段

代码：

@RequiresApi(Build.VERSION_CODES.Q)
override fun onPackageLoaded(param: PackageLoadedParam) {
    log(Log.INFO, TAG, "onPackageLoaded: " + param.packageName)
    log(Log.INFO, TAG, "default classloader is " + param.defaultClassLoader)
}

这里能拿到：

  • param.packageName ：当前被加载的包名
  • param.defaultClassLoader ：默认类加载器

这个阶段适合做轻量判断，比如确认当前包名、打印类加载器、过滤不需要处理的进程。模板暂时没有在这里安装 Hook，而是把实际演示放在 onPackageReady() 。

3. onPackageReady：应用更完整地准备好

代码开头：

override fun onPackageReady(param: PackageReadyParam) {
    log(Log.INFO, TAG, "onPackageReady: " + param.packageName)
    log(Log.INFO, TAG, "app classloader is " + param.classLoader)
    if (Build.VERSION.SDK_INT >= Build.VERSION_CODES.P) {
        log(Log.INFO, TAG, "app acf is " + param.appComponentFactory)
    }
    log(Log.INFO, TAG, "module apk path: " + this.moduleApplicationInfo.sourceDir)
    log(Log.INFO, TAG, "----------")

    if (!param.isFirstPackage) return
}

这一段先打印应用级信息：

  • param.packageName ：目标包名
  • param.classLoader ：应用 classLoader，后面反射目标类要用它
  • param.appComponentFactory ：Android P 以后可用，表示应用组件工厂
  • moduleApplicationInfo.sourceDir ：模块 APK 路径

然后有一个非常重要的判断：

if (!param.isFirstPackage) return

一个进程里可能加载多个 package 或 split。 isFirstPackage 用来避免同一个进程重复安装 Hook。对于多数 Hook 场景，这是一个很实用的保护：否则同一个方法可能被重复拦截，日志和返回值都会变得难以判断。

4. onSystemServerStarting：system_server 启动

代码：

override fun onSystemServerStarting(param: SystemServerStartingParam) {
    log(Log.INFO, TAG, "onSystemServerStarting, system classloader: " + param.classLoader)
}

这个回调只和系统进程有关，适合做系统服务、系统类、framework 层的 Hook。

当前模板只打印了 system classLoader，没有实际 Hook 系统服务。如果后续要拦截 com.android.server 下的类，可以从这个回调开始。

五、远程偏好读取流程

onPackageReady() 里有一段远程偏好代码：

val prefs = getRemotePreferences("test")
log(Log.INFO, TAG, "remote prefs: " + prefs.getInt("test", -1))
prefs.registerOnSharedPreferenceChangeListener { _, key ->
    val value = prefs.getInt(key, 0)
    log(Log.INFO, TAG, "onSharedPreferenceChanged: $key->$value")
}

它的作用是从模块侧读取一个名为 test 的远程 preferences，然后取出 key 为 test 的整数。

为什么要用远程偏好？因为 Hook 代码运行在目标 App 进程里，不在模块自己的进程里。传统 SharedPreferences 只能直接读当前进程所属应用的数据目录，跨应用直接读会遇到权限和路径问题。libxposed 的 remote preferences 是框架提供的跨进程配置读取方式。

        try {
            val text = openRemoteFile("test.txt").use {
                FileReader(it.fileDescriptor).readText()
            }
            log(Log.INFO, TAG, "remote file content: $text")
        } catch (_: FileNotFoundException) {
            log(Log.INFO, TAG, "remote file not found")
        }

这段代码和 getRemotePreferences("test") 的用途类似，都是让运行在目标 App 进程里的 Hook 代码访问模块侧数据。区别在于：

  • getRemotePreferences(...) 适合读取开关、数字、字符串这类小配置
  • openRemoteFile(...) 适合读取文本规则、证书、脚本、字典、JSON 配置这类文件内容

执行流程可以拆成 4 步：

Hook 代码运行在目标 App 进程
  ↓
调用 openRemoteFile("test.txt")
  ↓
框架从模块侧打开对应文件，并返回可读的文件描述符
  ↓
FileReader(it.fileDescriptor).readText() 读取文本内容

use { ... } 的作用是自动关闭 openRemoteFile(...) 返回的资源，避免文件描述符泄漏。读取成功时会打印：

remote file content: <文件内容>

如果模块侧没有这个文件， openRemoteFile("test.txt") 会触发 FileNotFoundException ，代码会进入 catch 并打印：

remote file not found

这也是为什么它用 try/catch 包起来：远程文件通常是可选配置，缺失时不应该让目标 App 崩溃。

要复现这段代码，需要注意两点：

test.txt ，内容可以先写一行简单文本，例如：

hello from remote file

这样目标进程进入 onPackageReady() 后，预期日志就是：

remote file content: hello from remote file

如果文件内容是 JSON，可以在读取后继续用 JSONObject(text) 或 kotlinx serialization 解析；如果是规则列表，可以按行拆分：

val rules = text.lineSequence()
    .map { it.trim() }
    .filter { it.isNotEmpty() && !it.startsWith("#") }
    .toList()

这样模块 App 负责维护文件，Hook 逻辑只负责读取和应用规则，适合做 “无需重新编译模块就更新规则” 的场景。

六、新旧 Hook 写法对比

如果你以前写过传统 Xposed API，最熟悉的入口通常是：

public class HookEntry implements IXposedHookLoadPackage {
    @Override
    public void handleLoadPackage(XC_LoadPackage.LoadPackageParam lpparam) {
        if (!"com.demo.target".equals(lpparam.packageName)) return;

        XposedHelpers.findAndHookMethod(
            "com.demo.target.Account",
            lpparam.classLoader,
            "getVipLevel",
            new XC_MethodHook() {
                @Override
                protected void afterHookedMethod(MethodHookParam param) {
                    Object origin = param.getResult();
                    XposedBridge.log("origin vip level: " + origin);
                    param.setResult("pro");
                }
            }
        );
    }
}

这套写法的核心是：

  • 入口类实现 IXposedHookLoadPackage
  • 所有包加载后都进入 handleLoadPackage(...)
  • 通过 lpparam.packageName 过滤目标 App
  • 通过 lpparam.classLoader 找目标类
  • 用 XposedHelpers.findAndHookMethod(...) 安装 Hook
  • 在 beforeHookedMethod(...) 或 afterHookedMethod(...) 中读参数、改参数、读返回值、改返回值

现在 libxposed 102 API 的模板写法变成：

class HookEntry : XposedModule() {
    override fun onPackageReady(param: PackageReadyParam) {
        if (param.packageName != "com.demo.target") return
        if (!param.isFirstPackage) return

        val accountClass =
            Class.forName("com.demo.target.Account", true, param.classLoader)
        val getVipLevel = accountClass.getDeclaredMethod("getVipLevel")

        hook(getVipLevel).intercept { chain ->
            val origin = chain.proceed() as String
            log(Log.INFO, TAG, "origin vip level: $origin")
            "pro"
        }
    }
}

同样是把 Account.getVipLevel() 的返回值改成 pro ，新旧 API 的思路不一样。

1. before/after 回调 vs chain 责任链

传统写法把一次方法调用拆成 “前” 和 “后”：

new XC_MethodHook() {
    @Override
    protected void beforeHookedMethod(MethodHookParam param) {
        param.args[0] = "new-arg";
    }

    @Override
    protected void afterHookedMethod(MethodHookParam param) {
        param.setResult("new-result");
    }
}

它的执行模型是：

beforeHookedMethod
  ↓
原始方法
  ↓
afterHookedMethod

libxposed 新 API 更像一条调用链：

hook(method).intercept { chain ->
    val newArgs = arrayOf("new-arg")
    val origin = chain.proceed(newArgs)
    "new-result"
}

它的执行模型是：

进入 intercept
  ↓
你决定是否 chain.proceed()
  ↓
你决定用原参数还是新参数继续
  ↓
你决定最终返回原结果还是新结果

所以旧写法更像 “框架自动帮你执行原方法，你在前后插代码”；新写法更像 “原方法是否执行、执行几次、用什么参数执行，都由当前链节点决定”。

2. 改返回值的对比

传统 Xposed：

XposedHelpers.findAndHookMethod(
    "com.demo.target.Account",
    lpparam.classLoader,
    "getVipLevel",
    new XC_MethodHook() {
        @Override
        protected void afterHookedMethod(MethodHookParam param) {
            String origin = (String) param.getResult();
            XposedBridge.log("origin vip level: " + origin);
            param.setResult("pro");
        }
    }
);

libxposed：

val accountClass =
    Class.forName("com.demo.target.Account", true, param.classLoader)
val getVipLevel = accountClass.getDeclaredMethod("getVipLevel")

hook(getVipLevel).intercept { chain ->
    val origin = chain.proceed() as String
    log(Log.INFO, TAG, "origin vip level: $origin")
    "pro"
}

两段代码的预期效果完全一样：目标 App 原本拿到 free ，现在拿到 pro 。

关键差异是返回值设置方式：

  • 旧写法：调用 param.setResult("pro")
  • 新写法： intercept 的返回值就是新的方法返回值

3. 跳过原方法的对比

传统 Xposed：

protected void beforeHookedMethod(MethodHookParam param) {
    param.setResult("pro");
}

beforeHookedMethod 里直接 setResult ，原方法不会再执行。

libxposed：

hook(getVipLevel).intercept { _ ->
    "pro"
}

不调用 chain.proceed() ，就不会继续执行后续链路和原方法。

这点非常重要：在新 API 里， chain.proceed() 就是 “继续往下调用” 的开关。

4. 修改参数的对比

假设目标方法是：

fun login(name: String, password: String): Boolean

传统 Xposed 通常在 beforeHookedMethod 里改参数：

protected void beforeHookedMethod(MethodHookParam param) {
    param.args[0] = "admin";
    param.args[1] = "123456";
}

libxposed 里不直接改原数组也可以，而是传一组新参数继续调用：

hook(loginMethod).intercept { chain ->
    val newArgs = arrayOf("admin", "123456")
    chain.proceed(newArgs)
}

如果还想读取原始参数：

hook(loginMethod).intercept { chain ->
    val oldName = chain.args[0] as String
    log(Log.INFO, TAG, "old name: $oldName")
    chain.proceed(arrayOf("admin", "123456"))
}

5. 调用原方法的对比

传统 Xposed 里，原方法一般会自动执行；如果想手动调用原方法，常见写法是保存 Method 后调用 XposedBridge.invokeOriginalMethod(...) 。

libxposed 里有两个常用方式：

chain.proceed()

这会继续调用 Hook 链上的后续节点，最终可能到达原方法。

getInvoker(method)
    .setType(Invoker.Type.ORIGIN)
    .invoke(chain.thisObject)

这会绕过 Hook 链，直接调用原始方法。

简单理解：

  • chain.proceed() ：尊重后续 Hook 链
  • Invoker.Type.ORIGIN ：只要原方法

6. callMethod/callStaticMethod 的对比

传统 Xposed 里， callMethod 不是安装 Hook 的 API，而是 “我已经拿到一个对象了，现在想反射调用它的方法” 的辅助工具。

例如目标类：

class Account {
    fun getToken(prefix: String): String {
        return "$prefix-real-token"
    }

    companion object {
        @JvmStatic
        fun version(): String = "1.0"
    }
}

以前常见写法是：

Object token = XposedHelpers.callMethod(
    accountObject,
    "getToken",
    "Bearer"
);

Object version = XposedHelpers.callStaticMethod(
    accountClass,
    "version"
);

它做了几件事：

  • 根据方法名和参数自动找匹配方法
  • 帮你处理 setAccessible(true) 这类反射细节
  • 调用实例方法或静态方法
  • 返回调用结果

在 libxposed 新 API 里，没有必要把 callMethod 当成 Hook API 来迁移。它对应的是 “反射调用” 这件事，可以直接用 Java/Kotlin 反射：

val getToken = accountClass.getDeclaredMethod("getToken", String::class.java)
getToken.isAccessible = true
val token = getToken.invoke(accountObject, "Bearer") as String

val version = accountClass
    .getDeclaredMethod("version")
    .invoke(null) as String

如果要在 Hook 链语境里更精确地控制 “调用的是原方法，还是带 Hook 链的方法”，就用 getInvoker(...) ：

val token = getInvoker(getToken)
    .setType(Invoker.Type.ORIGIN)
    .invoke(accountObject, "Bearer") as String

这段等价于 “直接调原始 getToken ”，不会再次进入当前 Hook 链。适合在 intercept 里读取原始计算结果，避免递归。

如果希望主动调用时仍然经过完整 Hook 链，可以用 special 调用：

val token = getInvoker(getToken)
    .setType(Invoker.Type.Chain.FULL)
    .invokeSpecial(accountObject, "Bearer") as String

可以这样记：

  • XposedHelpers.callMethod(...) ：旧 API 的便捷反射调用
  • Method.invoke(...) ：新代码里最直接的普通反射调用
  • getInvoker(method).setType(Invoker.Type.ORIGIN) ：绕过 Hook，调用原始实现
  • getInvoker(method).setType(Invoker.Type.Chain.FULL) ：主动发起一次完整 Hook 链调用

所以， callMethod 迁移时要先问一句：你只是想普通反射调用，还是想控制 Hook 链？普通调用用 Method.invoke(...) 就够；涉及 Hook 链边界时，用 getInvoker(...) 更清楚。

7. 为什么新 API 更适合复杂 Hook

传统 API 写简单 Hook 很直观，但复杂场景里会遇到几个问题：

  • 多个 Hook 叠加时，执行顺序和返回值传递不够直观
  • 想 “用不同参数调用原方法多次” 时写法比较绕
  • 想绕过 Hook 直接调原方法时，需要更小心递归
  • 热重载后要自己保存并清理旧 Hook

libxposed 新 API 把这些动作显式化：

  • chain.proceed() 表示继续调用链
  • chain.proceed(newArgs) 表示换参数继续调用链
  • chain.proceedWith(newThis) 表示换 this 对象继续调用链
  • Invoker.Type.ORIGIN 表示绕过 Hook 调原方法
  • oldHookHandles 给热重载清理旧 Hook 留了统一入口

所以，新 API 不是简单换个函数名，而是把 Hook 从 “前后回调模型” 升级成 “可控调用链模型”。

七、Hook 示例代码解析

val exampleClass =
    Class.forName("io.github.libxposed.example.Example", true, param.classLoader)
val exampleMethod = exampleClass.getDeclaredMethod("method")
val exampleConstructor = exampleClass.getDeclaredConstructor()

如果目标进程里没有这个类， Class.forName(...) 会抛出 ClassNotFoundException ，后面的 Hook 就不会安装。复现时应该替换成目标 App 里真实存在的类和方法。

如果你要 Hook 目标类：

package com.demo.target

class UserManager {
    fun getToken(): String = "real-token"
}

就应改成：

val exampleClass =
    Class.forName("com.demo.target.UserManager", true, param.classLoader)
val exampleMethod = exampleClass.getDeclaredMethod("getToken")

1. intercept：拦截方法调用

第一段 Hook：

hook(exampleMethod).intercept { chain ->
    log(Log.INFO, TAG, "call the following chains with the same args")
    var result = chain.proceed() as String

    log(Log.INFO, TAG, "call the following chains with different args")
    val old0 = chain.args[0] as String
    val new1 = Any()
    val newArgs = arrayOf(old0, new1)
    result += chain.proceed(newArgs) as String

    log(Log.INFO, TAG, "call the following chains with different this object")
    val newThis = Any()
    result += chain.proceedWith(newThis) as String
    result += chain.proceedWith(newThis, newArgs) as String

    log(Log.INFO, TAG, "call the raw method")
    result += getInvoker(exampleMethod).setType(Invoker.Type.ORIGIN)
        .invoke(chain.thisObject) as String

    log(Log.INFO, TAG, "returned value will pass to higher priority chains")
    result
}

intercept 可以理解成 “把原方法调用包成一条链”。进入回调时，你拿到的是 chain ，它包含：

  • chain.args ：本次调用参数
  • chain.thisObject ：实例方法的 this 对象
  • chain.proceed() ：继续调用后续 Hook 或原方法
  • chain.proceed(newArgs) ：换一组参数继续调用
  • chain.proceedWith(newThis) ：换一个 this 对象继续调用
  • chain.proceedWith(newThis, newArgs) ：同时替换 this 和参数

这和传统 beforeHookedMethod/afterHookedMethod 的思路不一样。传统 API 更像 “方法前后插桩”，而这里更像 “责任链”：你决定是否继续往下走，继续走时用什么参数、什么对象。

不过这段模板代码有一个复现注意点：它访问了 chain.args[0] ，还拼接了多个 String 返回值。因此被 Hook 的示例方法至少要满足：

  • 有第一个参数，并且第一个参数是 String
  • 返回值能转成 String
  • proceed(newArgs) 时参数数量和类型要能匹配目标方法

如果 Hook 的是真实无参方法，例如 getToken(): String ，就不能照抄 chain.args[0] 和 newArgs ，应该简化成：

hook(exampleMethod).intercept { chain ->
    val origin = chain.proceed() as String
    log(Log.INFO, TAG, "origin token: $origin")
    "hooked-$origin"
}

这段代码的预期效果是：目标 App 调用 getToken() 时，原始返回值会被读出并拼上 hooked- 前缀，调用方最终拿到的是修改后的字符串。

2. 多个 Hook 的链式关系

安装第二个 Hook：

hook(exampleMethod).intercept { chain ->
    chain.proceed()
}

这说明同一个方法可以有多条拦截器。每个 intercept 都是 Hook 链上的一个节点。

当方法被调用时，执行顺序大致是：

调用 exampleMethod
  ↓
进入第一个/高优先级 Hook 节点
  ↓
chain.proceed()
  ↓
进入下一个 Hook 节点
  ↓
chain.proceed()
  ↓
最终进入原始方法
  ↓
返回值沿 Hook 链向上返回

如果某个节点不调用 chain.proceed() ，原始方法和后续 Hook 就不会执行。这一点和传统 Xposed 中 param.setResult(...) 跳过原方法类似。

3. 构造函数 Hook、优先级和异常模式

Hook 无参构造函数：

hook(exampleConstructor)
    .setPriority(PRIORITY_HIGHEST)
    .setExceptionMode(ExceptionMode.PASSTHROUGH)
    .intercept { _ ->
        log(
            Log.INFO,
            TAG,
            "thrown exception will be propagated to upper interceptors or the caller"
        )
        throw RuntimeException("constructor hook exception")
    }

这里有两个配置点。

setPriority(PRIORITY_HIGHEST) 表示这个 Hook 优先级最高。优先级决定多个 Hook 节点之间谁先执行。

setExceptionMode(ExceptionMode.PASSTHROUGH) 表示 Hook 回调中抛出的异常会继续向上传递，可能传给上层拦截器或原始调用方。

当前示例主动抛出：

throw RuntimeException("constructor hook exception")

所以只要目标代码触发这个构造函数，并且异常没有被上层捕获，就可能导致目标流程异常。真实 Hook 时不要随便这样写；这段主要是演示异常模式。

八、Invoker：主动调用原方法或指定 Hook 链

HookEntry.kt 末尾演示了 getInvoker(...) ：

getInvoker(exampleMethod).setType(Invoker.Type.ORIGIN).invoke(Any())
getInvoker(exampleMethod).setType(Invoker.Type.Chain(-50)).invokeSpecial(Any())
getInvoker(exampleConstructor).setType(Invoker.Type.ORIGIN).newInstance()
getInvoker(exampleConstructor).setType(Invoker.Type.Chain.FULL)
    .newInstanceSpecial(exampleClass)
getInvoker(exampleConstructor).newInstanceSpecial(exampleClass)

Invoker 的作用是 “主动调用一个方法或构造函数”，并且可以选择从哪个层级调用。

1. ORIGIN：绕过 Hook 调原始方法

getInvoker(exampleMethod)
    .setType(Invoker.Type.ORIGIN)
    .invoke(chain.thisObject)

Invoker.Type.ORIGIN 表示直接调用原始方法，不走 Hook 链。常见用途是：

  • 在 Hook 内部拿原始返回值
  • 避免递归调用自己安装的 Hook
  • 对比 Hook 前后的行为

如果在 intercept 中直接反射调用同一个方法，很容易再次进入 Hook，造成递归。用 ORIGIN 可以明确告诉框架：“我要原方法，不要 Hook 后的方法”。

2. Chain：从指定优先级链路继续调用

getInvoker(exampleMethod)
    .setType(Invoker.Type.Chain(-50))
    .invokeSpecial(Any())

Invoker.Type.Chain(-50) 表示从某个 Hook 链位置继续执行。它适合高级场景，比如多个模块或多个 Hook 节点协作时，想跳过一部分高优先级逻辑，从中间继续调用。

大多数场景只需要：

  • chain.proceed() 调后续链路
  • Invoker.Type.ORIGIN 调原始方法

3. 构造函数 Invoker

getInvoker(exampleConstructor)
    .setType(Invoker.Type.ORIGIN)
    .newInstance()

这表示用原始构造函数创建实例。

getInvoker(exampleConstructor)
    .setType(Invoker.Type.Chain.FULL)
    .newInstanceSpecial(exampleClass)

这表示创建实例时走完整 Hook 链。最后一行：

getInvoker(exampleConstructor).newInstanceSpecial(exampleClass)

和上一行含义接近，默认就是完整 Hook 链。

九、热重载流程

模板声明了：

autoHotReload=true

所以 HookEntry.kt 实现了两个热重载回调。

1. onHotReloading：旧模块准备卸载

代码：

override fun onHotReloading(param: HotReloadingParam): Boolean {
    log(Log.INFO, TAG, "onHotReloading")
    param.setSavedInstanceState("Hello from last generation")
    return true
}

它做了两件事：

  • 打印 onHotReloading
  • 保存一段状态： Hello from last generation

返回 true 表示允许热重载继续。

2. onHotReloaded：新模块完成加载

代码：

override fun onHotReloaded(param: HotReloadedParam) {
    log(
        Log.INFO,
        TAG,
        "onHotReloaded: ${param.processName}, ${param.oldHookHandles.size} old hooks"
    )
    log(Log.INFO, TAG, "savedInstanceState: " + param.savedInstanceState)
    param.oldHookHandles.forEach { it.unhook() }
}

这个回调可以拿到：

  • 当前进程名
  • 旧 Hook 句柄数量
  • 上一代模块保存的状态

最关键的是：

param.oldHookHandles.forEach { it.unhook() }

热重载后，如果旧 Hook 不卸载，可能出现同一个方法被新旧两代模块重复拦截的问题。模板主动遍历旧 Hook 句柄并 unhook() ，这是正确的清理动作。

预期效果是模块更新后 Logcat 能看到：

0X->: onHotReloading
0X->: onHotReloaded: com.example.challenge, 3 old hooks
0X->: savedInstanceState: Hello from last generation

旧 Hook 数量取决于实际安装过多少 Hook。

十、普通 Activity 与 JNI 示例

除了模块入口，模板也是一个可打开的普通 Android 应用。

1. AndroidManifest

文件路径：

app/src/main/AndroidManifest.xml

入口 Activity：

<activity
    android:name=".MainActivity"
    android:exported="true">
    <intent-filter>
        <action android:name="android.intent.action.MAIN" />
        <category android:name="android.intent.category.LAUNCHER" />
    </intent-filter>
</activity>

所以安装 APK 后，桌面会出现模块应用图标。打开它走的是普通 App 流程，不代表模块已经在目标进程中生效。

2. MainActivity 加载 native 库

文件路径：

app/src/main/java/com/lsposedtemplate/MainActivity.kt

关键代码：

external fun stringFromJNI(): String

companion object {
    init {
        System.loadLibrary("lsposedtemplate")
    }
}

System.loadLibrary("lsposedtemplate") 会加载由 CMake 编译出来的 liblsposedtemplate.so 。

页面创建时：

binding.sampleText.text = stringFromJNI()

它调用 native 方法，把返回值显示到界面上的 TextView。

3. native-lib.cpp 返回字符串

文件路径：

app/src/main/cpp/native-lib.cpp

代码：

extern "C" JNIEXPORT jstring JNICALL
Java_com_lsposedtemplate_MainActivity_stringFromJNI(
        JNIEnv* env,
        jobject /* this */) {
    std::string hello = "Hello from C++";
    return env->NewStringUTF(hello.c_str());
}

JNI 函数名对应关系是：

Java_包名_类名_方法名

所以：

com.lsposedtemplate.MainActivity.stringFromJNI()

对应：

Java_com_lsposedtemplate_MainActivity_stringFromJNI

预期效果：打开模块自己的 App，屏幕中央显示：

Hello from C++

再次强调：这只是普通 JNI 示例，不是当前模板的 LSPosed Native 入口。

十一、常见问题

1. 看不到 onModuleLoaded 日志

优先检查：

  • APK 是否安装成功
  • LSPosed 管理器里是否启用模块
  • 目标 App 是否在作用域内
  • 目标 App 是否已经强制停止并重启
  • META-INF/xposed/java_init.list 是否存在于 APK 中
  • java_init.list 里的类名是否等于 com.lsposedtemplate.HookEntry

2. 报 ClassNotFoundException

这通常不是框架问题，而是目标类名不对，或者类还没被目标 App 的 classLoader 加载到。

处理方式：

  • 确认类名是完整包名
  • 确认使用的是 param.classLoader
  • 确认目标 APK 版本和你分析的 APK 版本一致
  • 对加固、插件化、动态 dex 场景，需要等真实业务 dex 加载后再 Hook

3. Hook 被重复执行

先确认是否漏掉了：

if (!param.isFirstPackage) return

然后确认热重载时是否清理旧 Hook：

param.oldHookHandles.forEach { it.unhook() }

多进程应用还要检查当前进程名。模板在 onModuleLoaded() 中打印了 param.processName ，可以先根据日志判断 Hook 到了哪些进程。

4. 打开模块 App 只有 Hello from C++

这是正常的。 Hello from C++ 来自 MainActivity.stringFromJNI() ，说明普通 JNI 示例正常。

它不能证明 LSPosed 模块已经在目标进程生效。模块是否生效要看目标进程里的 0X-> 生命周期日志。

总结

libxposed 102 API 模块的最小骨架：

  • module.prop 决定模块能力、API 版本、静态作用域和热重载
  • java_init.list 决定 Java/Kotlin 入口类
  • scope.list 提供默认目标包
  • HookEntry.kt 通过 XposedModule 生命周期接入目标进程
  • onPackageReady() 是当前模板中最适合安装应用 Hook 的位置
  • hook(...).intercept { chain -> ... } 是新 API 的核心拦截方式
  • getInvoker(...).setType(Invoker.Type.ORIGIN) 可以主动调用原始方法，避免递归进入 Hook
  • onHotReloaded() 中清理旧 Hook 句柄，可以避免热重载后重复拦截
