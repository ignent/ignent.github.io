ELF 文件格式解析

ZIP2026/6/19...大约 23 分钟XposedELFNative逆向工程文件格式

一、ELF 解决的是地址与装载问题

ELF（Executable and Linkable Format）是 Linux、Android Native 层、共享库和核心转储文件常见的二进制文件格式。理解 ELF 时，最先要抓住的是下面几个概念：

概念白话解释
文件偏移数据在文件里的位置，类似 “第几页第几行”
虚拟地址程序运行后，数据或代码在进程内存里的地址
Section给编译器、链接器、逆向工具看的逻辑分区
Segment给内核加载器看的内存映射分区
符号函数名、变量名、外部函数名等 “名字”
重定位链接器或动态链接器把占位地址补成真实地址的过程

如果只记一句话：

ELF 文件记录了：哪些数据在哪里、哪些代码要加载到内存哪里、哪些函数地址还需要后面补上。

做 Native Hook、so 分析、符号定位、偏移换算时，真正反复遇到的也是这些问题：

  1. 这个文件是什么类型，能不能执行？
  2. 某个函数或字符串在文件里的位置在哪里？
  3. 文件加载到内存后，它会变成什么地址？
  4. 外部函数，例如 printf 、 strcmp 、 RegisterNatives ，最终是怎么找到真实实现的？

本文会用一个最小 C 程序说明 ELF 的结构，并结合关键指令解释字符串引用、参数传递和外部函数调用是如何完成的。

1.1 示例程序

示例程序只有一件事：输出一行字符串。

int main() {
    printf("Hello, YRX!");
    return 0;
}

从源代码到可执行文件，中间会经过两个重要阶段：

两个文件的区别如下：

文件类型状态重点
main.oET_REL 可重定位目标文件还不能直接运行保存代码、字符串、符号、待修补地址
main.outET_EXEC 可执行文件可以运行已分配内存地址，带有动态链接信息

把它理解成装修房子也可以：

  1. main.o 像装修材料清单：有门、窗、灯，但还没确定装到哪面墙。
  2. 链接器像施工队：把材料放到具体位置，顺便标记哪些东西要从外部采购。
  3. main.out 像施工完成的房子：每个房间、开关、线路都有了明确位置。
  4. 动态链接器像入住前的接线员：把外部依赖，例如 libc 的 printf ，接到真实位置。

二、ELF 的两张地图：Section 和 Segment

ELF 文件里同时存在两种 “地图”。

视角单位谁主要使用关心什么
链接视图Section编译器、链接器、逆向工具代码在哪里、字符串在哪里、符号表在哪里
执行视图Segment内核、动态链接器哪些内容要映射进内存，权限是什么

2.1 Section：给工具看的逻辑分区

Section 可以理解成文件里的文件夹：

Section常见内容读者需要知道的含义
.text机器码函数代码通常在这里
.rodata只读数据字符串常量通常在这里
.symtab静态符号表函数名、变量名、未解析符号
.strtab字符串表给 .symtab 提供名字文本
.dynsym动态符号表运行时还需要动态链接器处理的符号
.dynstr动态字符串表给 .dynsym 提供名字文本
.rela.text代码相关重定位表告诉链接器代码里哪些地址还没填
.rela.pltPLT 相关重定位表告诉动态链接器外部函数调用要补哪里
.got 、 .got.plt地址表外部函数或全局变量的运行时地址入口
.dynamic动态链接配置依赖库、重定位表、动态符号表位置

逆向工具常用 Section，因为它回答的是 “我想找某类东西，它在文件哪一块”。

2.2 Segment：给系统加载器看的搬运箱

程序运行时，内核不会按 .text 、 .rodata 一个个 Section 去搬。它主要看 Program Header 里的 Segment。

Segment 可以理解成装车用的大箱子。多个 Section 会被打包进同一个 Segment，然后一起映射进内存。

例如：

Segment 权限常见包含内容为什么这样分
r--ELF Header、动态符号、重定位信息只读元数据，不应该被修改
r-x.text 、 .plt代码需要可执行，但不应该可写
r--.rodata 、异常处理信息字符串常量只读
rw-.data 、 .bss 、 .got运行时需要修改的数据

这也是为什么 Hook 和漏洞利用里经常关心权限：代码段一般 r-x ，数据段一般 rw- ，可写又可执行的区域通常是不安全的。

2.3 文件结构总览

一个典型 ELF 大致长这样：

ELF File
+-----------------------------+
| ELF Header                  | 文件身份、入口地址、各种表的位置
+-----------------------------+
| Program Header Table        | 执行视图：Segment 列表
+-----------------------------+
| Sections                    | 代码、字符串、符号表、重定位表等内容
+-----------------------------+
| Section Header Table        | 链接视图：Section 列表
+-----------------------------+

如果把 ELF Header 看成目录页，它最重要的作用是告诉工具：

  1. Program Header Table 在哪里。
  2. Section Header Table 在哪里。
  3. 程序入口地址在哪里。
  4. 这个文件是 32 位还是 64 位，是小端还是大端，目标架构是什么。

三、ELF Header：先确认文件身份

两个示例文件的前 16 字节都以 ELF 魔数开头：

7f 45 4c 46 02 01 01 00 ...

字段含义如下：

字段值说明
0x7f 45 4c 46\x7fELFELF 魔数，表示这是 ELF 文件
EI_CLASS0x0264 位 ELF
EI_DATA0x01小端序
e_machine0x3ex86-64 架构

3.1 main.o 的 Header 特征

字段值说明
e_typeET_REL可重定位目标文件
e_entry0x0还没有最终入口地址
e_phoff0x0没有 Program Header
e_shoff0x260Section Header Table 位于文件偏移 0x260
e_shnum14共 14 个 Section Header

这里最重要的是： main.o 还不是一个能直接运行的程序，所以它没有真正的入口地址，也没有 Program Header。

3.2 main.out 的 Header 特征

字段值说明
e_typeET_EXEC可执行文件
e_entry0x401050程序入口地址
e_phoff0x40Program Header Table 紧跟 ELF Header
e_shoff0x3640Section Header Table 位于文件尾部附近
e_phnum13共 13 个 Program Header
e_shnum31共 31 个 Section Header

这里最重要的是： main.out 已经可以运行，所以它有程序入口 0x401050 ，也有 Program Header 来指导系统如何加载。

四、 main.o ：链接前的半成品

main.o 是编译出来的目标文件。它已经有代码和字符串，但还不知道最终要被放到内存的哪个地址。

4.1 main.o 里有什么

Section大小作用
.text0x23main 函数的机器码
.rela.text0x30.text 里需要链接器修补的位置
.rodata0x0c字符串常量 Hello, YRX!
.eh_frame0x38栈展开和异常处理元数据
.rela.eh_frame0x18.eh_frame 的重定位信息
.symtab0x90静态符号表
.strtab0x14符号名称字符串表
.shstrtab0x74Section 名称字符串表

从这些 Section 可以推断出：

  1. 程序里有一段代码，放在 .text 。
  2. 程序里有一个字符串，放在 .rodata 。
  3. 程序里有一些名字，放在 .symtab 和 .strtab 。
  4. 程序里有待修补地址，放在 .rela.text 。

4.2 符号表告诉我们：谁已经有了，谁还缺着

main.o 的符号表里能看到两条关键信息：

0000000000000000 g F .text  0000000000000023 main
0000000000000000     *UND*  0000000000000000 printf

把它翻译成人话：

符号状态含义
main已定义当前文件里已经有 main 函数代码
printfUND 未定义当前文件只知道要调用 printf ，但不知道它在哪里

printf 未定义并不是错误。因为 printf 本来就在 libc 里，链接器后面会把这个外部函数接上。

4.3 重定位表告诉我们：哪里还要补地址

分析 main.o 时，除了 .text 里的机器码，还要重点看重定位表。

重定位表可以理解成一张 “待办清单”：

重定位位置目标白话解释
0x0b.rodata - 0x4这里将来要填入字符串常量的位置
0x18printf - 0x4这里将来要填入 printf 调用入口的位置
0x20 in .eh_frame.text栈展开元数据需要引用代码段

也就是说， main.o 里至少有两个问题还没解决：

  1. "Hello, YRX!" 最终会在内存的哪个地址？
  2. printf 最终要跳到哪里？

链接器的工作就是回答这两个问题。

4.4 .text 中的指令与占位地址

main.o 的 .text 里已经有 main 函数的机器码：

0000000000000000 <main>:
   0: f3 0f 1e fa          endbr64
   4: 55                   pushq  %rbp
   5: 48 89 e5             movq   %rsp, %rbp
   8: 48 8d 05 00 00 00 00 leaq   0x0(%rip), %rax
   f: 48 89 c7             movq   %rax, %rdi
  12: b8 00 00 00 00       movl   $0x0, %eax
  17: e8 00 00 00 00       callq  0x1c
  1c: b8 00 00 00 00       movl   $0x0, %eax
  21: 5d                   popq   %rbp
  22: c3                   retq

这段代码对应 main 的函数流程：

指令作用
endbr64Intel CET 相关的间接跳转保护标记，对示例业务逻辑没有影响
pushq %rbp保存调用者的栈基址
movq %rsp, %rbp建立当前函数的栈帧
leaq 0x0(%rip), %rax计算字符串地址，并把结果放入 rax
movq %rax, %rdi把字符串地址放入 rdi ，作为第 1 个函数参数
movl $0x0, %eax调用变参函数前清空 eax ，表示没有用 XMM 寄存器传浮点参数
callq 0x1c调用函数；这里的目标地址还是占位值
movl $0x0, %eax设置 main 的返回值为 0
popq %rbp恢复调用者的栈基址
retq从 main 返回

其中有两处 00 00 00 00 是链接前的占位值：

指令位置占位字段重定位目标链接后的效果
0x8 的 leaq指令中的 4 字节位移.rodata - 0x4让 leaq 算出字符串常量地址
0x17 的 callq指令中的 4 字节相对偏移printf - 0x4让 callq 跳到 printf 的调用入口

leaq 0x0(%rip), %rax 使用 RIP 相对寻址。 rip 表示当前指令流的位置，链接器把占位位移修好后，这条指令就能算出 .rodata 中字符串的运行时地址。

callq 也使用相对偏移。它不是把完整的 64 位目标地址直接写进指令，而是写入 “从下一条指令到目标位置的距离”。所以重定位项里经常看到 -0x4 ：相对地址的计算基准在 4 字节立即数字段之后。

五、 main.out ：链接后的可执行文件

链接之后， main.out 已经具备执行视图。相比 main.o ，它多了很多运行时需要的东西：

  1. _start 、 _init 、 _fini 等启动和收尾代码。
  2. .interp ，指定动态链接器路径。
  3. .dynsym 、 .dynstr ，供动态链接器识别外部符号。
  4. .rela.dyn 、 .rela.plt ，供加载时或首次调用时修补地址。
  5. .plt 、 .plt.sec 、 .got 、 .got.plt ，支撑外部函数调用。
  6. .dynamic ，记录依赖库、动态符号表、重定位表等信息。

5.1 关键 Section 分布

Section虚拟地址大小作用
.interp0x4003180x1c动态链接器路径 /lib64/ld-linux-x86-64.so.2
.dynsym0x4003d00x60动态符号表
.dynstr0x4004300x4a动态符号字符串表
.rela.dyn0x4004b80x30普通动态重定位表
.rela.plt0x4004e80x18外部函数调用相关重定位表
.plt0x4010200x20外部函数跳板
.plt.sec0x4010400x10printf 调用入口
.text0x4010500x109_start 、运行时辅助函数、 main
.rodata0x4020000x10只读常量，字符串位于 0x402004
.dynamic0x403e080x1d0动态链接元数据
.got0x403fd80x10全局偏移表
.got.plt0x403fe80x20PLT 使用的 GOT 表项
.data0x4040080x10已初始化全局数据
.bss0x4040180x08未初始化全局数据，运行时清零

这张表已经足够解释大部分现象：

  1. 代码主要在 0x401050 附近。
  2. 字符串主要在 0x402000 附近。
  3. 动态链接相关数据在 .dynamic 、 .got 、 .got.plt 。
  4. printf 不是直接写死成 libc 地址，而是先走 .plt.sec 和 .got.plt 。

5.2 字符串的位置怎么变了

main.o 里的字符串内容是：

48 65 6c 6c 6f 2c 20 59 52 58 21 00

它对应：

Hello, YRX!\0

到了 main.out ， .rodata 变成：

01 00 02 00 48 65 6c 6c 6f 2c 20 59 52 58 21 00

前 4 字节属于 _IO_stdin_used ，真正的字符串从 0x402004 开始。

所以如果在调试器里查看：

x/s 0x402004

就能看到：

"Hello, YRX!"

5.3 printf 为什么不直接变成 libc 地址

很多初学者会期待链接器直接把 printf 改成 libc 里的真实地址。实际情况通常不是这样。

原因是：动态库的加载地址可能每次都不同。 libc.so.6 在运行时放到哪里，要等动态链接器加载后才知道。

因此可执行文件里通常会放一个中间层：

main -> printf@plt -> GOT 槽位 -> libc 里的 printf

可以这样理解：

名称白话解释
PLT外部函数跳板，代码先跳到这里
GOT地址表，里面保存最终要跳到的真实地址
.rela.plt告诉动态链接器哪个 GOT 槽位对应哪个外部函数
JUMP_SLOT外部函数调用使用的 GOT 槽位类型

本例里 printf 对应的动态重定位项是：

Offset类型符号作用
0x404000R_X86_64_JUMP_SLOTprintfprintf@plt 使用的 GOT 槽位

所以当追踪工具看到 0x401040 、 0x404000 、 printf@GLIBC_2.2.5 时，它们其实是在描述同一条外部函数调用链路的不同位置。

六、从 main.o 到 main.out ：链接器到底补了什么

可以把链接过程看成 “把未知地址填好”。

main.o 阶段main.out 阶段解释
.rodata 还没有最终虚拟地址字符串位于 0x402004链接器把只读数据放入只读 Segment
printf 是 UND 未定义符号调用 0x401040 <.plt.sec>链接器生成 PLT/GOT 调用链
main 在 .text 内偏移为 0x0main 位于 0x401136链接器给 .text 分配了虚拟地址
.text 里有占位值占位值被替换成相对地址程序运行时能找到字符串和函数

如果只看最终结果， main 里的关键动作是：

1. 找到字符串地址 0x402004
2. 把字符串作为第一个参数
3. 调用 printf 的 PLT 入口 0x401040
4. 返回 0

最终机器码对应的行为是：先得到字符串地址，再把它作为参数传给 printf ，最后返回 0 。

链接后， main.out 里对应的两条关键指令变成：

40113e: 48 8d 05 bf 0e 00 00  leaq 0xebf(%rip), %rax  # 0x402004
40114d: e8 ee fe ff ff        callq 0x401040 <.plt.sec>

leaq 0xebf(%rip), %rax 会用当前 rip 加上 0xebf ，得到字符串地址 0x402004 。 callq 0x401040 会跳到 printf 的 PLT 入口，由 PLT/GOT 继续完成到 libc 的间接调用。

完整的 main 调用过程可以整理为：

步骤指令运行时含义
计算字符串地址leaq 0xebf(%rip), %rax得到 0x402004
设置第 1 个参数movq %rax, %rdirdi = "Hello, YRX!" 的地址
准备变参调用movl $0x0, %eaxprintf 没有浮点变参
调用外部函数callq 0x401040进入 printf@plt
设置返回值movl $0x0, %eaxmain 返回 0

七、Program Header：程序如何进入内存

main.out 的 Program Header 描述了运行时的内存布局：

Segment文件偏移虚拟地址文件大小内存大小权限
PT_PHDR0x400x4000400x2d80x2d8r--
PT_INTERP0x3180x4003180x1c0x1cr--
PT_LOAD0x00x4000000x5000x500r--
PT_LOAD0x10000x4010000x1690x169r-x
PT_LOAD0x20000x4020000xec0xecr--

换成内存图更直观：

0x400000 - 0x400500  r--  ELF Header / PHDR / .interp / .dynsym / .rela.*
0x401000 - 0x401169  r-x  .init / .plt / .plt.sec / .text / .fini
0x402000 - 0x4020ec  r--  .rodata / .eh_frame_hdr / .eh_frame
0x403df8 - 0x404020  rw-  .init_array / .dynamic / .got / .got.plt / .data / .bss

读这张图时只要记住：

  1. r-x 区域通常是代码。
  2. r-- 区域通常是只读数据和元数据。
  3. rw- 区域通常是运行时会改的数据。
  4. .bss 不占文件内容，加载进内存后由内核清零。

最后一个 PT_LOAD 的 memsz 比 filesz 多 0x8 ，这正好对应 .bss 。也就是说，文件里不用真的存 8 个 0，系统加载时帮它准备好一块清零内存即可。

八、程序启动时发生了什么

main.out 的入口不是 main ，而是 ELF Header 里的 e_entry ：

e_entry = 0x401050

这个地址通常对应 _start 。它是 C 运行时的入口，负责把程序带到 main 。

因为系统启动的是 ELF 入口，C 运行时初始化完成后，才会调用用户写的 main 。

8.1 常见追踪地址怎么理解

如果用 GDB、perf、Frida、Dobby 或 LSPosed Native Hook 追踪这个程序，常见地址可以这样读：

地址或符号所属区域为什么会出现
0x401050 _start.textELF Header 的入口地址指向这里
0x403fd8.got_start 通过该 GOT 槽调用 __libc_start_main
0x401136 main.textlibc 初始化后回调用户代码
0x402004.rodatamain 使用的字符串常量
0x401040 .plt.sec.plt.secmain 先调用 printf 跳板
0x404000.got.pltprintf 的 GOT 槽位
printf@GLIBC_2.2.5libc动态链接器最终解析到的真实函数

典型调试命令如下：

b *0x401050       # 观察 _start
b *0x401136       # 观察 main
b *0x401040       # 观察 printf 的 PLT 入口
x/s 0x402004      # 查看字符串常量
x/gx 0x404000     # 查看 printf 的 GOT.plt 槽位

这些命令的重点不是背地址，而是知道地址来自哪里：

  1. 入口地址来自 ELF Header。
  2. 函数地址来自符号表或反汇编结果。
  3. 字符串地址来自 .rodata 。
  4. 外部函数槽位来自 .rela.plt 和 .got.plt 。

九、Android so 和 Native Hook 里为什么总说 “基址 + 偏移”

上面的 main.out 是 ET_EXEC ，示例地址固定在 0x400000 附近。但 Android 里的 .so 通常是共享库，类型多为 ET_DYN 。

共享库的特点是：每次运行时加载到哪里，不一定固定。

所以静态分析工具里看到的地址，通常不能直接拿去 Hook。需要换算：

运行时地址 = 模块基址 + 文件内偏移

例如：

信息示例含义
模块基址0x7a12000000从 /proc/self/maps 读取
静态偏移0x1234IDA、Ghidra、readelf 中分析得到
运行时地址0x7a12001234Hook 时真正使用的地址

这也是 Native Hook 代码经常先读取 /proc/self/maps 的原因：

先找到 libxxx.so 的加载基址，再加上目标函数偏移。

理解 ELF 后，再看这些概念会更自然：

Hook 术语ELF 里的对应关系
模块基址某个 ELF 被映射进进程内存的起点
偏移地址目标相对模块起点的位置
导出函数 Hook通过动态符号表找到函数
非导出函数 Hook通过静态分析偏移定位函数
GOT Hook修改 GOT 表项，让外部函数跳到替换实现
PLT Hook拦截外部函数跳板

十、ELF.bt 能帮我们看什么

ELF.bt 这类模板的作用，是把裸二进制文件翻译成结构化视图。它不会告诉你 “业务逻辑是什么”，但能告诉你 “这个地址属于什么结构”。

模板结构对应 ELF 结构分析价值
e_ident_tELF 标识校验魔数、位数、字节序、ABI
elf_headerELF Header定位入口地址、Program Header、Section Header
program_table_entry64_tProgram Header解析 PT_LOAD 、 PT_DYNAMIC 、 PT_INTERP 、 PT_GNU_RELRO
section_table_entry64_tSection Header解析节名、类型、虚拟地址、文件偏移、大小
Elf64_SymSymbol Table Entry解析 main 、 printf 、 _start 等符号
Elf64_Dyn_tDynamic Entry解析 NEEDED 、 PLTGOT 、 JMPREL 、 RELA 等动态链接字段

模板执行流程可以理解为：

分析 ELF 文件时，建议按下面顺序看：

  1. 先看 ELF Header：确认文件类型、架构、入口地址。
  2. 再看 Program Header：确认哪些区域会被加载进内存。
  3. 再看 Section Header：定位 .text 、 .rodata 、 .dynsym 、 .rela.plt 。
  4. 再看 Symbol Table：找函数名和未定义符号。
  5. 最后看 Relocation Table：确认哪些地址会被链接器或动态链接器修补。

先用结构表确定文件布局，再结合反汇编确认具体指令引用了哪些地址。

十二、性能、体积与安全建议

12.1 体积优化

针对这种小程序，体积主要来自 C 运行时、动态链接信息、符号表和调试辅助信息。

目标建议
移除符号表发布版本执行 strip main.out
减少未使用函数和数据编译加 -ffunction-sections -fdata-sections ，链接加 -Wl,--gc-sections
优化体积使用 -Os
避免引入复杂格式化逻辑常量字符串输出可用 puts 替代 printf
保留分析能力调试版本保留 -g ，发布版本再 strip

静态链接看似减少运行时依赖，但通常会显著增大文件体积，不适合追求小体积的普通命令行程序。

12.2 运行效率

这个样例程序没有复杂循环，也没有明显 CPU 热点。真正的运行时开销主要来自：

  1. 进程启动：内核装载 ELF、启动动态链接器。
  2. 动态链接：解析 .dynamic 、处理 .rela.dyn 和 .rela.plt 。
  3. 首次调用外部函数：如果启用 lazy binding，第一次进入 printf@plt 时需要解析真实 libc 地址。
  4. I/O 输出： printf 最终写标准输出，I/O 成本远高于本地几条指令。

如果追踪工具显示耗时集中在 ld-linux 、 __libc_start_main 、 printf 或系统调用附近，这是正常现象，并不代表 main 本身存在性能瓶颈。

12.3 安全与稳定性

场景建议
防止 GOT 被运行时篡改启用 RELRO： -Wl,-z,relro -Wl,-z,now
防止栈执行保持 PT_GNU_STACK 为 rw- ，不要开启可执行栈
提升栈溢出检测使用 -fstack-protector-strong
避免固定地址被利用使用 PIE 与 ASLR
便于崩溃定位调试版本保留符号表，配合 addr2line 或 gdb

十三、常见误区

13.1 printf 一直显示为未定义，是不是出错了

在目标文件阶段这是正常现象：

U printf

这表示当前文件需要 printf ，但 printf 由外部库提供。链接生成可执行文件后，它会通过 .dynsym 、 .rela.plt 、 .got.plt 与 libc 建立联系。

13.2 为什么程序入口不是 main

因为 C 程序启动前还要初始化运行时环境。系统先进入 ELF Header 指定的 _start ，再由 __libc_start_main 调用用户写的 main 。

13.3 为什么 Hook 地址在本机可用，换环境后失效

因为很多 Android so 或开启 PIE 的 Linux 程序会受 ASLR 影响。静态分析得到的地址通常只是偏移，运行时必须使用：

目标函数运行时地址 = /proc/self/maps 中的模块基址 + 静态分析得到的偏移

13.4 为什么追踪日志只看到 PLT，看不到 libc 真函数

因为程序先调用 printf@plt ，再通过 GOT 跳转到 libc。需要继续跟踪 0x404000 对应的 GOT 槽位，或直接 Hook libc 中解析后的 printf 地址。

13.5 为什么要同时看结构表和反汇编

结构表负责说明 “数据在哪里”，反汇编负责说明 “代码如何使用这些数据”。建议重点结合下面几类信息：

  1. ELF Header
  2. Program Header
  3. Section Header
  4. Symbol Table
  5. Relocation Table
  6. Dynamic Table

例如本例中， .rodata 给出字符串所在区域，重定位表指出 leaq 的位移需要修补，反汇编则展示 leaq 如何把字符串地址放进 rax ，再由 movq %rax, %rdi 传给 printf 。

总结

本例从 main.o 到 main.out 展示了 ELF 的核心机制：

  1. main.o 是链接前的半成品，以 Section 为中心，保存代码、字符串、符号和重定位请求。
  2. 链接器把 .text 、 .rodata 等 Section 分配到具体虚拟地址，并为 printf 生成 PLT/GOT 调用链。
  3. main.out 是可执行文件，以 Segment 为中心供内核装载， PT_LOAD 决定虚拟内存映射， PT_DYNAMIC 决定动态链接行为。
  4. 动态链接器在运行时继续处理 .dynamic 、 .rela.dyn 、 .rela.plt ，把外部函数接到真实地址。
  5. 在 Android Native Hook 中，常见的 “模块基址 + 偏移”“GOT/PLT Hook”“符号表恢复”“调用栈追踪”，都可以从 ELF 结构里找到来源。

读 ELF 的关键是建立地址和结构之间的对应关系：文件里有什么，运行时会搬到哪里，哪些地址已经确定，哪些地址需要后面修补。再结合关键指令，就能解释 Native Hook 里的函数地址、字符串地址、PLT/GOT 跳转和 “模块基址 + 偏移”。
