内存分段

以下对比 x86-64 Linux、AArch64 Linux、macOS arm64 三种环境里的 “内存分段”。

先把容易混在一起的三个概念拆开：

  1. CPU 分段机制：x86 历史上的段寄存器、段基址、段界限。到了 x86-64 long mode，普通用户程序基本使用 “平坦地址空间”， CS 、 DS 、 SS 这类段不再像 16/32 位时代那样划分内存。 FS / GS 仍有特殊用途，例如线程局部存储。
  2. 可执行文件里的 section/segment：汇编器和链接器把代码、只读数据、可写数据放到不同 section；加载器按更粗的 segment 把程序映射进进程地址空间。
  3. 进程运行时的虚拟内存区域：程序真正运行时，除了代码和数据，还会有栈、堆、共享库、动态链接器、匿名映射、内核提供的辅助映射等。

重点讲第 2 和第 3 点：汇编代码写进哪些段，链接后文件里长什么样，运行时又被操作系统映射成什么权限。

说明：这里的 AArch64 和 ARM64 指同一类 64 位 Arm 架构。Linux AArch64 使用 ELF；macOS arm64 使用 Mach-O。两者寄存器和基础指令相似，但文件格式、段名、链接方式、系统调用方式不同。

初学阶段可以这样记：

  • section 是给汇编器 / 链接器看的小盒子，例如 .text 、 .data 、 .bss 。
  • segment 是给加载器看的大盒子，加载器按权限把若干内容映射进虚拟内存。
  • 进程内存映射是运行后的结果，可以用 /proc/$pid/maps 或 vmmap 观察。

2. section 和 segment 到底差在哪

用一个很粗糙但好记的模型：

汇编源文件
  |
  |  汇编器 as / clang
  v
目标文件 .o
  |
  |  链接器 ld / clang
  v
可执行文件
  |
  |  内核加载器 + 动态链接器
  v
进程虚拟内存

在这个过程中：

  • .text 这类 section 主要服务于编译、汇编、链接、重定位和符号管理。
  • PT_LOAD 或 __TEXT 这类 segment 主要服务于程序加载。
  • .bss 这类未初始化数据在文件里通常只记录 “需要多少空间”，不会真的把一大段 0 写进文件；进程启动时由加载器映射并清零。

举例：

ELF 文件中：

section 视角：
  .text      代码
  .rodata    只读字符串
  .data      已初始化全局变量
  .bss       未初始化全局变量

segment 视角：
  LOAD r-x   代码等可执行内容
  LOAD r--   只读内容
  LOAD rw-   可写数据，通常也覆盖 .bss 运行时空间

macOS Mach-O 的命名方式更直接暴露 segment：

Mach-O 文件中：

segment __TEXT
  section __text       机器指令
  section __const      只读常量
  section __cstring    C 字符串常量

segment __DATA
  section __data       已初始化可写数据
  section __bss        未初始化可写数据

segment __LINKEDIT     符号表、重定位、动态链接信息等
segment __PAGEZERO     低地址保护区，防止空指针附近地址被正常访问

注意：不同链接器版本、发行版默认选项、是否 PIE、是否动态链接，都会影响最终 segment 数量和地址。观察时重点看 名字、权限、大小关系，不要死记某个固定地址。

3. 进程虚拟内存不是只有 .text/.data/.bss

一个运行中的程序通常包含：

区域来源常见权限作用
代码区可执行文件 .text 或 __TEXT,__text读 + 执行存放机器指令
只读数据.rodata 或 __TEXT,__const读字符串常量、查表数据
可写数据.data 或 __DATA,__data读 + 写有初始值的全局变量
BSS.bss 或 __DATA,__bss读 + 写没有显式初始值的全局变量，启动时清零
堆brk / mmap 或 malloc 分配器读 + 写动态分配内存
栈内核创建读 + 写函数调用、局部变量、返回地址
共享库动态链接器映射各自不同libc/libSystem 等库代码和数据
辅助映射内核或动态链接器创建各自不同vDSO、guard page、dyld 信息等

所以，“代码段、数据段、栈、堆” 是学习时的简化模型。真正看 /proc/$pid/maps 或 vmmap 时，输出中可能看到更多行。

4. Linux x86-64：ELF 段和运行时映射

下面的程序包含四类典型 section：

  • .text ：机器指令。
  • .rodata ：只读提示字符串。
  • .data ：有初始值的全局变量 counter 。
  • .bss ：未初始化缓冲区 scratch 。

程序会先改写 .data 和 .bss ，再打印一行提示，然后阻塞在 read(0, scratch, 1) 。这样可以在另一个终端查看该程序的进程内存映射，按 Enter 后程序退出。

文件名： seg-x86.s

.section .rodata
msg:
    .ascii "x86-64 Linux ELF segments are mapped. Press Enter to exit.\n"
msg_len = . - msg

.section .data
.balign 8
counter:
    .quad 41                         # 8 字节全局变量，文件中带有初始值 41

.section .bss
.balign 16
scratch:
    .space 4096                      # 预留 4096 字节，文件中不保存这 4096 个 0

.section .text
.global _start
_start:
    # 1. 修改 .data 中的 counter。
    #    counter 在可写数据段里，所以运行时权限应该允许写入。
    mov counter(%rip), %rax          # rax = counter 的当前值，也就是 41
    add $1, %rax                     # rax = rax + 1，变成 42
    mov %rax, counter(%rip)          # counter = 42，写回 .data

    # 2. 修改 .bss 中的 scratch。
    #    .bss 启动时会被清零，这里把第一个字节写成 ASCII 'A'。
    movb $65, scratch(%rip)          # scratch[0] = 65，也就是字符 'A'

    # 3. write(1, msg, msg_len)
    #    Linux x86-64 系统调用约定：
    #    rax = 系统调用号
    #    rdi = 第 1 个参数
    #    rsi = 第 2 个参数
    #    rdx = 第 3 个参数
    mov $1, %rax                     # rax = 1，write 系统调用号
    mov $1, %rdi                     # rdi = 1，标准输出 stdout
    lea msg(%rip), %rsi              # rsi = msg 地址，不是 msg 里的内容
    mov $msg_len, %rdx               # rdx = 要写出的字节数
    syscall                          # 进入内核执行 write

    # 4. read(0, scratch, 1)
    #    这里故意从标准输入读 1 字节，让程序停住。
    #    可以在另一个终端查看 /proc/$pid/maps。
    mov $0, %rax                     # rax = 0，read 系统调用号
    mov $0, %rdi                     # rdi = 0，标准输入 stdin
    lea scratch(%rip), %rsi          # rsi = scratch 缓冲区地址
    mov $1, %rdx                     # rdx = 最多读取 1 字节
    syscall                          # 等待输入；按 Enter 后会继续

    # 5. exit(0)
    mov $60, %rax                    # rax = 60，exit 系统调用号
    xor %rdi, %rdi                   # rdi = 0，退出码为 0
    syscall

编译运行：

as --64 seg-x86.s -o seg-x86.o
ld seg-x86.o -o seg-x86
./seg-x86

第一个终端会显示：

x86-64 Linux ELF segments are mapped. Press Enter to exit.

先不要按 Enter。打开第二个终端查看进程映射：

pid=$(pgrep -n seg-x86)
cat /proc/$pid/maps | sed -n '1,30p'

输出可能出现类似这样的行，地址会因系统而异：

00400000-00401000 r--p 00000000 ... /path/to/seg-x86
00401000-00402000 r-xp 00001000 ... /path/to/seg-x86
00402000-00403000 r--p 00002000 ... /path/to/seg-x86
00403000-00404000 rw-p 00003000 ... /path/to/seg-x86
...
7ffd...-7ffd... rw-p 00000000 ... [stack]

权限字段可以这样读：

字符含义
r可读
w可写
x可执行
pprivate，私有映射，写入时通常触发 copy-on-write
sshared，共享映射

重点观察：

  • 有一段 r-xp ，这是可执行代码所在映射。
  • 有一段 rw-p ，这是可写数据和 .bss 所在映射。
  • [stack] 不是来自 .text/.data/.bss ，这是内核为进程创建的栈。

再看 ELF 文件手写 section 和 segment：

readelf -S seg-x86 | egrep 'Name|\.text|\.rodata|\.data|\.bss'
readelf -l seg-x86

readelf -S 看 section，适合回答 “代码和数据分别叫什么名字”。 readelf -l 看 program header/segment，适合回答 “加载器按什么权限把文件映射进内存”。

还可以看每个 section 的大小：

objdump -h seg-x86

5. Linux AArch64：同样是 ELF，指令和系统调用不同

Linux AArch64 和 Linux x86-64 的可执行文件格式都是 ELF，所以 .text 、 .rodata 、 .data 、 .bss 这些名字很像。差异主要在：

  • 指令集不同：x86-64 用 mov 、 syscall ；AArch64 用 ldr/str 、 svc #0 。
  • 系统调用约定不同：Linux AArch64 用 x8 放系统调用号，用 x0 、 x1 、 x2 等放参数。
  • 取全局符号地址的写法不同：AArch64 常用 adrp + add 组合，配合 :lo12: 重定位。

文件名： seg-arm64.s

.section .rodata
msg:
    .ascii "AArch64 Linux ELF segments are mapped. Press Enter to exit.\n"
msg_len = . - msg

.section .data
.balign 8
counter:
    .quad 41                         // 8 字节全局变量，文件中带有初始值 41

.section .bss
.balign 16
scratch:
    .space 4096                      // 预留 4096 字节，加载到内存后清零

.section .text
.global _start
_start:
    // 1. 修改 .data 中的 counter。
    //    adrp 先取 counter 所在页的地址，add 再加页内偏移。
    //    这种写法比 adr 更适合全局符号，因为目标可以离当前指令更远。
    adrp x9, counter                 // x9 = counter 所在 4KB 页的页地址
    add x9, x9, :lo12:counter        // x9 = x9 + counter 的页内偏移
    ldr x10, [x9]                    // x10 = 内存[x9]，读取 counter
    add x10, x10, #1                 // x10 = x10 + 1，变成 42
    str x10, [x9]                    // 内存[x9] = x10，写回 counter

    // 2. 修改 .bss 中的 scratch。
    adrp x9, scratch                 // x9 = scratch 所在页的页地址
    add x9, x9, :lo12:scratch        // x9 = scratch 的完整地址
    mov w10, #65                     // w10 = 65，也就是 ASCII 'A'
    strb w10, [x9]                   // scratch[0] = 'A'，只写 1 字节

    // 3. write(1, msg, msg_len)
    //    Linux AArch64 系统调用约定：
    //    x8 = 系统调用号
    //    x0 = 第 1 个参数
    //    x1 = 第 2 个参数
    //    x2 = 第 3 个参数
    mov x8, #64                      // x8 = 64，write 系统调用号
    mov x0, #1                       // x0 = 1，标准输出 stdout
    adrp x1, msg                     // x1 = msg 所在页的页地址
    add x1, x1, :lo12:msg            // x1 = msg 的完整地址
    mov x2, #msg_len                 // x2 = 要写出的字节数
    svc #0                           // 进入内核执行 write

    // 4. read(0, scratch, 1)
    //    阻塞等待输入，方便另一个终端观察 /proc/$pid/maps。
    mov x8, #63                      // x8 = 63，read 系统调用号
    mov x0, #0                       // x0 = 0，标准输入 stdin
    adrp x1, scratch                 // x1 = scratch 所在页的页地址
    add x1, x1, :lo12:scratch        // x1 = scratch 的完整地址
    mov x2, #1                       // x2 = 最多读取 1 字节
    svc #0                           // 等待输入；按 Enter 后继续

    // 5. exit(0)
    mov x8, #93                      // x8 = 93，exit 系统调用号
    mov x0, #0                       // x0 = 0，退出码为 0
    svc #0

在 ARM64 Linux 上编译运行：

as seg-arm64.s -o seg-arm64.o
ld seg-arm64.o -o seg-arm64
./seg-arm64

如果是在真正的 ARM64 Linux 机器上运行，另一个终端可以这样看：

pid=$(pgrep -n seg-arm64)
cat /proc/$pid/maps | sed -n '1,30p'
readelf -S seg-arm64 | egrep 'Name|\.text|\.rodata|\.data|\.bss'
readelf -l seg-arm64

如果是在 x86-64 Linux 上用交叉工具链查看 AArch64 文件，用交叉版工具：

aarch64-linux-gnu-readelf -S seg-arm64 | egrep 'Name|\.text|\.rodata|\.data|\.bss'
aarch64-linux-gnu-readelf -l seg-arm64
aarch64-linux-gnu-objdump -h seg-arm64

可以发现：文件格式和 section/segment 思路与 x86-64 Linux 基本一致，变的是机器指令、寄存器、系统调用号和调用指令。

6. macOS arm64：Mach-O 的 segment 名字更显眼

macOS arm64 使用 Mach-O，不是 ELF。Mach-O 的段名经常写成两个部分：

.section __TEXT,__const

这里：

  • __TEXT 是 Mach-O segment 名。
  • __const 是这个 segment 里的 section 名。

初学者可以先记住常见组合：

写法含义
__TEXT,__text代码
__TEXT,__const只读常量
__TEXT,__cstringC 字符串常量
__DATA,__data已初始化可写数据
__DATA,__bss未初始化可写数据
__LINKEDIT链接编辑信息，通常由链接器生成
__PAGEZERO低地址不可访问保护区

下面的程序和前两个 Linux 版本做同样的事：修改可写数据，写 .bss ，打印提示，然后调用 _read 等待输入。

文件名： seg-mac.s

.section __TEXT,__const
msg:
    .ascii "macOS arm64 Mach-O segments are mapped. Press Enter to exit.\n"
msg_len = . - msg

.data
.p2align 3
counter:
    .quad 41                         // 8 字节全局变量，放进 __DATA,__data

// .zerofill 用来声明 Mach-O 的零填充 section。
// 参数含义：
//   __DATA      segment 名
//   __bss       section 名
//   scratch     符号名
//   4096        预留字节数
//   4           对齐指数，2^4 = 16 字节对齐
.zerofill __DATA,__bss,scratch,4096,4

.section __TEXT,__text,regular,pure_instructions
.globl _main
.p2align 2
_main:
    // macOS arm64 通常从 C 运行时调用 _main。
    // 因为下面会 bl _write 和 bl _read，x30 返回地址会被覆盖，
    // 所以先把 x29/x30 保存到栈上。
    stp x29, x30, [sp, #-16]!        // sp -= 16；保存帧指针 x29 和返回地址 x30
    mov x29, sp                      // 建立当前函数的帧指针

    // 1. 修改 __DATA,__data 中的 counter。
    //    Mach-O arm64 常用 @PAGE/@PAGEOFF 重定位取全局地址。
    adrp x9, counter@PAGE            // x9 = counter 所在 4KB 页的页地址
    add x9, x9, counter@PAGEOFF      // x9 = counter 的完整地址
    ldr x10, [x9]                    // x10 = counter
    add x10, x10, #1                 // x10 = 42
    str x10, [x9]                    // counter = 42

    // 2. 修改 __DATA,__bss 中的 scratch。
    adrp x9, scratch@PAGE            // x9 = scratch 所在页
    add x9, x9, scratch@PAGEOFF      // x9 = scratch 的完整地址
    mov w10, #65                     // w10 = ASCII 'A'
    strb w10, [x9]                   // scratch[0] = 'A'

    // 3. write(1, msg, msg_len)
    //    入门阶段不建议在 macOS 直接硬编码裸 syscall。
    //    这里调用 libSystem 提供的 _write：
    //    ssize_t write(int fd, const void *buf, size_t count)
    //
    //    AArch64 C 调用约定：
    //    x0 = 第 1 个参数
    //    x1 = 第 2 个参数
    //    x2 = 第 3 个参数
    //    x0 = 返回值
    mov x0, #1                       // x0 = 1，标准输出 stdout
    adrp x1, msg@PAGE                // x1 = msg 所在页
    add x1, x1, msg@PAGEOFF          // x1 = msg 的完整地址
    mov x2, #msg_len                 // x2 = 要写出的字节数
    bl _write                        // 调用 libSystem 的 write()

    // 4. read(0, scratch, 1)
    //    等待输入，方便在另一个终端运行 vmmap 查看内存布局。
    mov x0, #0                       // x0 = 0，标准输入 stdin
    adrp x1, scratch@PAGE            // x1 = scratch 所在页
    add x1, x1, scratch@PAGEOFF      // x1 = scratch 的完整地址
    mov x2, #1                       // x2 = 最多读取 1 字节
    bl _read                         // 调用 libSystem 的 read()

    // 5. main 返回 0。
    mov w0, #0                       // main 的返回值为 0
    ldp x29, x30, [sp], #16          // 恢复 x29/x30；sp += 16
    ret                              // 返回给 C 运行时，由运行时退出进程

编译运行：

clang seg-mac.s -o seg-mac
./seg-mac

第一个终端停住后，另一个终端查看 Mach-O 文件结构：

size -m seg-mac
otool -l seg-mac | egrep 'segname|sectname|initprot|maxprot|vmsize|filesize'

size -m 会按 Mach-O segment/section 显示大小。输出可能类似：

Segment __PAGEZERO: ...
Segment __TEXT: ...
    Section __text: ...
    Section __const: ...
Segment __DATA: ...
    Section __data: ...
    Section __bss: ...
Segment __LINKEDIT: ...

再看运行时映射：

pid=$(pgrep -x seg-mac | tail -n 1)
vmmap "$pid" | egrep '__TEXT|__DATA|__LINKEDIT|STACK|MALLOC' | head -40

可能看到类似：

__TEXT       100...-100... [  16K] r-x/r-x ... /path/to/seg-mac
__DATA_CONST 100...-100... [  16K] r--/rw- ... /path/to/seg-mac
__DATA       100...-100... [  16K] rw-/rw- ... /path/to/seg-mac
__LINKEDIT   100...-100... [  16K] r--/r-- ... /path/to/seg-mac

Stack        ...

macOS 的 vmmap 权限经常显示成 current/max 两组，例如 r-x/r-x 。前面是当前权限，后面是最大权限。

7. .bss 为什么 “不占文件空间”

.data 和 .bss 都是可写全局数据，但这些值区别很大：

.section .data
counter:
    .quad 41             # 文件中真的保存 41 这个初始值

.section .bss
buffer:
    .space 4096          # 文件中通常不保存 4096 个 0，只记录运行时要有 4096 字节

原因是：未初始化全局变量默认就是 0。与其把大量 0 写进可执行文件，不如在文件里记录 “这里需要 N 字节零填充空间”，加载器创建进程时再把那块内存清零。

在 ELF 的 program header 里，经常能看到：

FileSiz < MemSiz

这表示该 segment 在文件里占用的字节数小于运行时内存占用的字节数，多出来的部分通常就是 .bss 这类零填充区域。

在 Mach-O 里， __DATA,__bss 常通过 .zerofill 表示， size -m 可能显示 zerofill 。

8. x86-64 的 “分段” 现在还重要吗

如果接触过 16 位或 32 位 x86，可能见过这些概念：

  • CS ：代码段。
  • DS ：数据段。
  • SS ：栈段。
  • 段选择子、段描述符、GDT/LDT。

到了 Linux x86-64 用户态，这些不再是普通程序组织内存的主要方式。x86-64 long mode 下，常规代码和数据访问基本使用平坦地址空间，程序主要依赖 分页机制 和 虚拟内存映射 来隔离权限。

但不要把理解成 “段寄存器完全没用了”：

  • FS 在 Linux x86-64 用户态常用于线程局部存储，也就是 TLS。
  • GS 在内核态有重要用途，例如访问每 CPU 数据。
  • 调试、反汇编、系统编程时仍可能看到段寄存器相关内容。

对本教程来说，初学者先把重点放在：

ELF section -> ELF segment -> /proc/$pid/maps

这条线更有实际价值。

9. AArch64 和 macOS arm64 没有 x86 那套段寄存器

AArch64 没有 x86 那种 CS/DS/SS 段寄存器模型。AArch64 也有复杂的内存管理机制，例如：

  • 虚拟地址到物理地址的页表转换。
  • 页权限控制，例如可读、可写、可执行。
  • 异常级别和内存属性。
  • 线程局部存储相关寄存器，例如 TPIDR_EL0 。

但从写入门汇编程序的角度看，主要接触的是：

  • 把代码放进 .text 或 __TEXT,__text 。
  • 把只读常量放进 .rodata 或 __TEXT,__const 。
  • 把可写全局变量放进 .data 或 __DATA,__data 。
  • 把未初始化缓冲区放进 .bss 或 __DATA,__bss 。
  • 用工具查看最终映射权限。

Linux AArch64 和 macOS arm64 的最大差别不在 CPU 指令本身，而在 操作系统 ABI 和可执行文件格式。

10. 地址、值、权限：三个最容易混的点

10.1 标签是地址，不是值

counter:
    .quad 41

counter 是一个地址名字。内存里那个地址处保存的 8 字节内容才是 41 。

x86-64：

lea counter(%rip), %rbx      # rbx = counter 的地址
mov counter(%rip), %rax      # rax = counter 地址里的 8 字节值

AArch64：

adrp x9, counter
add x9, x9, :lo12:counter    // x9 = counter 的地址
ldr x10, [x9]                // x10 = counter 地址里的 8 字节值

macOS arm64：

adrp x9, counter@PAGE
add x9, x9, counter@PAGEOFF  // x9 = counter 的地址
ldr x10, [x9]                // x10 = counter 地址里的 8 字节值

10.2 section 名字不等于运行时权限

.text 通常不可写， .data 通常不可执行，但最终权限不是由名字魔法决定的，而是由链接器生成的加载信息和操作系统加载策略决定。

所以要用工具确认：

readelf -l ./seg-x86
cat /proc/$pid/maps

或：

otool -l ./seg-mac
vmmap "$pid"

10.3 栈和堆不是 .stack 和 .heap

初学图里常画：

text
data
bss
heap
stack

但大多数普通可执行文件里没有一个必须叫 .heap 的 section，也没有一个必须叫 .stack 的 section。

  • 栈通常由内核在创建进程时建立。
  • 堆通常由 C 库分配器通过 brk 或 mmap 管理。
  • 汇编里的 .bss 只是未初始化的静态存储，不是 “堆”。

12. 小练习

  1. 把 counter 的初始值从 41 改成 100 ，重新编译运行。观察文件大小是否明显变化。
  2. 把 scratch 从 4096 改成 1048576 ，重新编译后对比 ls -lh seg-x86 和 readelf -l seg-x86 的 MemSiz 。输出中可能看到 .bss 增大主要影响运行时内存需求，而不是等量增大文件内容。
  3. 尝试把写入 .rodata 的代码加进去，例如在 x86-64 中对 msg(%rip) 执行写操作。程序大概率会因为权限错误崩溃。这个实验有助于理解 r-- 和 r-x 为什么不能随便写。
  4. 在 macOS 上用 otool -l seg-mac 找到 __TEXT 和 __DATA 的 initprot 。思考为什么代码段需要执行权限，而数据段通常不需要执行权限。

13. 常见坑

13.1 把 ELF 的 .rodata 照搬到 macOS

Linux:

.section .rodata

macOS arm64 更常见：

.section __TEXT,__const

Mach-O 的 .section 通常要写成 segment,section 两级名字。

13.2 在 macOS 入门代码里硬编码 Linux syscall

Linux AArch64:

mov x8, #64
svc #0

macOS arm64 不要直接照搬。入门阶段建议：

bl _write

并用 clang 链接，让 libSystem 和 C 运行时辅助处理平台细节。

13.3 忘记 .bss 启动时清零

.bss 不是 “随机垃圾区”。静态存储期的未初始化对象会被初始化为 0。汇编里放在 .bss 或 Mach-O __DATA,__bss 的空间，正常加载后也是清零的。

13.4 用固定地址讲解 ASLR

现代系统通常启用 ASLR，地址可能每次运行都不同。学习时更应该关注：

  • 哪些映射来自可执行文件。
  • 哪些映射是只读、可执行、可写。
  • .bss 为什么让 MemSiz 大于 FileSiz 。
  • 栈、堆、共享库为什么不是手写汇编文件中的 section。
