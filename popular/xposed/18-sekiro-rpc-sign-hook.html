Sekiro签名RPC

ZIP2026/6/19...大约 10 分钟XposedLSPosedlibxposedSekiroRPC

LSPosed 使用 Sekiro RPC 远程调用签名方法

概述

上一篇已经解释了 libxposed 102 API 模块怎样被 LSPosed 识别、加载和回调。本文继续 Sekiro RPC 代码：模块进入目标 App 进程后，一边 Hook 目标签名方法用于观察入参与结果，一边启动 Sekiro 客户端，把目标 App 内部的签名算法包装成远程接口。

这次代码的目标很明确：

  • 只在 com.example.challenge 中执行业务逻辑
  • 找到混淆类 o00oOOoO.o000OOo
  • 定位签名方法 OooO(ByteArray): String
  • Hook 该方法，打印真实入参和返回值
  • 启动 Sekiro 客户端连接 192.168.100.234:5612
  • 注册 HookEntry 测试 action，返回当前时间
  • 注册 app_one 业务 action，接收 page 和 timestamp ，在目标进程内调用原签名方法并返回签名结果

读完本文，应该能理解这条链路：

外部请求 Sekiro Server
  ↓
Sekiro Server 转发到目标 App 进程里的 SekiroClient
  ↓
根据 action 找到 AppOneHook
  ↓
AutoBind 注入 page、timestamp 参数
  ↓
AppOneHook 反射调用目标 App 的混淆签名方法
  ↓
返回 page、timestamp、input、sign

一、相关文件

HookEntry.kt 负责模块生命周期、目标包过滤、签名方法 Hook、Sekiro 客户端启动。

AppOneHook.kt 负责真正的远程业务接口：把外部传入的参数拼成目标 App 需要的签名字符串，然后调用目标 App 自己的签名方法。

二、依赖与模块配置

1. Sekiro 依赖

gradle/libs.versions.toml 中已经配置：

[versions]
sekiroBusinessApi = "1.5"

[libraries]
sekiro-business-api = { module = "cn.iinti.sekiro3.business:sekiro-business-api", version.ref = "sekiroBusinessApi" }

app/build.gradle.kts 中引入：

dependencies {
    compileOnly(libs.libxposed.api)
    implementation(libs.service)
    implementation(libs.dexkit)
    implementation(libs.sekiro.business.api)
}

2. API 版本

module.prop 当前内容：

minApiVersion=102
targetApiVersion=102
staticScope=true
autoHotReload=true

这里把 minApiVersion 调整到了 102 。原因是模板当前就是按 libxposed API 102 编写，依赖版本也是：

libxposedApi = "102.0.0"

设备上的 LSPosed API 版本太低时，模块不应该被加载。

3. 默认作用域

scope.list 当前只有一行：

com.example.challenge

它表示模块默认作用在 com.example.challenge 。实际运行时还要在 LSPosed 管理器里启用模块、勾选作用域，并重启目标 App。

三、入口流程：从包加载到 RPC 启动

HookEntry 继承 XposedModule ：

class HookEntry : XposedModule() {
    companion object {
        const val TAG = "0X->"
        public lateinit var hostClassLoader: ClassLoader
    }
}

这里新增了一个很关键的全局变量：

public lateinit var hostClassLoader: ClassLoader

它保存目标 App 的 ClassLoader。后面的 AppOneHook 不在 onPackageReady() 方法体内，但它仍然需要反射目标 App 的混淆类，所以要通过 HookEntry.hostClassLoader 拿到正确的类加载器。

1. onPackageLoaded：保存默认 ClassLoader

当前代码：

@RequiresApi(Build.VERSION_CODES.Q)
override fun onPackageLoaded(param: PackageLoadedParam) {
    hostClassLoader = param.defaultClassLoader
    Log.d(TAG, "onPackageLoaded: ${param.packageName}")
    Log.d(TAG, "default classloader is ${param.defaultClassLoader}")
}

param.defaultClassLoader 是包加载阶段拿到的默认类加载器。代码把它保存到 hostClassLoader ，后续 RPC handler 可以直接使用。

需要注意，真正安装业务逻辑是在 onPackageReady() 里做的，因为这个阶段应用的 classLoader、组件工厂等信息更完整。

2. onPackageReady：过滤目标 App

核心代码：

override fun onPackageReady(param: PackageReadyParam) {
    Log.d(TAG, "onPackageReady: " + param.packageName)
    Log.d(TAG, "app classloader is " + param.classLoader)
    if (Build.VERSION.SDK_INT >= Build.VERSION_CODES.P) {
        Log.d(TAG, "app acf is " + param.appComponentFactory)
    }
    Log.d(TAG, "module apk path: " + this.moduleApplicationInfo.sourceDir)
    Log.d(TAG, "----------")

    if (param.packageName != "com.example.challenge") return
    if (!param.isFirstPackage) return

    installSignHook(param.classLoader)

    SekiroClient("0X", "marble", "192.168.100.234", 5612)
        .setupSekiroRequestInitializer { _, registry ->
            registry.registerSekiroHandler(object : ActionHandler {
                override fun action(): String {
                    return "HookEntry"
                }

                override fun handleRequest(
                    sekiroRequest: SekiroRequest,
                    sekiroResponse: SekiroResponse
                ) {
                    sekiroResponse.success<String>(System.currentTimeMillis().toString())
                }
            })
            registry.registerSekiroHandler(AppOneHook())
        }.start()
}

这段逻辑可以拆成 5 步：

  1. 打印包名、ClassLoader、模块 APK 路径，方便确认模块确实进入了目标进程。
  2. 判断包名，不是 com.example.challenge 就直接返回。
  3. 判断 param.isFirstPackage ，避免同一进程内重复安装 Hook、重复启动 Sekiro 客户端。
  4. 调用 installSignHook(param.classLoader) ，先把签名方法 Hook 起来。
  5. 创建并启动 SekiroClient ，注册两个远程 action。

param.isFirstPackage 很重要。Xposed 回调可能在同一进程里触发多次，如果不加这个判断， SekiroClient 可能重复连接，目标方法也可能被重复 Hook，日志和结果都会变得混乱。

四、签名方法 Hook

1. 定位目标类和目标方法

installSignHook() 的前半段：

private fun installSignHook(classLoader: ClassLoader) {
    try {
        val signClass = Class.forName("o00oOOoO.o000OOo", true, classLoader)
        val signMethod = signClass.getDeclaredMethod("OooO", ByteArray::class.java)

        hook(signMethod)
            .setId("o00oOOoO.o000OOo#OooO")
            .intercept {
                val input = (it.getArg(0) as ByteArray).toString(Charsets.UTF_8)
                val result = it.proceed() as String
                val message = "OooO input: $input, result: $result"
                Log.d(TAG, message)
                log(Log.DEBUG, TAG, message)
                result
            }

        Log.d(TAG, "installSignHook: hook installed")
        log(Log.DEBUG, TAG, "installSignHook: hook installed")
    } catch (throwable: Throwable) {
        Log.e(TAG, "installSignHook failed", throwable)
        log(Log.ERROR, TAG, "installSignHook failed", throwable)
    }
}

目标类名是：

o00oOOoO.o000OOo

目标方法签名是：

OooO(byte[]): String

所以反射代码写成：

val signClass = Class.forName("o00oOOoO.o000OOo", true, classLoader)
val signMethod = signClass.getDeclaredMethod("OooO", ByteArray::class.java)

这里必须使用目标 App 的 classLoader 。如果用模块自己的 ClassLoader，系统只会在模块 APK 里找类，而 o00oOOoO.o000OOo 是目标 App 的混淆类，必然找不到。

2. intercept 的执行顺序

Hook 部分：

hook(signMethod)
    .setId("o00oOOoO.o000OOo#OooO")
    .intercept {
        val input = (it.getArg(0) as ByteArray).toString(Charsets.UTF_8)
        val result = it.proceed() as String
        val message = "OooO input: $input, result: $result"
        Log.d(TAG, message)
        log(Log.DEBUG, TAG, message)
        result
    }

intercept 里的 it 是调用链对象，可以读取参数，也可以决定是否继续执行原方法。

这段代码的流程是：

目标 App 调用 OooO(byte[])
  ↓
进入 intercept
  ↓
读取第 0 个参数，按 UTF-8 转成字符串
  ↓
it.proceed() 执行原始 OooO(byte[])
  ↓
拿到原方法返回的 sign
  ↓
打印 input 和 sign
  ↓
返回 result，不改变原 App 行为

也就是说，当前 Hook 的作用是 观察，不是篡改。它不会修改入参，也不会替换返回值，只是把真实调用链里的明文和结果打出来。

3. 预期日志

安装成功后会看到：

0X->: installSignHook: hook installed

当目标 App 自己调用签名方法时，会看到类似：

0X->: OooO input: page=11718728400000, result: <sign>

如果看到 installSignHook failed ，优先检查：

  • 包名是否确实是 com.example.challenge
  • LSPosed 作用域是否勾选了目标 App
  • 目标类名 o00oOOoO.o000OOo 是否因版本变化而改变
  • 方法名 OooO 和参数类型 ByteArray 是否仍然匹配
  • Hook 执行时机是否早于目标类加载完成

五、SekiroClient：把目标进程变成远程服务

1. 创建客户端

代码：

SekiroClient("0X", "marble", "192.168.100.234", 5612)

构造参数含义是：

SekiroClient(sekiroGroup, clientId, serverHost, serverPort)

对应当前代码：

参数当前值作用
sekiroGroup0XSekiro 分组，外部请求时用它定位一组客户端
clientIdmarble当前客户端 ID
serverHost192.168.100.234Sekiro Server 地址
serverPort5612Sekiro Server 端口

start() 调用后，目标 App 进程里的模块代码会尝试连接 Sekiro Server。连接成功后，外部请求就可以通过 Sekiro Server 转发到这个 App 进程。

2. 注册 handler

代码：

.setupSekiroRequestInitializer { _, registry ->
    registry.registerSekiroHandler(object : ActionHandler {
        override fun action(): String {
            return "HookEntry"
        }

        override fun handleRequest(
            sekiroRequest: SekiroRequest,
            sekiroResponse: SekiroResponse
        ) {
            sekiroResponse.success<String>(System.currentTimeMillis().toString())
        }
    })
    registry.registerSekiroHandler(AppOneHook())
}

ActionHandler 有两个核心方法：

  • action() ：返回 action 名，外部请求根据这个名字路由到对应 handler
  • handleRequest(...) ：处理请求并写回响应

当前注册了两个 action：

actionhandler作用
HookEntry匿名 ActionHandler测试 RPC 是否通，返回当前时间戳字符串
app_oneAppOneHook业务接口，调用目标 App 签名方法

建议先请求 HookEntry 。如果它能返回当前时间，说明 Sekiro Server、网络、客户端注册都没问题，再继续调 app_one 。

六、AppOneHook：远程调用签名算法

1. 参数自动绑定

AppOneHook 开头：

class AppOneHook : ActionHandler {

    @field:AutoBind("page", defaultValue = "1")
    var page: Int = 1

    @field:AutoBind("timestamp", defaultValue = "0")
    var timestamp: Long = 0L

    override fun action(): String {
        return "app_one"
    }
}

@AutoBind 是 Sekiro 提供的运行时字段注入注解。请求到达 app_one 时，Sekiro 会从请求参数里取出同名字段并赋值：

  • 请求参数 page 绑定到 page: Int
  • 请求参数 timestamp 绑定到 timestamp: Long

如果外部没有传参数，就使用默认值：

  • page 默认为 1
  • timestamp 默认为 0

action() 返回的是：

app_one

所以外部请求必须指定 action=app_one ，才会进入这个 handler。

2. 生成待签名字符串

handleRequest() 里先处理时间戳：

val realTimestamp = if (timestamp == 0L) {
    System.currentTimeMillis()
} else {
    timestamp
}
val input = "page=$page$realTimestamp"

逻辑是：

  • 如果外部传了 timestamp ，就使用外部传入值
  • 如果外部没有传， timestamp 会是默认值 0 ，代码改用当前系统时间
  • 最终拼接出 page=<page><realTimestamp>

例如：

page=1
timestamp=1718728400000

最终参与签名的字符串是：

page=11718728400000

注意这里不是 page=1&timestamp=1718728400000 ，中间没有 &timestamp= ，而是直接把 page= 、页码、时间戳拼在一起。复现时要严格按代码里的格式拼接，否则签名结果会不一致。

当前响应里返回的 timestamp 字段是原始入参 timestamp ，不是 realTimestamp 。所以如果外部不传 timestamp，响应里的 timestamp 仍然是 0 ，但 input 中已经使用了当前时间。

3. 反射调用目标签名方法

核心代码：

val signClass =
    Class.forName("o00oOOoO.o000OOo", true, HookEntry.hostClassLoader)
val signObj = signClass.getDeclaredConstructor().newInstance()
val signMethod =
    signClass.getDeclaredMethod("OooO", ByteArray::class.java)

val sign = signMethod.invoke(
    signObj,
    input.toByteArray(Charsets.UTF_8)
) as String

复用目标 App 的实现：

外部传入 page、timestamp
  ↓
模块拼接 input
  ↓
通过目标 ClassLoader 找到混淆签名类
  ↓
newInstance() 创建目标类对象
  ↓
getDeclaredMethod(...) 找到 OooO(byte[])
  ↓
invoke(...) 调用原方法
  ↓
得到 sign

这种方式的好处是稳定、省事：只要目标 App 的签名方法还能被定位，就不需要把算法移植到 Python、Node.js 或 Java 服务端。

4. 返回响应

成功时：

sekiroResponse.success(
    mapOf(
        "page" to page,
        "timestamp" to timestamp,
        "input" to input,
        "sign" to sign
    )
)

返回数据包含：

字段含义
page本次请求页码
timestamp外部传入的 timestamp，未传时为 0
input实际参与签名的字符串
sign目标 App 原签名方法计算出的结果

失败时：

catch (throwable: Throwable) {
    Log.e(TAG, "handleRequest failed", throwable)
    sekiroResponse.failed("handleRequest failed: ${throwable.message}")
}

这样远程调用方不会只看到连接断开，而是能拿到一段失败信息。排查类名、方法名、构造函数、参数类型错误时很有用。

七、完整请求流程

把前面的代码连起来，完整流程如下：

1. 安装并启用模块
   ↓
2. LSPosed 读取 module.prop、java_init.list、scope.list
   ↓
3. 启动 com.example.challenge
   ↓
4. HookEntry.onPackageLoaded 保存 hostClassLoader
   ↓
5. HookEntry.onPackageReady 过滤包名和 isFirstPackage
   ↓
6. installSignHook 安装 OooO(byte[]) 的观察型 Hook
   ↓
7. SekiroClient 连接 192.168.100.234:5612
   ↓
8. 注册 HookEntry 和 app_one 两个 action
   ↓
9. 外部请求 action=app_one&page=1&timestamp=1718728400000
   ↓
10. Sekiro Server 把请求转发给目标 App 进程里的 AppOneHook
   ↓
11. AutoBind 注入 page、timestamp
   ↓
12. AppOneHook 拼接 input = page=11718728400000
   ↓
13. 反射调用 o00oOOoO.o000OOo.OooO(inputBytes)
   ↓
14. 返回 input 和 sign
