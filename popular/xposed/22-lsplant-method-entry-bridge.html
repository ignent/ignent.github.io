LSPlant方法入口桥接

ZIP2026/6/24...大约 27 分钟XposedLSPlantARTARM64ArtMethodNative Hook

LSPlant 方法入口桥接：调用链、ARM64 入口与解释器桥

概述

前面已经从 ArtMethod 入口替换、ART 虚拟机创建、类加载初始化和 LSPlant 初始化基础设施几个角度看过 ART。本文继续把线往真正的调用入口上收束：一个被 LSPlant Hook 的 Java 方法，最终是怎样从普通 Java 调用跳到 callback，再通过 backup 回到原方法的。

本文围绕四个问题展开：

  1. Hooker.hook() 到 lsplant::Hook() 的方法调用链路是什么？
  2. ARM64 下 LSPlant 生成的 quick entry trampoline 到底执行了什么？
  3. ArtMethod::SetEntryPoint() 为什么既要改 quick entry，有些旧版本还要改 interpreter entry？
  4. art_quick_to_interpreter_bridge 在去优化和解释执行里扮演什么角色？

最终能看到的效果很直接：

Hook 前：LSPTest.staticMethod() 返回 false
Hook 后：LSPTest.staticMethod() 返回 true
调用 backup：仍然返回原始 false
UnHook 后：LSPTest.staticMethod() 再次返回 false

但这背后的 native 链路并不短：

UnitTest.t01_staticMethod()
  -> Hooker.hook(target, replacement, owner)
  -> Hooker.doHook(Member original, Method callback)
  -> Java_org_lsposed_lsplant_Hooker_doHook()
  -> lsplant::Hook(env, target_method, hooker_object, callback_method)
  -> BuildDex() 生成签名兼容的 hook stub 和 backup stub
  -> ArtMethod::FromReflectedMethod() 取 target/hook/backup 的 ArtMethod*
  -> DoHook(target, hook, backup)
  -> GenerateTrampolineFor(hook)
  -> target->BackupTo(backup)
  -> target->SetEntryPoint(trampoline)
  -> 后续 quick 调用进入 trampoline
  -> trampoline 读取 hook ArtMethod 的 quick entry
  -> 执行生成的 hook stub
  -> hooker_object.callback(Object[] args)
  -> replacement.invoke(...)

注意

本文讨论的是 ART 内部实现，不是 Android SDK 稳定公开接口。 ArtMethod 字段偏移、 libart.so 符号名、quick entry、JIT、ClassLinker 和解释器桥都可能随 Android 版本、厂商 ROM、编译选项变化。请把本文当作源码阅读和实验复现指南，不要把内部偏移或私有符号跨版本照搬。

本文验证的最小现象

读者复现时不要只看 Hook() 返回非空，还要验证三件事：

  1. 目标方法调用已经变成 replacement 的结果。
  2. backup 反射调用仍能得到原始结果。
  3. UnHook() 后目标方法恢复原始行为。

这三点同时成立，才说明 target、hook stub、backup stub 和入口恢复链路都能工作。

核心代码

1. Java 层入口： Hooker.hook()

LSPlant 测试工程的 Java 层封装很小，但它刚好展示了 Hook 框架常见的三类对象：

  • target ：要 Hook 的原始 Method 或 Constructor 。
  • replacement ：真正的替换逻辑。
  • backup ：LSPlant 生成并返回的备份方法，用于调用原始逻辑。
// 文件：test/src/main/java/org/lsposed/lsplant/Hooker.java

package org.lsposed.lsplant;

import java.lang.reflect.InvocationTargetException;
import java.lang.reflect.Member;
import java.lang.reflect.Method;

public class Hooker {

    /**
     * 传给 replacement 的上下文对象。
     *
     * backup：LSPlant 返回的备份 Method，可以反射调用原始逻辑。
     * args：LSPlant 生成的 stub 收集到的参数数组。
     *      非静态方法 args[0] 是 this，静态方法没有 this 占位。
     */
    static class MethodCallback {
        Method backup;
        Object[] args;

        MethodCallback(Method backup, Object[] args) {
            this.backup = backup;
            this.args = args;
        }
    }

    // 保存 native Hook 成功后返回的备份方法。
    public Method backup;

    // 被 Hook 的目标方法或构造函数，用于 unhook。
    private Member target;

    // 业务层 replacement。测试里来自 Replacement.class。
    private Method replacement;

    // replacement 的接收者对象。静态 replacement 可以为 null。
    private Object owner = null;

    private Hooker() {
    }

    // native 层会调用 lsplant::Hook(env, original, this, callback)。
    private native Method doHook(Member original, Method callback);

    // native 层会调用 lsplant::UnHook(env, target)。
    private native boolean doUnhook(Member target);

    /**
     * 这个方法不是业务 replacement，而是 LSPlant 生成 stub 后固定调用的桥。
     * 生成的 hook stub 会把目标方法参数装箱成 Object[]，再调用这里。
     */
    public Object callback(Object[] args)
            throws InvocationTargetException, IllegalAccessException {
        var methodCallback = new MethodCallback(backup, args);
        return replacement.invoke(owner, methodCallback);
    }

    public boolean unhook() {
        return doUnhook(target);
    }

    public static Hooker hook(Member target, Method replacement, Object owner) {
        Hooker hooker = new Hooker();
        try {
            // callbackMethod 是 Hooker.callback(Object[])，不是 Replacement 里的方法。
            var callbackMethod = Hooker.class.getDeclaredMethod("callback", Object[].class);

            // native 返回 backup Method。返回 null 表示 Hook 失败。
            var result = hooker.doHook(target, callbackMethod);
            if (result == null) return null;

            hooker.backup = result;
            hooker.target = target;
            hooker.replacement = replacement;
            hooker.owner = owner;
        } catch (NoSuchMethodException ignored) {
        }
        return hooker;
    }
}

这里有一个容易误解的点：传给 native 的 callback_method 是 Hooker.callback(Object[]) ，不是 Replacement.staticMethodReplacement(...) 。 Replacement 只是被 Hooker.callback() 反射调用的一层业务逻辑。这样设计可以让 Hooker 保存上下文、backup 和多个 callback 列表，比较接近 Xposed 框架的做法。

2. JNI 入口： test.cpp

测试模块的 native 代码负责三件事：

  • 用 xDL 打开 libart.so 并解析符号。
  • 用 Dobby 提供 inline hook 和 unhook 能力。
  • 在 JNI_OnLoad() 中调用 lsplant::Init() 。
// 文件：test/src/main/jni/test.cpp

#include <jni.h>
#include <dobby.h>
#include <sys/mman.h>
#include <string_view>
#include <xdl.h>
#include "logging.h"

// 当前工程使用 C++20/23 modules 暴露 LSPlant API。
import lsplant;

// 下面这些宏用于把 ART 代码页临时改成 RWX，方便 Dobby 写 inline hook。
// 真实产品里应优先使用更受控的内存权限策略，避免长期 RWX。
#define _uintval(p) reinterpret_cast<uintptr_t>(p)
#define _ptr(p) reinterpret_cast<void *>(p)
#define _align_up(x, n) (((x) + ((n) - 1)) & ~((n) - 1))
#define _align_down(x, n) ((x) & -(n))
#define _page_size 4096
#define _page_align(n) _align_up(static_cast<uintptr_t>(n), _page_size)
#define _ptr_align(x) _ptr(_align_down(reinterpret_cast<uintptr_t>(x), _page_size))
#define _make_rwx(p, n) \
    ::mprotect( \
        _ptr_align(p), \
        _page_align(_uintval(p) + n) != _page_align(_uintval(p)) \
            ? _page_align(n) + _page_size \
            : _page_align(n), \
        PROT_READ | PROT_WRITE | PROT_EXEC \
    )

// Java 层 LSPTest.initHooker() 会读取这个结果。
bool init_result;

void *find_symbol(void *handle, const char *sys_name) {
    // 先查动态符号表。
    void *addr = xdl_sym(handle, sys_name, nullptr);

    // 如果动态符号表找不到，再查调试/静态符号表。
    if (nullptr == addr) {
        addr = xdl_dsym(handle, sys_name, nullptr);
    }
    return addr;
}

void *InlineHooker(void *target, void *hooker) {
    // Dobby 写跳转前需要目标页可写可执行。
    _make_rwx(target, _page_size);

    // origin_call 是 Dobby 返回的原函数跳板。
    void *origin_call;
    if (DobbyHook(target, hooker, &origin_call) == RS_SUCCESS) {
        return origin_call;
    }
    return nullptr;
}

bool InlineUnhooker(void *func) {
    // 移除 Dobby 安装的 inline hook。
    return DobbyDestroy(func) == RT_SUCCESS;
}

extern "C"
JNIEXPORT jboolean JNICALL
Java_org_lsposed_lsplant_LSPTest_initHooker(JNIEnv *, jclass) {
    return init_result;
}

extern "C"
JNIEXPORT jobject JNICALL
Java_org_lsposed_lsplant_Hooker_doHook(
        JNIEnv *env,
        jobject thiz,
        jobject target,
        jobject callback) {
    // thiz 是 Hooker 对象，用来保存上下文；callback 是 Hooker.callback(Object[])。
    return lsplant::Hook(env, target, thiz, callback);
}

extern "C"
JNIEXPORT jboolean JNICALL
Java_org_lsposed_lsplant_Hooker_doUnhook(JNIEnv *env, jobject, jobject target) {
    return lsplant::UnHook(env, target);
}

JNIEXPORT jint JNICALL
JNI_OnLoad(JavaVM *vm, void *) {
    JNIEnv *env;
    if (vm->GetEnv((void **) &env, JNI_VERSION_1_6) != JNI_OK) {
        return JNI_ERR;
    }

    // 打开 libart.so。LSPlant 后续会请求大量 ART 内部符号。
    static void *handle = xdl_open("libart.so", XDL_DEFAULT);

    lsplant::InitInfo initInfo{
        .inline_hooker = InlineHooker,
        .inline_unhooker = InlineUnhooker,
        .art_symbol_resolver = [](std::string_view symbol) -> void * {
            return find_symbol(handle, symbol.data());
        },
        .art_symbol_prefix_resolver = [](auto symbol) {
            return find_symbol(handle, symbol.data());
        },
    };

    // Init 会缓存 JNI 入口、解析 ArtMethod 布局、hook ClassLinker/JIT 等内部函数。
    init_result = lsplant::Init(env, initInfo);
    return JNI_VERSION_1_6;
}

InitInfo 是 LSPlant 能工作的前提。它不内置具体 inline hook 框架，而是把 inline_hooker 、 inline_unhooker 、 art_symbol_resolver 交给使用者。这样 LSPlant 可以在不同项目中接 Dobby、shadowhook 或其他方案。

3. lsplant::Hook() ：从反射对象到 ArtMethod

lsplant::Hook() 是整个链路的核心。下面保留主线代码，省略了部分局部引用包装和日志细节：

// 文件：lsplant/src/main/jni/lsplant.cc

[[maybe_unused]] jobject Hook(
        JNIEnv *env,
        jobject target_method,
        jobject hooker_object,
        jobject callback_method) {
    // target_method 必须是 Method 或 Constructor。
    if (!target_method || !JNI_IsInstanceOf(env, target_method, executable)) {
        LOGE("target method is not an executable");
        return nullptr;
    }

    // callback_method 同样必须是可执行反射对象。
    if (!callback_method || !JNI_IsInstanceOf(env, callback_method, executable)) {
        LOGE("callback method is not an executable");
        return nullptr;
    }

    // 通过反射 Method/Constructor 找到 ART 内部 ArtMethod*。
    auto *target = ArtMethod::FromReflectedMethod(env, target_method);
    bool is_static = target->IsStatic();

    // LSPlant 不允许重复 Hook 同一个 ArtMethod。
    if (IsHooked(target, true)) {
        LOGW("Skip duplicate hook");
        return nullptr;
    }

    // BuildDex 会动态生成一个类：
    // 1. hook method：签名和目标方法一致，内部调用 Hooker.callback(Object[])
    // 2. backup method：签名和目标方法一致，稍后会被 target->BackupTo() 填入原方法信息
    std::tie(built_class, hooker_field, hook_method, backup_method) =
        BuildDex(
            env,
            callback_class_loader.get(),
            ArtMethod::GetMethodShorty(env, target_method),
            is_static,
            target->IsConstructor() ? "constructor" : target_method_name.get(),
            class_name.get(),
            callback_method_name.get());

    if (!built_class || !hooker_field || !hook_method || !backup_method) {
        LOGE("Failed to generate hooker");
        return nullptr;
    }

    // 把生成类里的 hook/backup method 转成 Java 反射对象。
    auto reflected_hook = JNI_ToReflectedMethod(env, built_class, hook_method, JNI_TRUE);
    auto reflected_backup = JNI_ToReflectedMethod(env, built_class, backup_method, JNI_TRUE);

    // backup 可能是 private 或包内方法，先放开反射访问。
    JNI_CallVoidMethod(env, reflected_backup, set_accessible, JNI_TRUE);

    // 再把 Java 反射对象转回 ArtMethod*，后续直接修改 ART 内部结构。
    auto *hook = ArtMethod::FromReflectedMethod(env, reflected_hook.get());
    auto *backup = ArtMethod::FromReflectedMethod(env, reflected_backup.get());

    // 生成类有一个静态字段保存 hooker_object。
    // hook stub 执行时会从这个字段取出 Hooker 实例，再调用 callback(Object[])。
    JNI_SetStaticObjectField(env, built_class, hooker_field, hooker_object);

    if (DoHook(target, hook, backup)) {
        jobject global_backup = JNI_NewGlobalRef(env, reflected_backup);

        // 记录 target <-> backup 的关系，供 JIT、ClassLinker、UnHook 使用。
        RecordHooked(target, target->GetDeclaringClass()->GetClassDef(), global_backup, backup);

        // 记录 JIT movement，避免 JIT code cache 回收时 target/backup 混乱。
        RecordJitMovement(target, backup);

        // backup 也要记录为 deoptimized，避免生成类静态 trampoline 修复覆盖它的入口。
        RecordDeoptimized(hook->GetDeclaringClass()->GetClassDef(), backup);
        return global_backup;
    }

    return nullptr;
}

这段代码的关键不是 “拿一个 Method 换另一个 Method”，而是生成了两个运行时方法：

方法来源作用
hookBuildDex() 生成和目标方法签名一致，负责把参数装箱为 Object[] 并调用 Hooker.callback()
backupBuildDex() 生成后再由 target->BackupTo(backup) 填充保存原始 ArtMethod 信息，供 backup.invoke(...) 调回原方法
target原始目标方法quick entry 被改成 LSPlant 生成的 trampoline

4. BuildDex() ：为什么要动态生成 stub

LSPlant 要 Hook 任意 Java 方法，而目标方法的签名可能是：

boolean staticMethod()
String normalMethod(String a, int b, long c)
String manyParametersMethod(String a, boolean b, byte c, short d, int e, long f, float g, double h, Integer i, Long j)

如果直接把所有目标方法都跳到一个固定 native 函数，就要手写复杂的 ABI 参数搬运、装箱和返回值适配。LSPlant 的方案是动态生成 Dex stub，让 ART 自己按 Java 调用规则处理参数和返回值。

核心逻辑如下，省略了 DexBuilder 的细节构造代码：

// 文件：lsplant/src/main/jni/lsplant.cc

std::tuple<jclass, jfieldID, jmethodID, jmethodID> BuildDex(
        JNIEnv *env,
        jobject class_loader,
        std::string_view shorty,
        bool is_static,
        std::string_view method_name,
        std::string_view hooker_class,
        std::string_view callback_name) {
    // shorty[0] 是返回值类型，shorty.substr(1) 是参数类型。
    // 例如 "(String, int, long) -> String" 的 shorty 可理解为 LLIJ。
    auto return_type =
        shorty[0] == 'L'
            ? TypeDescriptor::Object
            : TypeDescriptor::FromDescriptor(shorty[0]);

    auto parameter_types = std::vector<TypeDescriptor>();

    // 非静态方法需要额外把 this 放到第一个参数。
    if (!is_static) {
        parameter_types.push_back(TypeDescriptor::Object);
    }

    // 把 shorty 中的参数字符转换成 DexBuilder 类型描述。
    for (const char &param : shorty.substr(1)) {
        parameter_types.push_back(
            param == 'L'
                ? TypeDescriptor::Object
                : TypeDescriptor::FromDescriptor(static_cast<char>(param)));
    }

    // 创建生成类中的静态字段，用来保存 Hooker 对象。
    auto *hooker_field = cbuilder.CreateField(generated_field_name, hooker_type)
                             .access_flags(dex::kAccStatic)
                             .Encode();

    // 创建 hook 方法：方法名默认跟目标方法相同，签名跟目标方法兼容。
    auto hook_builder{cbuilder.CreateMethod(
        generated_method_name == "{target}" ? method_name.data() : generated_method_name,
        Prototype{return_type, parameter_types})};

    // 创建 Object[]，长度等于参数数量。
    auto tmp{hook_builder.AllocRegister()};
    hook_builder.BuildConst(tmp, static_cast<int>(parameter_types.size()));
    auto hook_params_array{hook_builder.AllocRegister()};
    hook_builder.BuildNewArray(hook_params_array, TypeDescriptor::Object, tmp);

    // 把每个参数装箱后放入 Object[]。
    // long/double 这类 wide 参数会占两个寄存器，所以 j 需要额外递增。
    for (size_t i = 0U, j = 0U; i < parameter_types.size(); ++i, ++j) {
        hook_builder.BuildBoxIfPrimitive(Value::Parameter(j), parameter_types[i],
                                         Value::Parameter(j));
        hook_builder.BuildConst(tmp, static_cast<int>(i));
        hook_builder.BuildAput(
            Instruction::Op::kAputObject,
            hook_params_array,
            Value::Parameter(j),
            tmp);
        if (parameter_types[i].is_wide()) ++j;
    }

    // 调用 Hooker.callback(Object[])，返回 Object。
    auto handle_hook_method{dex_file.GetOrDeclareMethod(
        hooker_type,
        callback_name.data(),
        Prototype{TypeDescriptor::Object, TypeDescriptor::Object.ToArray()})};

    // 读取静态字段 hooker，作为 callback 的 this。
    hook_builder.AddInstruction(
        Instruction::GetStaticObjectField(hooker_field->decl->orig_index, tmp));
    hook_builder.AddInstruction(
        Instruction::InvokeVirtualObject(handle_hook_method.id, tmp, tmp, hook_params_array));

    // 根据目标返回值类型拆箱、cast 或直接 return。
    if (return_type == TypeDescriptor::Void) {
        hook_builder.BuildReturn();
    } else if (return_type.is_primitive()) {
        auto box_type{return_type.ToBoxType()};
        const ir::Type *type_def = dex_file.GetOrAddType(box_type);
        hook_builder.AddInstruction(Instruction::Cast(tmp, Value::Type(type_def->orig_index)));
        hook_builder.BuildUnBoxIfPrimitive(tmp, box_type, tmp);
        hook_builder.BuildReturn(tmp, false, return_type.is_wide());
    } else {
        const ir::Type *type_def = dex_file.GetOrAddType(return_type);
        hook_builder.AddInstruction(Instruction::Cast(tmp, Value::Type(type_def->orig_index)));
        hook_builder.BuildReturn(tmp, true);
    }

    // backup 方法先生成一个签名兼容的空壳。
    // 真正的原方法信息会在 DoHook() 中由 target->BackupTo(backup) 复制进去。
    auto backup_builder{cbuilder.CreateMethod("backup", Prototype{return_type, parameter_types})};
    // 这里省略不同返回值的默认 return 代码。

    // 最后把 Dex image 加载进运行时，并返回生成类、hooker 字段、hook 方法、backup 方法。
}

这种设计的好处是：

  • 参数装箱、拆箱、返回值类型检查都在 Java/Dex 层完成。
  • quick entry trampoline 只需要把执行入口切到 hook ArtMethod ，不用理解每种 Java 签名。
  • backup 是一个真正的 Method ，可以通过反射调用，这和 Xposed 的 callOriginalMethod 语义很接近。

代价也很明显：每次进入 callback 都要创建 Object[] ，原始参数会发生装箱，频繁 Hook 热路径方法时会带来额外分配和反射开销。

5. ARM64 trampoline：quick entry 实际跳到哪里

LSPlant 在 lsplant.cc 里为不同架构准备了不同的 trampoline 模板。本文只看 ARM64：

// 文件：lsplant/src/main/jni/lsplant.cc

consteval inline auto GetTrampoline() {
    if constexpr (is_arch_v<Arch::kAArch64>) {
        return std::make_tuple(
            // 这段字节是 ARM64 机器码模板，最后 8 字节会被替换为 hook ArtMethod*。
            "\x60\x00\x00\x58"      // ldr x0, literal: 从模板末尾读出 hook ArtMethod*
            "\x10\x00\x40\xf8"      // ldr x16, [x0, #entry_point_offset]
            "\x00\x02\x1f\xd6"      // br x16
            "\x78\x56\x34\x12"
            "\x78\x56\x34\x12"_uarr,

            // entry_point_offset 不是 ArtMethod 偏移本身，
            // 而是“要把 ArtMethod quick entry 偏移写进哪一段指令”的 bit 位置。
            uint8_t{44u},

            // hook ArtMethod* 在 trampoline 模板中的写入位置。
            uintptr_t{12u});
    }
}

auto [trampoline, entry_point_offset, art_method_offset] = GetTrampoline();

模板初始含义可以翻译成伪汇编：

ldr x0, .Lhook_method_pointer
ldr x16, [x0, #ArtMethod.entry_point_from_quick_compiled_code_]
br  x16

.Lhook_method_pointer:
    .quad hook_art_method

UpdateTrampoline() 会把运行时探测到的 ArtMethod quick entry 偏移编码进第二条 ldr 指令：

// 文件：lsplant/src/main/jni/lsplant.cc

inline void UpdateTrampoline(uint8_t offset) {
    // 把 ArtMethod::GetEntryPointOffset() 写进 trampoline 模板中的 ldr immediate 字段。
    // ARM64 ldr unsigned immediate 对齐编码，这里直接按 bit 位置打补丁。
    trampoline[entry_point_offset / CHAR_BIT] |= offset << (entry_point_offset % CHAR_BIT);
    trampoline[entry_point_offset / CHAR_BIT + 1] |=
        offset >> (CHAR_BIT - entry_point_offset % CHAR_BIT);
}

bool InitNative(JNIEnv *env, const HookHandler &handler) {
    if (!ArtMethod::Init(env, handler)) {
        LOGE("Failed to init art method");
        return false;
    }

    // ArtMethod::Init() 先探测出 quick entry 偏移，再更新 trampoline 模板。
    UpdateTrampoline(ArtMethod::GetEntryPointOffset());

    // 后续继续初始化 Thread、ClassLinker、JIT、Instrumentation 等模块。
}

随后 GenerateTrampolineFor(hook) 会把具体的 hook ArtMethod* 写入模板末尾，并复制到可执行内存：

// 文件：lsplant/src/main/jni/lsplant.cc

void *GenerateTrampolineFor(art::ArtMethod *hook) {
    // 拷贝一份模板，避免修改全局模板。
    auto data = trampoline;

    // 在模板末尾写入 hook ArtMethod*。
    // ARM64 trampoline 第一条 ldr 会把这个指针读进 x0。
    *reinterpret_cast<ArtMethod **>(data.data() + art_method_offset) = hook;

    // 如果外部提供了可执行内存分配器，优先使用外部分配器。
    if (executable_memory_allocator) {
        if (auto *memory = static_cast<char *>(executable_memory_allocator(data))) {
            __builtin___clear_cache(memory, memory + data.size());
            return memory;
        }
    }

    // 否则 LSPlant 自己按页分配 trampoline 池。
    // 新系统优先使用 memfd/ashmem 做 RX/RW 双映射，退化时才用 RWX mmap。
    auto *address_ptr = reinterpret_cast<char *>(address);

    if (dual_regions.contains(__builtin_align_down(address_ptr, kPageSize))) {
        // 双映射下，address_ptr 是 RX 视图；写入要走同一页后面的 RW 视图。
        std::memcpy(address_ptr + kPageSize, data.data(), data.size());
    } else {
        // 普通 mmap 情况下直接写入。
        std::memcpy(address_ptr, data.data(), data.size());
    }

    // 清理指令缓存，确保 CPU 后续执行的是新写入的机器码。
    __builtin___clear_cache(address_ptr, reinterpret_cast<char *>(address + data.size()));
    return address_ptr;
}

ARM64 下方法调用进入 target 后，ART quick invoke 会跳到 target 的 quick entry。此时 quick entry 已经被改成上面的 trampoline，所以执行顺序变成：

target ArtMethod.quick_entry
  -> LSPlant trampoline
  -> 读取 hook ArtMethod*
  -> 读取 hook ArtMethod.quick_entry
  -> br 到 hook 的 quick entry
  -> 执行 BuildDex 生成的 hook stub

这里 trampoline 没有直接写死某个函数地址，而是通过 hook ArtMethod 间接读取 quick entry。这样做能适应 hook stub 后续被 ART 初始化、编译或修复入口的情况。

6. DoHook() ：真正设置入口

DoHook() 是入口替换发生的地方：

// 文件：lsplant/src/main/jni/lsplant.cc

bool DoHook(ArtMethod *target, ArtMethod *hook, ArtMethod *backup) {
    // 进入 GC 临界区，避免修改方法入口时和 GC/调试器状态冲突。
    ScopedGCCriticalSection section(
        art::Thread::Current(),
        art::gc::kGcCauseDebugger,
        art::gc::kCollectorTypeDebugger);

    // 暂停所有线程，减少其他线程正在调用或更新同一方法入口的风险。
    ScopedSuspendAll suspend("LSPlant Hook", false);

    // 生成指向 hook ArtMethod 的 trampoline。
    if (auto *entrypoint = GenerateTrampolineFor(hook); !entrypoint) {
        LOGE("Failed to generate trampoline");
        return false;
    } else {
        // intrinsic 方法可能被 ART 特殊优化，先取消 intrinsic 标记。
        target->SetNonIntrinsic();

        // 把 target 的当前 ArtMethod 内容复制到 backup。
        target->BackupTo(backup);

        // 禁止 target 后续被编译器继续优化，避免 entry 被 JIT/AOT 覆盖。
        target->SetNonCompilable();

        // 核心动作：target 的 quick entry 改成 LSPlant trampoline。
        target->SetEntryPoint(entrypoint);

        return true;
    }
}

这段代码解释了为什么 Hook 框架不能只做一次普通指针写入：

  • 修改入口前要考虑其他线程是否正在执行。
  • target 的原始状态要复制到 backup。
  • target 要尽量避免继续被 JIT 编译覆盖。
  • intrinsic 方法要去掉特殊标记。
  • 静态方法、未初始化类、JIT code cache、debuggable instrumentation 后续都可能再改入口，所以 LSPlant 还要在其他 ART 函数上打保护性 Hook。

7. ArtMethod::BackupTo() 与 SetEntryPoint()

ArtMethod 是 ART 内部结构，LSPlant 不能依赖稳定公开头文件，只能运行时探测字段布局。

现代 Android 上， ArtMethod::Init() 的关键策略是：

// 文件：lsplant/src/main/jni/art/runtime/art_method.cxx

static bool Init(JNIEnv *env, const HookHandler handler) {
    auto sdk_int = GetAndroidApiLevel();

    // Android 8.0+ 使用 java.lang.reflect.Executable。
    // Android 6.0/7.x 使用 AbstractMethod。
    // Android 5.x 还有 java.lang.reflect.ArtMethod。
    if (sdk_int >= kSdkOreo) {
        executable = JNI_FindClass(env, "java/lang/reflect/Executable");
    } else if (sdk_int >= kSdkMarshmallow) {
        executable = JNI_FindClass(env, "java/lang/reflect/AbstractMethod");
    } else {
        executable = JNI_FindClass(env, "java/lang/reflect/ArtMethod");

    // Android 6.0+ 的反射对象里有 artMethod long 字段。
    if (sdk_int >= kSdkMarshmallow) {

    auto constructors =
        JNI_Cast<jobjectArray>(JNI_CallObjectMethod(env, throwable, get_declared_constructors));
    auto *first = FromReflectedMethod(env, constructors[0].get());
    auto *second = FromReflectedMethod(env, constructors[1].get());
    art_method_size =
        reinterpret_cast<uintptr_t>(second) - reinterpret_cast<uintptr_t>(first);

    entry_point_offset = art_method_size - kPointerSize;
    data_offset = entry_point_offset - kPointerSize;

    // access_flags 偏移通过反射对象的 accessFlags 值反查。
    // 找不到时退回到常见偏移 4。
}

入口设置本身很短：

// 文件：lsplant/src/main/jni/art/runtime/art_method.cxx

void SetEntryPoint(void *entry_point) {
    // 写 ptr_sized_fields_ 里的 quick compiled code entry。
    *reinterpret_cast<void **>(
        reinterpret_cast<uintptr_t>(this) + entry_point_offset) = entry_point;

    // Android 5.x/6.0 部分版本还有独立的 interpreter entry。
    // 如果只改 quick entry，解释器路径可能不走新入口。
    if (interpreter_entry_point_offset) {
        *reinterpret_cast<void **>(
            reinterpret_cast<uintptr_t>(this) + interpreter_entry_point_offset) =
            reinterpret_cast<void *>(&art_interpreter_to_compiled_code_bridge_);
    }
}

BackupTo() 则负责把原始 target 信息复制进 backup：

// 文件：lsplant/src/main/jni/art/runtime/art_method.cxx

void BackupTo(ArtMethod *backup) {
    // 先把 target 标记成不要继续编译。
    SetNonCompilable();

    // 复制完整 ArtMethod 内容到 backup。
    // 注意：这是内部结构拷贝，不是公开 API。
    backup->CopyFrom(this);

    // 清掉 fast interpreter 到 interpreter 的特殊调用标记。
    ClearFastInterpretFlag();

    // 非静态 backup 改成 private，避免虚分派或访问规则引入额外路径。
    if (!backup->IsStatic()) {
        backup->SetPrivate();
    }
}

backup 不是简单保存一个函数指针，而是保存一份 ArtMethod 状态。这也是为什么 backup.invoke(...) 能走原方法逻辑。

流程拆解

总体调用链

实际执行时的两条路径

Hook 后目标方法有两条常用路径。

第一条是 replacement 路径：

LSPTest.staticMethod()
  -> target.quick_entry = trampoline
  -> trampoline 读取 hook.quick_entry
  -> hook stub 收集参数 Object[]
  -> Hooker.callback(args)
  -> Replacement.staticMethodReplacement(callback)
  -> return true

第二条是 backup 路径：

hooker.backup.invoke(null)
  -> backup ArtMethod
  -> backup 保留 target 被 Hook 前的 ArtMethod 内容
  -> 执行原始 staticMethod()
  -> return false

这就是为什么测试里可以同时断言：

Assert.assertTrue(LSPTest.staticMethod());
Assert.assertFalse((boolean) hooker.backup.invoke(null));

UnHook 路径

UnHook() 的核心动作是用 backup 覆盖 target，再恢复 access flags：

// 文件：lsplant/src/main/jni/lsplant.cc

bool DoUnHook(ArtMethod *target, ArtMethod *backup) {
    ScopedGCCriticalSection section(
        art::Thread::Current(),
        art::gc::kGcCauseDebugger,
        art::gc::kCollectorTypeDebugger);
    ScopedSuspendAll suspend("LSPlant Hook", false);

    // 先保存 target 当前 flags 和 trampoline 地址。
    auto access_flags = target->GetAccessFlags();
    auto *entry_point = target->GetEntryPoint();

    // 用 backup 的 ArtMethod 内容恢复 target。
    target->CopyFrom(backup);

    // 恢复 target 原来的访问标记。
    target->SetAccessFlags(access_flags);

    // 如果 trampoline 来自外部 allocator，可以回收。
    if (auto *start = __builtin_align_down(entry_point, kPageSize);
        executable_memory_recycler &&
        !mmap_regions.contains(start) &&
        !dual_regions.contains(start)) {
        executable_memory_recycler(entry_point);
    }

    return true;
}

注意

LSPlant 的公开注释明确提醒： UnHook() 后再调用之前返回的 backup，行为未定义。因为 target/backup 关系、全局引用和入口状态已经被清理。

原理分析

quick entry 是什么

在 ART 中，一个 Java 方法运行时对应一个 ArtMethod 。 ArtMethod 内部会保存若干与执行相关的入口，其中本文关注的是 quick compiled code entry。

可以把它理解为：

ArtMethod
  access_flags_
  declaring_class_
  dex_method_index_
  data_
  entry_point_from_quick_compiled_code_

普通 quick 调用时，ART 会从当前方法的 ArtMethod 里取 quick entry，然后跳转执行。LSPlant 利用的正是这一点：不改调用点，也不改 Java 字节码，而是改被调用方法自己的入口。

这类 Hook 的优点是：

  • 调用方不需要重新编译。
  • 对反射调用、普通调用都可能生效。
  • target 和 backup 都可以用 Method 反射对象表示。

限制也很明确：

  • 已经被调用方内联进 caller 的场景不会自动生效。
  • ART 可能在类初始化、JIT 编译、debug instrumentation 中重新设置 entry。
  • ArtMethod 布局和 entry 偏移不是公开 ABI。

为什么要暂停线程和进入 GC 临界区

DoHook() 不是普通业务字段修改。它改的是运行时正在使用的执行入口。

如果其他线程同时调用 target，可能出现：

  • target 已经复制到 backup，但 quick entry 还没改完。
  • JIT 或 ClassLinker 正在更新同一个方法入口。
  • GC、调试器或 instrumentation 正在遍历线程栈和方法元数据。

因此 LSPlant 在入口替换时使用：

ScopedGCCriticalSection
  -> 告诉 ART 当前处于特殊 GC 临界区
ScopedSuspendAll
  -> 暂停其他线程

这不能让所有风险消失，但能显著降低修改 ArtMethod 时的并发窗口。

为什么需要 JIT 和 ClassLinker 保护

如果只实现 target->SetEntryPoint(trampoline) ，在简单 demo 里可能能跑，但复杂场景很容易失效。

例如：

  • 类还没初始化时，静态方法可能先指向 resolution/static trampoline。
  • 类初始化完成后， ClassLinker::FixupStaticTrampolines 会批量修正静态方法入口。
  • JIT 编译完成后，ART 可能把方法入口改成新的 compiled code。
  • JIT code cache 回收时，obsolete method 可能移动。
  • Java debuggable 或 method tracing 场景下，Instrumentation 可能把入口改成解释器入口。

LSPlant 为这些情况做了传播和恢复。

class.cxx 会在类状态变成 initialized 前备份 hooked static method 的旧入口：

// 文件：lsplant/src/main/jni/art/mirror/class.cxx

static void BackupClassMethods(const dex::ClassDef *class_def, art::Thread *self) {
    BackupMethods out;
    if (!class_def) return;

    // 找出这个 class_def 下已经 Hook 的静态方法。
    hooked_classes_.if_contains(class_def, [&out](const auto &it) {
        for (auto method : it.second) {
            if (method->IsStatic()) {
                // 保存当前 entry，后面 ClassLinker 修复完静态 trampoline 后再恢复。
                out.emplace(method, method->GetEntryPoint());
            }
        }
    });

    if (!out.empty()) {
        std::unique_lock lk(backup_methods_lock_);
        backup_methods_[self].emplace(class_def, std::move(out));
    }
}

class_linker.cxx 在 FixupStaticTrampolines 后恢复 target 的 LSPlant trampoline，并把新入口传播给 backup：

// 文件：lsplant/src/main/jni/art/runtime/class_linker.cxx

static void RestoreBackup(const dex::ClassDef *class_def, art::Thread *self) {
    auto methods = mirror::Class::PopBackup(class_def, self);

    for (const auto &[art_method, old_trampoline] : methods) {
        // ClassLinker 可能刚刚给 art_method 写了新入口。
        auto new_trampoline = art_method->GetEntryPoint();

        // 对 target 恢复 LSPlant 原来的 trampoline。
        art_method->SetEntryPoint(old_trampoline);

        auto deoptimized = IsDeoptimized(art_method);
        auto backup_method = IsHooked(art_method);

        if (backup_method) {
            // 如果不是 deoptimized，把 ClassLinker 新生成的入口同步给 backup。
            // 这样 backup.invoke(...) 仍然能走原始方法的新可执行入口。
            if (!deoptimized && new_trampoline != old_trampoline) {
                backup_method->SetEntryPoint(new_trampoline);
            }
        }
    }
}

JIT 相关逻辑也类似。 jit.cxx 在编译任务里把 target 的编译传播给 backup，避免编译器直接覆盖 target：

// 文件：lsplant/src/main/jni/art/runtime/jit/jit.cxx

inline static auto AddCompileTask_ =
    "_ZN3art3jit3Jit14AddCompileTaskEPNS_6ThreadEPNS_9ArtMethodENS_15CompilationKindEb"_sym
        .hook->*[]
    <MemBackup auto backup>
    (Jit *thiz,
     Thread *self,
     ArtMethod *method,
     CompilationKind compilation_kind,
     bool precompile) static -> void {
        // 只处理非预编译的 optimized 编译任务。
        if (compilation_kind == kOptimized && !precompile) {
            if (auto b = IsHooked(method); b) {
                // target 已经 Hook，则把编译任务转给 backup。
                method = b;
            }
        }
        return backup(thiz, self, method, compilation_kind, precompile);
    };

art_quick_to_interpreter_bridge 解决什么问题

LSPlant 的 Deoptimize() 最终会尝试把一个非 native 方法的入口切到解释器：

// 文件：lsplant/src/main/jni/lsplant.cc

[[maybe_unused]] bool Deoptimize(JNIEnv *env, jobject method) {
    auto *art_method = ArtMethod::FromReflectedMethod(env, method);

    // 记录原方法为 deoptimized。如果它已被 Hook，实际对 backup 做去优化。
    RecordDeoptimized(art_method->GetDeclaringClass()->GetClassDef(), art_method);
    if (auto *backup = IsHooked(art_method); backup) {
        art_method = backup;
    }

    if (!art_method || art_method->IsNative()) {
        return false;
    }

    return ClassLinker::SetEntryPointsToInterpreter(art_method);
}

ClassLinker::SetEntryPointsToInterpreter() 有两条路径：

// 文件：lsplant/src/main/jni/art/runtime/class_linker.cxx

static bool SetEntryPointsToInterpreter(ArtMethod *art_method) {
    // native 方法不能切到 Java 解释器。
    if (art_method->IsNative()) {
        return false;
    }

    // 如果当前 Android 版本能解析到 ClassLinker::SetEntryPointsToInterpreter，
    // 直接调用 ART 自己的实现。
    if (SetEntryPointsToInterpreter_) {
        SetEntryPointsToInterpreter_(nullptr, art_method);
        return true;
    }

    // 某些版本符号不可用时，退回为手动设置 quick entry 到 quick-to-interpreter bridge。
    if (art_quick_to_interpreter_bridge_) {
        art_method->SetEntryPoint(
            reinterpret_cast<void *>(&art_quick_to_interpreter_bridge_));
        return true;
    }

    return false;
}

art_quick_to_interpreter_bridge 是 ART 的 quick 调用世界通往解释器的桥。以 ARM64 为例，AOSP 的汇编入口会做三件事：

保存 quick 调用参数和引用寄存器
把 method、Thread*、当前 quick frame 栈指针传给 C++ bridge
调用 artQuickToInterpreterBridge 后恢复现场，并处理返回值或异常

C++ 侧的 artQuickToInterpreterBridge 会继续：

检查方法是否可调用
根据 ArtMethod 找到 shorty 和 Dex code item
把 quick ABI 中的参数搬进 ShadowFrame
必要时确保声明类已经初始化
调用 EnterInterpreterFromEntryPoint 进入解释器
处理 deoptimize、异常和返回值

所以去优化后的调用链会变成：

caller quick compiled code
  -> callee ArtMethod.quick_entry = art_quick_to_interpreter_bridge
  -> 保存 quick 参数
  -> 构造解释器 ShadowFrame
  -> EnterInterpreterFromEntryPoint
  -> 解释执行 callee 的 Dex 指令

这对 Hook 很重要：如果某个 caller 已经把 callee 内联了，单独 Hook callee 不一定能命中。把 caller 或相关方法 deoptimize 后，caller 会回到解释执行或不再使用已内联的 quick compiled code，更容易重新走方法分派。

quick bridge 和 LSPlant trampoline 的区别

二者都可能被写进 ArtMethod 的 quick entry，但语义完全不同：

入口写入对象目的
LSPlant trampoline被 Hook 的 target 方法把 target 调用转发到 hook stub
art_quick_to_interpreter_bridge被 deoptimize 的方法，或旧版本 interpreter entry 辅助路径把 quick 调用转入解释器

LSPlant trampoline 的下一跳是 hook ArtMethod.quick_entry 。 art_quick_to_interpreter_bridge 的下一跳是 ART 解释器。

不要把这两个入口混在一起：

  • Hook target： target.quick_entry = lsplant_trampoline
  • Deoptimize backup/caller： method.quick_entry = art_quick_to_interpreter_bridge

版本差异

LSPlant 代码里已经体现了不少版本差异，复现时需要特别注意：

Android 版本差异点
Android 5.x可能存在 java.lang.reflect.ArtMethod ，并有单独的 interpreter entry 偏移
Android 6.0-7.x反射基类为 AbstractMethod ， artMethod 字段可用于取 ArtMethod*
Android 8.0+反射基类变成 Executable
Android 9+SetNotIntrinsic 、Java debuggable、Instrumentation 分支更重要
Android 11+kAccPreCompiled 、JniIdManager、class status 等行为继续变化
Android 13 附近SetEntryPointsToInterpreter 符号可能不可用，LSPlant 会尝试解析或推导 art_quick_to_interpreter_bridge
Android 17/API 37README 声明支持，但厂商分支和预览实现仍需重新验证内部符号和偏移

这也是 LSPlant 初始化为什么要做这么多探测，而不是写死一套结构体。

常见错误与排查

LSPTest.initHooker() 返回 false

常见原因：

  • JNI_OnLoad() 没有拿到 JNIEnv* 。
  • xdl_open("libart.so") 失败。
  • InitInfo 中的 inline_hooker 、 inline_unhooker 、 art_symbol_resolver 为空。
  • 当前系统的 libart.so 符号和 LSPlant 适配逻辑不匹配。
  • C++ modules、NDK、CMake 版本不满足当前源码要求。

排查方式：

adb logcat -s LSPlant:D LSPlant-test:D '*:S'
./gradlew :test:assembleDebug --stacktrace

重点看是否有：

Failed to find artMethod field
Failed to init art method
Failed to init class linker
Failed to find GetMethodShorty

Hook() 返回 null

常见原因：

  • target_method 不是 Method 或 Constructor 。
  • callback_method 不是 Hooker.callback(Object[]) 这样的可执行反射对象。
  • 同一个 target 已经被 Hook，触发 Skip duplicate hook 。
  • BuildDex() 生成类失败。
  • callback_method 所属类和 hooker_object 不匹配。

排查重点：

var callbackMethod = Hooker.class.getDeclaredMethod("callback", Object[].class);
var result = hooker.doHook(target, callbackMethod);

不要把 Replacement.class.getDeclaredMethod(...) 直接传给 native 的 callback_method 。测试工程里 Replacement 是由 Hooker.callback() 间接反射调用的。

Hook 后没有命中 replacement

常见原因：

  • 调用方已经内联了目标方法。
  • Hook 的不是实际运行时调用的那个重载或桥方法。
  • target 类还没初始化，后续 FixupStaticTrampolines 又改了入口。
  • JIT 或 instrumentation 重新设置了 method code。

排查建议：

  • 先 Hook 一个普通非内联热点的小方法，确认主链路正常。
  • 对 caller 做 lsplant::Deoptimize() ，而不是只 deoptimize callee。
  • 确认方法签名，尤其是 Kotlin 默认参数、synthetic bridge、泛型擦除后的签名。
  • 打开日志观察 Done hook 后 entrypoint 是否又被后续日志更新。

backup.invoke(...) 崩溃或结果不对

常见原因：

  • backup 在 UnHook() 后继续使用，属于未定义行为。
  • 非静态方法调用 backup 时忘记传 this 。
  • 参数数组和目标签名不匹配。
  • proxy、abstract、intrinsic 方法走了特殊分支，当前 Android 版本适配不足。

排查建议：

// 静态方法 backup 没有 this。
hooker.backup.invoke(null);

// 非静态方法 backup 的第一个反射接收者是原对象。
hooker.backup.invoke(test, a, b, c);

ARM64 设备上出现 SIGSEGV 或非法指令

常见原因：

  • trampoline 内存不可执行或写入失败。
  • 写入 trampoline 后没有清理 instruction cache。
  • ArtMethod::entrypoint offset 探测错误。
  • 厂商 ROM 修改了 ART 布局或符号。
  • 自定义 allocator 没有满足可执行内存和生命周期要求。

排查建议：

  • 先不要提供自定义 executable_memory_allocator ，让 LSPlant 使用默认 memfd/ashmem/mmap 路径。
  • 打印 ArtMethod::entrypoint offset 和 trampoline 地址。
  • 确认设备 ABI 是 arm64-v8a ，不要把 ARM64 结论套到 32 位 ARM。
  • 若系统启用了更严格的 W^X 策略，优先使用 RX/RW 双映射，不要长期依赖 RWX。

art_quick_to_interpreter_bridge 解析失败

常见原因：

  • 当前系统隐藏或裁剪了相关符号。
  • ClassLinker::SetEntryPointsToInterpreter 和 bridge 符号都无法解析。
  • xDL 没有查到 .symtab 。
  • ART 版本已经改变了符号名或入口组织方式。

排查建议：

  • 先看 ClassLinker::SetEntryPointsToInterpreter 是否可用，可用时不需要手动 bridge fallback。
  • 检查 art_symbol_resolver 是否同时查了 xdl_sym 和 xdl_dsym 。
  • 在目标设备上用符号工具确认 libart.so 是否保留目标符号。
  • 对新 Android 版本不要只改符号名，必须重新理解该版本 ClassLinker 和 entrypoint 初始化流程。

总结

LSPlant 的 Java 方法 Hook 主线可以概括成一句话：

动态生成签名兼容的 hook/backup Dex 方法，再把 target ArtMethod 的 quick entry 改成指向 hook ArtMethod 的 trampoline。

围绕这句话，本文拆了四层：

  • Java 层： Hooker.hook() 保存上下文， Hooker.callback(Object[]) 统一转发到 replacement。
  • native 层： lsplant::Hook() 生成 stub、取 ArtMethod* 、记录 target/backup 关系。
  • ARM64 入口：trampoline 读取 hook ArtMethod* ，再跳到 hook.quick_entry 。
  • 解释器桥： art_quick_to_interpreter_bridge 把 quick 调用转成解释器执行，用于 deoptimize 和内联规避。
