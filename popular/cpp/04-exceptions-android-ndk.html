C++ 异常机制：try/catch/throw 与 Android NDK 的限制和成本

C++ 异常经常被简化成一句话： throw 抛出， catch 捕获。真正写项目时，更重要的问题通常是：

  • 什么时候应该抛异常，什么时候不应该抛？
  • 抛异常时，局部对象会不会析构？
  • 为什么推荐 “按值抛出、按引用捕获”？
  • catch 的顺序为什么会影响结果？
  • 在 Android NDK 里，C++ 异常能不能直接穿过 JNI 边界抛给 Java/Kotlin？
  • 打开异常支持会增加哪些成本？

本文用两个可以复现的示例回答这些问题：

  1. 一个本地 CMake 示例：观察 try 、 catch 、 throw 、栈展开和 RAII 清理。
  2. 一个 Android NDK/JNI 示例：在 native 层抛 C++ 异常，在 JNI 边界捕获并转换成 Java 异常。

目标效果

复现完成后，你应该能写出这样的 native 代码：核心 C++ 逻辑可以用异常表达 “无法完成任务”，但所有 JNI 导出函数都负责把 C++ 异常截住，再通过 ThrowNew 转成 Java/Kotlin 能处理的异常。

2. 先跑通本地 C++ 异常示例

这个小项目模拟 “解析订单并计算金额”。输入合法时返回总价；输入非法时抛出自定义异常 OrderError 。程序会打印每个作用域的进入和离开日志，用来观察异常抛出后局部对象是否被析构。

2.3 核心源码

文件路径： src/main.cpp

// src/main.cpp
// 作用：演示 C++17 中 try/catch/throw、栈展开、RAII 清理和 rethrow。

#include <exception>  // 使用 std::exception 作为通用异常基类。
#include <iomanip>    // 使用 std::fixed 和 std::setprecision 格式化金额。
#include <iostream>   // 使用 std::cout 输出验证日志。
#include <sstream>    // 使用 std::istringstream 拆分输入文本。
#include <stdexcept>  // 使用 std::runtime_error、std::invalid_argument、std::out_of_range。
#include <string>     // 使用 std::string 保存文本。

// OrderError 是业务异常类型。
// 继承 std::runtime_error 后，可以通过 what() 返回错误消息。
class OrderError : public std::runtime_error {
public:
    // explicit 防止 const char* 或 std::string 被意外隐式转换成 OrderError。
    explicit OrderError(const std::string& message)
        : std::runtime_error(message) {}
};

// Trace 是一个 RAII 辅助类。
// 构造函数打印进入作用域，析构函数打印离开作用域。
// 当异常导致栈展开时，已经构造成功的局部对象仍会析构。
class Trace {
public:
    // scope 保存当前作用域名称，用于输出日志。
    explicit Trace(std::string scope)
        : scope_(std::move(scope)) {
        std::cout << "[enter] " << scope_ << '\n';
    }

    // 析构函数默认不应该抛异常。
    // noexcept 明确告诉读者和编译器：这个清理动作不会抛出异常。
    ~Trace() noexcept {
        std::cout << "[leave] " << scope_ << '\n';
    }

    // Trace 只用于观察当前作用域，不需要复制。
    Trace(const Trace&) = delete;
    Trace& operator=(const Trace&) = delete;

private:
    std::string scope_; // 当前作用域名称。
};

// Order 保存解析后的订单数据。
struct Order {
    std::string sku;   // 商品 SKU。
    int count;         // 购买数量，必须为正数。
    double unit_price; // 单价，必须大于等于 0。
};

// parse_int 把文本解析成 int。
// 参数 text 是待解析文本，field_name 用于生成清晰的错误消息。
int parse_int(const std::string& text, const std::string& field_name) {
    std::size_t parsed_length = 0; // std::stoi 实际解析的字符数量。

    try {
        // std::stoi 可能抛 std::invalid_argument 或 std::out_of_range。
        int value = std::stoi(text, &parsed_length, 10);

        // parsed_length 不等于 text.size() 说明存在尾随字符，例如 "12abc"。
        if (parsed_length != text.size()) {
            throw OrderError(field_name + " has trailing characters: " + text);
        }

        return value;
    } catch (const std::invalid_argument&) {
        // 捕获标准库异常后，转换成更贴近业务语义的 OrderError。
        throw OrderError(field_name + " is not an integer: " + text);
    } catch (const std::out_of_range&) {
        // 数字超出 int 范围时，给调用方一个可理解的错误消息。
        throw OrderError(field_name + " is out of int range: " + text);
    }
}

// parse_double 把文本解析成 double。
// 写法和 parse_int 类似，但使用 std::stod。
double parse_double(const std::string& text, const std::string& field_name) {
    std::size_t parsed_length = 0;

    try {
        double value = std::stod(text, &parsed_length);

        if (parsed_length != text.size()) {
            throw OrderError(field_name + " has trailing characters: " + text);
        }

        return value;
    } catch (const std::invalid_argument&) {
        throw OrderError(field_name + " is not a number: " + text);
    } catch (const std::out_of_range&) {
        throw OrderError(field_name + " is out of double range: " + text);
    }
}

// parse_order 解析一行订单文本。
// 输入格式固定为：SKU 数量 单价，例如 "BOOK-CPP 2 79.5"。
Order parse_order(const std::string& line) {
    Trace trace("parse_order");

    std::istringstream input(line); // 把字符串包装成输入流，方便用 >> 拆字段。
    std::string sku;
    std::string count_text;
    std::string price_text;

    // 如果缺少任一字段，说明输入格式错误。
    if (!(input >> sku >> count_text >> price_text)) {
        throw OrderError("order line must be: <sku> <count> <unit_price>");
    }

    // 解析数量和价格。这里可能抛 OrderError。
    int count = parse_int(count_text, "count");
    double unit_price = parse_double(price_text, "unit_price");

    return Order{sku, count, unit_price};
}

// calculate_total 计算订单总价。
// 参数 order 按 const 引用传入，避免复制并防止函数修改订单。
double calculate_total(const Order& order) {
    Trace trace("calculate_total");

    if (order.count <= 0) {
        throw OrderError("count must be positive");
    }

    if (order.unit_price < 0.0) {
        throw OrderError("unit_price must not be negative");
    }

    return static_cast<double>(order.count) * order.unit_price;
}

// run_case 包住一条完整流程：解析、计算、捕获异常。
void run_case(const std::string& line) {
    std::cout << "\n-- case: \"" << line << "\" --\n";
    Trace trace("run_case");

    try {
        Order order = parse_order(line);
        double total = calculate_total(order);

        std::cout << "result: " << order.sku
                  << " total=" << std::fixed << std::setprecision(2)
                  << total << '\n';
    } catch (const OrderError& error) {
        // 先捕获更具体的业务异常。
        // catch by const reference 可以避免异常对象切片和不必要复制。
        std::cout << "caught OrderError: " << error.what() << '\n';
    } catch (const std::exception& error) {
        // 再捕获标准异常基类，兜住其他标准库异常。
        std::cout << "caught std::exception: " << error.what() << '\n';
    }
}

// rethrow_demo 演示重新抛出当前异常。
void rethrow_demo() {
    std::cout << "\n-- rethrow demo --\n";

    try {
        try {
            throw OrderError("database is offline");
        } catch (const OrderError& error) {
            std::cout << "inner log: " << error.what() << '\n';

            // throw; 表示重新抛出“当前正在处理的原始异常”。
            // 不要写 throw error;，那会创建一个新的异常对象。
            throw;
        }
    } catch (const std::exception& error) {
        std::cout << "outer catch: " << error.what() << '\n';
    }
}

int main() {
    std::cout << "== local C++ exception lab ==\n";

    run_case("BOOK-CPP 2 79.5");    // 合法输入。
    run_case("BOOK-CPP 0 79.5");    // 数量非法，会在 calculate_total 抛异常。
    run_case("BOOK-CPP two 79.5");  // 数量不是整数，会在 parse_int 抛异常。
    run_case("BOOK-CPP 2 -1.0");    // 单价非法，会在 calculate_total 抛异常。

    rethrow_demo();

    return 0;
}

3. 分解 try/catch/throw 的关键规则

3.1 throw 表示当前函数无法完成任务

parse_int 里的这句代码：

throw OrderError(field_name + " is not an integer: " + text);

含义不是 “普通分支跳转”，而是：当前函数无法把输入转换成合法整数，继续返回一个普通 int 会误导调用方，所以把错误交给外层处理。

适合用异常表达的场景：

  • 构造函数无法建立对象不变量。
  • 函数无法产生承诺的返回值。
  • 调用方传入的参数不满足函数契约。
  • 底层资源获取失败，例如文件、网络、内存。

不适合用异常表达的场景：

  • 正常循环退出。
  • 高频分支判断。
  • 可以预期的大量失败结果，例如 “搜索不到某条记录”。
  • 跨语言 ABI 边界直接传播错误。

3.2 try 的范围要覆盖可能失败的完整流程

run_case 中的 try 包住解析和计算：

try {
    Order order = parse_order(line);
    double total = calculate_total(order);
    // ...
} catch (const OrderError& error) {
    // ...
}

这样设计的原因是：调用者关心的是 “一条订单能否处理成功”，而不是每个内部函数分别怎么失败。内部函数只负责发现错误并抛出，边界函数负责捕获和转成用户能理解的结果。

3.3 catch 顺序要从具体到宽泛

推荐顺序：

catch (const OrderError& error) {
    // 先处理业务异常。
} catch (const std::exception& error) {
    // 再处理标准异常基类。
}

如果反过来写：

catch (const std::exception& error) {
    // OrderError 也会先匹配到这里。
} catch (const OrderError& error) {
    // 这段通常没有机会执行。
}

OrderError 继承自 std::runtime_error ，而 std::runtime_error 继承自 std::exception 。更宽泛的 catch 放前面，会把派生类异常提前截走。

3.4 按值抛出，按 const 引用捕获

推荐：

throw OrderError("count must be positive");

catch (const OrderError& error) {
    std::cout << error.what() << '\n';
}

原因：

  • 按值抛出：异常运行时会管理异常对象的生命周期，不需要你手动 new 或 delete 。
  • 按引用捕获：避免复制异常对象。
  • 按基类值捕获会发生对象切片，派生类信息可能丢失。

避免：

throw new OrderError("bad"); // 不要抛裸指针，容易泄漏和混乱所有权。

catch (std::exception error) {
    // 不要按基类值捕获，派生类部分可能被切掉。
}

3.5 栈展开与 RAII

当 calculate_total 抛出异常时，程序不会直接跳到 catch 后完全忽略中间对象。它会沿调用栈向外查找匹配的处理器，并销毁已经构造完成的局部对象。这个过程叫栈展开。

在示例里， Trace 的析构日志证明了这一点：

[enter] calculate_total
[leave] calculate_total
caught OrderError: count must be positive

这也是 RAII 能和异常配合的核心原因。把资源放进对象里，让析构函数负责释放资源，异常路径和正常路径都能清理。

常见 RAII 资源类型：

  • std::unique_ptr 管理堆对象。
  • std::vector 管理动态数组。
  • 文件句柄包装类在析构函数里关闭文件。
  • 互斥锁包装类在析构函数里解锁。

注意

析构函数不要抛异常。尤其是在栈展开过程中，如果析构函数再次抛出异常，程序通常会调用 std::terminate 终止。

3.6 noexcept 表示不允许异常逃出函数

Trace 的析构函数写成：

~Trace() noexcept {
    std::cout << "[leave] " << scope_ << '\n';
}

noexcept 的意思是：异常不应该从这个函数逃出去。它常用于析构函数、移动构造、移动赋值、 swap 等底层操作。

注意， noexcept 不是 “自动捕获异常”。如果一个 noexcept 函数真的让异常逃出，程序会终止。因此不要为了 “优化” 随手给所有函数加 noexcept ，只在你能保证失败不会通过异常传播时使用。

4. Android NDK 示例：在 JNI 边界转换异常

本节做一个最小 Android App。Java 层调用 native 方法 describeOrder("3") 、 describeOrder("0") 、 describeOrder("abc") ：

  • "3" ：native 返回成功字符串。
  • "0" ：native 抛 C++ ParseError ，JNI 边界捕获后转成 Java IllegalArgumentException 。
  • "abc" ：同样转成 Java IllegalArgumentException 。

4.5 Java 入口代码

文件路径： app/src/main/java/com/example/ndkexceptionlab/MainActivity.java

// app/src/main/java/com/example/ndkexceptionlab/MainActivity.java
// 作用：加载 native 库，调用 JNI 方法，并显示 Java 捕获到的异常。

package com.example.ndkexceptionlab;

import android.app.Activity;
import android.os.Bundle;
import android.widget.TextView;

public class MainActivity extends Activity {
    static {
        // 加载 CMake 生成的 libnative_exception_lab.so。
        // System.loadLibrary 参数不带 lib 前缀，也不带 .so 后缀。
        System.loadLibrary("native_exception_lab");
    }

    // native 表示方法实现在 C/C++ 层。
    // 方法名、包名、参数类型需要和 native-lib.cpp 中的 JNI 函数对应。
    private native String describeOrder(String input);

    @Override
    protected void onCreate(Bundle savedInstanceState) {
        super.onCreate(savedInstanceState);

        // TextView 用来显示每个测试用例的执行结果。
        TextView resultView = new TextView(this);
        resultView.setTextSize(16.0f);
        resultView.setPadding(32, 32, 32, 32);
        resultView.setText(runCases());

        setContentView(resultView);
    }

    // runCases 依次调用 native 方法，观察成功返回和异常转换。
    private String runCases() {
        StringBuilder output = new StringBuilder();

        callNative(output, "3");   // 合法输入，应该成功返回。
        callNative(output, "0");   // 非法输入，native 转成 IllegalArgumentException。
        callNative(output, "abc"); // 非法输入，native 转成 IllegalArgumentException。

        return output.toString();
    }

    // callNative 把单次调用包在 Java try/catch 里。
    private void callNative(StringBuilder output, String input) {
        try {
            String result = describeOrder(input);
            output.append("input=")
                    .append(input)
                    .append(" -> ")
                    .append(result)
                    .append('\n');
        } catch (IllegalArgumentException error) {
            // C++ ParseError 会在 JNI 边界被转换成这个异常。
            output.append("input=")
                    .append(input)
                    .append(" -> Java caught ")
                    .append(error.getClass().getSimpleName())
                    .append(": ")
                    .append(error.getMessage())
                    .append('\n');
        }
    }
}

4.7 Native 核心源码

文件路径： app/src/main/cpp/native-lib.cpp

// app/src/main/cpp/native-lib.cpp
// 作用：演示 Android NDK 中 C++ 异常如何在 JNI 边界被捕获并转换成 Java 异常。

#include <jni.h>       // JNI 类型和函数，例如 JNIEnv、jstring、JNIEXPORT。
#include <stdexcept>   // std::runtime_error、std::invalid_argument、std::out_of_range。
#include <string>      // std::string。

namespace {

// ParseError 表示 native 核心逻辑的解析错误。
// 它只在 C++ 层传播，不直接跨 JNI 边界传给 Java。
class ParseError : public std::runtime_error {
public:
    explicit ParseError(const std::string& message)
        : std::runtime_error(message) {}
};

// ScopedUtfChars 是一个 RAII 包装类。
// 它负责从 jstring 获取 UTF-8 字符，并在析构函数中释放。
class ScopedUtfChars {
public:
    // env 是当前线程的 JNI 环境指针。
    // value 是 Java 传入的 String 对象。
    ScopedUtfChars(JNIEnv* env, jstring value)
        : env_(env), value_(value), chars_(env->GetStringUTFChars(value, nullptr)) {}

    // 析构函数释放 GetStringUTFChars 获取的资源。
    // 如果 chars_ 为 nullptr，说明获取失败，不需要释放。
    ~ScopedUtfChars() noexcept {
        if (chars_ != nullptr) {
            env_->ReleaseStringUTFChars(value_, chars_);
        }
    }

    ScopedUtfChars(const ScopedUtfChars&) = delete;
    ScopedUtfChars& operator=(const ScopedUtfChars&) = delete;

    // get 返回底层 const char*。
    // 返回 nullptr 通常表示 JVM 已经设置了待处理异常，例如 OutOfMemoryError。
    const char* get() const noexcept {
        return chars_;
    }

private:
    JNIEnv* env_;       // JNI 环境指针，不拥有对象。
    jstring value_;     // 原始 Java String，不拥有对象。
    const char* chars_; // JVM 提供的 UTF-8 字符指针，需要 Release。
};

// parse_positive_count 是纯 C++ 核心逻辑。
// 它不知道 JNI，也不调用 Java API；失败时抛 ParseError。
int parse_positive_count(const std::string& text) {
    if (text.empty()) {
        throw ParseError("count is empty");
    }

    std::size_t parsed_length = 0;

    try {
        int value = std::stoi(text, &parsed_length, 10);

        if (parsed_length != text.size()) {
            throw ParseError("count has trailing characters: " + text);
        }

        if (value <= 0) {
            throw ParseError("count must be positive: " + text);
        }

        return value;
    } catch (const std::invalid_argument&) {
        throw ParseError("count is not an integer: " + text);
    } catch (const std::out_of_range&) {
        throw ParseError("count is out of int range: " + text);
    }
}

// throw_java_exception 把 C++ 错误消息转换成 Java 异常。
// class_name 使用 JNI 类名格式，例如 "java/lang/IllegalArgumentException"。
void throw_java_exception(JNIEnv* env, const char* class_name, const std::string& message) {
    jclass exception_class = env->FindClass(class_name);

    // 如果 FindClass 失败，JVM 已经设置了一个待处理异常。
    // 此时不能继续随意调用 JNI 函数，直接返回即可。
    if (exception_class == nullptr) {
        return;
    }

    // ThrowNew 不会像 C++ throw 那样展开 native 栈。
    // 它是在当前 Java 线程上设置一个待处理 Java 异常。
    env->ThrowNew(exception_class, message.c_str());
}

} // namespace

extern "C" JNIEXPORT jstring JNICALL
Java_com_example_ndkexceptionlab_MainActivity_describeOrder(
        JNIEnv* env,
        jobject /* this_object */,
        jstring input) {
    try {
        if (input == nullptr) {
            throw ParseError("input is null");
        }

        // 用 RAII 管理 GetStringUTFChars / ReleaseStringUTFChars。
        ScopedUtfChars chars(env, input);

        // chars.get() 为 nullptr 时，通常已有 Java 异常待处理，例如 OutOfMemoryError。
        // 这里直接返回 nullptr，让异常回到 Java 层。
        if (chars.get() == nullptr) {
            return nullptr;
        }

        // 从 JNI 字符串转成 std::string 后，后续逻辑保持纯 C++。
        int count = parse_positive_count(std::string(chars.get()));

        std::string message = "native accepted count=" + std::to_string(count);

        // NewStringUTF 可能因为内存不足返回 nullptr，并设置 Java 异常。
        // 如果成功，返回 Java String；如果失败，直接把 pending exception 交还 Java。
        return env->NewStringUTF(message.c_str());
    } catch (const ParseError& error) {
        // 在 JNI 边界捕获业务异常，转换成 Java IllegalArgumentException。
        throw_java_exception(env, "java/lang/IllegalArgumentException", error.what());
        return nullptr;
    } catch (const std::exception& error) {
        // 兜住其他 C++ 标准异常，转换成 Java RuntimeException。
        throw_java_exception(env, "java/lang/RuntimeException", error.what());
        return nullptr;
    } catch (...) {
        // 兜住非 std::exception 异常。生产代码应尽量避免抛这种异常。
        throw_java_exception(env, "java/lang/RuntimeException", "unknown native exception");
        return nullptr;
    }
}

这个文件里最重要的边界是：

  • parse_positive_count 是纯 C++ 逻辑，可以抛 ParseError 。
  • Java_com_example...describeOrder 是 JNI 导出函数，必须捕获所有 C++ 异常。
  • throw_java_exception 使用 JNI ThrowNew 设置 Java 异常，而不是继续抛 C++ 异常。

5. Android NDK 中异常使用的限制

5.1 CMake 默认支持 C++ 异常，ndk-build 默认关闭

现代 NDK 使用 Clang 和 libc++。官方文档说明：

  • C++ 异常由 libc++ 支持。
  • CMake 和 standalone toolchain 默认启用 C++ 异常。
  • ndk-build 默认关闭 C++ 异常，需要显式开启。

如果你使用 CMake，通常不需要手动添加 -fexceptions 。如果你使用 ndk-build，可以在 Android.mk 的模块里写：

# Android.mk
# 作用：只给当前模块启用 C++ 异常支持。

LOCAL_CPP_FEATURES := exceptions

也可以在 Application.mk 里全局启用：

# Application.mk
# 作用：给整个 ndk-build 应用启用 C++ 异常支持。

APP_CPPFLAGS := -fexceptions

更推荐模块级 LOCAL_CPP_FEATURES := exceptions ，因为它表达的是 “这个模块需要异常能力”，而不是给所有模块硬塞编译参数。

注意

如果某个模块用 -fno-exceptions 编译，包含 throw 或 catch 的代码通常无法编译。不要假设所有第三方 native 库都允许 C++ 异常穿过它们的接口。

5.2 不要使用 system C++ runtime 承载异常代码

NDK 现在应优先使用 libc++。 system runtime 不是完整 C++ 标准库，只提供很有限的 C++ runtime ABI 能力，不支持异常处理和 RTTI。

CMake 下 ANDROID_STL 默认是 c++_static 。如果你的 App 只有一个 native shared library，静态 libc++ 通常可以工作；如果有多个 native shared library，必须认真处理 C++ runtime 的选择。

5.3 一个 App 内不要混用多个 C++ runtime

多个 .so 如果各自静态链接一份 C++ runtime，可能出现非常隐蔽的问题：

  • 在一个库里分配内存，在另一个库里释放，导致堆损坏。
  • 一个库抛出的异常在另一个库里捕获不到，导致崩溃。
  • std::string 、 std::vector 等标准库类型 ABI 不兼容。

实用建议：

  • 只有一个 native .so ：可以使用默认的 c++_static 。
  • 多个 native .so 且它们之间传递 C++ 对象或异常：优先统一使用 c++_shared ，并确保所有库使用同一 NDK/STL 配置。
  • 对外暴露给其他语言或第三方库的边界：尽量用 C ABI、状态码、错误对象，不要暴露 C++ 异常。

5.4 C++ 异常不能跨 JNI 边界传播到 Java/Kotlin

这是 Android NDK 里最容易踩的坑。

错误写法：

extern "C" JNIEXPORT void JNICALL
Java_com_example_App_bad(JNIEnv*, jobject) {
    // 不要让 C++ 异常逃出 JNI 函数。
    throw std::runtime_error("native failed");
}

正确写法：

extern "C" JNIEXPORT void JNICALL
Java_com_example_App_good(JNIEnv* env, jobject) {
    try {
        // 调用可能抛 C++ 异常的 native 核心逻辑。
    } catch (const std::exception& error) {
        jclass clazz = env->FindClass("java/lang/RuntimeException");
        if (clazz != nullptr) {
            env->ThrowNew(clazz, error.what());
        }
    }
}

原因是 JNI 的 Java 异常和 C++ 异常不是同一种机制。JNI 的 Throw / ThrowNew 是给当前线程设置一个 pending Java exception；它不会像 C++ throw 那样立刻展开 native 栈。native 函数返回到 managed 层后，Java/Kotlin 才会按自己的异常机制处理它。

5.5 有 pending Java exception 时不要继续随意调用 JNI

Android JNI 文档明确要求：当线程上已经有 pending exception 时，大多数 JNI 函数都不能再调用。你应该：

  • 检查返回值。
  • 使用 ExceptionCheck 或 ExceptionOccurred 判断是否有 pending exception。
  • 处理后返回到 Java/Kotlin。
  • 如果确实要吞掉异常，必须 ExceptionClear ，但不要无理由丢弃异常。

示例里的这段代码就是为了遵守这个规则：

ScopedUtfChars chars(env, input);

if (chars.get() == nullptr) {
    return nullptr;
}

GetStringUTFChars 返回 nullptr 时，JVM 可能已经设置了 OutOfMemoryError 。此时 native 方法直接返回，Java 层会看到该异常。

6. 异常的成本：不是不能用，而是要用在边界上

C++ 异常常被称为 “正常路径零成本”，这句话容易误解。更准确的说法是：在很多主流 ABI 和编译器实现里，没有异常发生时，编译器不会在每个调用点插入大量显式错误检查分支；它会生成额外的异常表、栈展开信息和 personality 函数相关元数据。

也就是说：

  • 正常路径通常没有 “每一步都判断错误码” 的运行时分支成本。
  • 二进制体积可能增加，因为需要异常表和 unwind 信息。
  • 真正抛出异常时成本较高，因为运行时要创建异常对象、查找处理器、展开调用栈、执行析构函数。
  • 抛异常的耗时不稳定，不适合硬实时路径或帧循环热路径。

在 Android 上还要额外考虑：

  • APK/AAB 体积敏感，异常和 libc++ runtime 都会影响 native 产物大小。
  • 多 .so 静态链接 runtime 可能导致异常跨库捕获失败。
  • JNI 边界必须转换异常，不能直接跨语言传播。
  • 一些团队为了体积或历史原因会使用 -fno-exceptions ，这会影响第三方库集成策略。

实用判断：

场景建议
构造对象失败、解析输入失败、资源获取失败可以使用异常
JNI 导出函数捕获所有 C++ 异常，转换成 Java 异常或错误码
C ABI、插件 ABI、跨 .so 边界避免直接传播 C++ 异常
高频循环、渲染帧、音频回调不要用异常做普通分支
禁用异常的工程使用 std::optional 、 std::expected 、错误码或结果对象

std::expected 版本提醒

std::expected 是 C++23 标准库能力。Android NDK 中 libc++ 对不同 C++ 标准库特性的支持会随 NDK 版本变化。如果目标工程仍使用 C++17，可以使用自定义结果类型、 std::optional 搭配错误信息，或项目内已有的 Result<T, E> 。

7. 常见错误和排查

7.1 报错：cannot use 'throw' with exceptions disabled

原因：当前目标被 -fno-exceptions 编译。

排查：

  • CMake 项目检查 CMakeLists.txt 、工具链文件、三方库配置中是否加入了 -fno-exceptions 。
  • Android Gradle + CMake 项目查看生成的 CMake 构建命令。AGP 会在构建目录保存 CMake 命令信息，可以搜索 build_command.txt 或查看 compile_commands.json 。
  • ndk-build 项目确认是否添加 LOCAL_CPP_FEATURES := exceptions 或 APP_CPPFLAGS := -fexceptions 。

7.2 Java 没捕获到异常，App 直接 native crash

原因：C++ 异常逃出了 JNI 导出函数。

排查：

  • 所有 extern "C" JNIEXPORT ... JNICALL Java_... 函数外层都加 try/catch 。
  • 至少捕获 const std::exception& 和 catch (...) 。
  • 在 catch 中使用 ThrowNew 或返回错误码，不要继续 throw; 。

7.3 JNI 报错：JNI DETECTED ERROR IN APPLICATION

可能原因：有 pending Java exception 时继续调用了不允许的 JNI 函数。

排查：

  • 对 FindClass 、 GetMethodID 、 Call*Method 、 NewStringUTF 等调用检查返回值。
  • 调用 Java 方法后，如果后续还要继续 JNI 操作，先用 ExceptionCheck 判断。
  • 有异常就返回，或明确 ExceptionClear 后完成补救逻辑。

7.4 异常跨 .so 捕获失败

可能原因：

  • 多个 native 库使用了不同 C++ runtime。
  • 第三方库和 App 使用不同 NDK/STL/ABI 配置。
  • 某个库禁用了异常。

排查：

  • 统一 NDK 版本。
  • 统一 STL 选择。
  • 多 native shared library 场景优先评估 c++_shared 。
  • 不在库边界暴露 C++ 异常，改用错误码或结果对象。

7.5 析构函数抛异常导致 terminate

原因：析构函数在栈展开过程中再次抛异常。

排查：

  • 析构函数写成 noexcept ，内部捕获并记录清理失败。
  • 把可能失败的关闭 / 提交动作移到显式成员函数，例如 close() 或 commit() 。
  • 析构函数只做 “尽力释放”，不要报告需要调用方恢复的业务错误。

8. 小结

C++ 异常适合表达 “函数无法完成承诺任务” 的失败，配合 RAII 可以让资源清理代码集中在析构函数里，避免每层手写错误码清理逻辑。

在 Android NDK 中，真正要守住的是边界：

  • C++ 核心逻辑内部可以抛异常。
  • JNI 导出函数必须捕获异常。
  • 使用 ThrowNew 转成 Java/Kotlin 异常。
  • 不要在 pending Java exception 状态下继续随意调用 JNI。
  • 不要让 C++ 异常穿过 JNI、C ABI、插件 ABI 或不受控的 .so 边界。

异常不是免费机制。正常路径通常较轻，但二进制体积会增加，真正抛出时成本高且不稳定。因此，把异常用于错误边界，而不是普通控制流，是更稳妥的工程选择。
